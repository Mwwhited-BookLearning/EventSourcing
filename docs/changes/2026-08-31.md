# 2026-08-31

## Added: `myTasks` GraphQL query over the flow engine's `PendingTask` read model

Continuing the PlantUML-native flow engine work (the queued ADR-101):
`Samples.Vitals.Flows` and `Samples.Meridian.Flows` now share one
physical SQLite file (`../pending-tasks.db`, relative to each worker's
own project directory, resolving to `src/pending-tasks.db` for both)
instead of two separate per-domain databases, so a single cross-domain
query can read both. `EventStore.Host.Sqlite` gained a read-only
`PendingTasksDbContext` registration and a new static
`EventStore.GraphQL.PendingTaskQueries` (`myTasks`), following the
existing `RegistryQueries` convention — no `ORDER BY` per the standing
"the task list can be out of order, it's just a query" instruction, with
in-memory `RequiredClaim` filtering via `RequiredClaimEvaluator`.
Verified live end to end: published a real `AdverseEventReported`,
confirmed the task appears in `myTasks` for a caller holding the
`review:ae` claim and not for one without it, then published a real
`authorityDecision` and confirmed it disappears from both the database
and the query. `EventStore.UnitTests` (86/86) and the
`ProjectionsSqliteTests`/`GraphQlHttpSqliteTests` regression suites pass
unmodified.

## Added: client-web "My Tasks" list (`/tasks`)

New `useMyTasks.ts` composable (`@eventstore/mvvm-client`) — a plain
polled GraphQL query, not a subscription, since there is no `myTasks`
Subscription field to consume (the same "just a query" design as the
server-side change above). New `components/tasks/MyTasksView.vue`
(domain-agnostic `n-data-table`) + `views/TasksView.vue` (the thin
router-level wrapper that picks which reviewer identity's claims the
query runs as — `vitals-pi-client`/`meridian-analyst-client`/
`follower-client`, mirroring `QueueView.vue`'s own
`VitalsPiQueue`/`MeridianAnalystQueue` split). Wired into the existing
router/nav shell (`ADR-099`) with no `requiresDomain` gate — cross-domain
by design, matching the real `EventStore.AppHost` topology where every
`client-web-*` instance already points at the same single `eventstore`
Host regardless of `AppId`. "Open" navigates to the existing `/queue`
decision screen; the decision UI itself is unchanged.

Verified with a real headless Chromium (Playwright, via a throwaway
`scratchpad/PlaywrightCheck` console app against the already-installed
`Microsoft.Playwright` package) driving a real `npm run dev:vitals` Vite
server against manually-started `EventStore.DevIdp`/`.Host.Sqlite`
processes — not just `vue-tsc`/`vitest`, per this repo's own standing
"run the real thing" rule for UI changes. That live run surfaced two
real, previously-undiscovered defects, fixed in the same pass:

- `docs/bugs/framework/service/devidp-token-endpoint-missing-standalone-cors-origin.md`
  — DevIdp's `/connect/token` had no `Cors:AllowedOrigins` entry for
  standalone (no-`AppHost`) client-web dev, breaking every client-web
  feature that fetches a token in that mode, not just this one.
- `docs/bugs/framework/service/devidp-duplicate-typed-extra-claims-collapse.md`
  — `vitals-pi-client`'s own `review:ae` claim was silently dropped by
  DevIdp's token issuance (`SetClaim` overwriting a same-typed claim
  instead of `AddClaim` accumulating it), so a real issued token only
  ever carried `review:ionm`. Also fixed `meridian-analyst-client`'s own
  claim seed list in the same pass — it was missing `identity:review`
  (Workflow A's decision claim), the same "union of every decision claim
  this domain names" rule `vitals-pi-client` already documents, found by
  the same code read that isolated the collapse bug above.

`client-web`'s own test suite (47 existing + 4 new `useMyTasks.spec.ts`)
and `vue-tsc`/`vite build` for both packages stay green throughout.
