## Item 7 committed; item 8, "Derived/Materialized Event Types (deferred)," built — this design's most complex single item, and two real EF Core bugs found only by running the tests

Direct instruction: "keep going," continuing straight into the item
`08-build-plan.md` itself flags as arguably the most complex of the 48
(n-ary cross-stream join, a background worker process, durable TTL-
bounded join state, definition-graph cycle detection, a hop-count safety
net) — built in full rather than pausing to check in, per the same
"check off work as you go, then continue" rhythm already in force.

**`ADR-007` names three concrete shapes as complexity without actually
specifying them — this pass is the data-model authority for all three**,
per this repo's own standing rule that the item building a persisted
shape owns its naming, not a later sweep:
- `DerivationCursor` (`AppId`, `DerivationName`, `SourceEventType`,
  `LastProcessedSequenceNumber`) — a per-derivation-per-source tailing
  checkpoint, deliberately modeled on `EventTailReader`'s own `lastSeen`
  cursor but persisted, so a worker restart resumes rather than re-
  tailing from `BackfillMode`'s starting point every time.
- The join-key extraction itself: `$on`'s pairwise `Source/Field eq
  Source/Field` equalities are fed into a union-find over `(source,
  field)` endpoints, grouping every field transitively tied to the same
  logical key into one class — supports a genuine n-ary join (not just a
  hand-special-cased two-source pair), matching `ADR-007`'s explicit
  "arbitrary-length `$from`" requirement without extra code per source
  count.
- `ContinuousEnrichment`'s exact re-emission trigger, which `ADR-007`'s
  own prose ("any new arrival... re-emits, joined against the current
  latest state of the others") leaves genuinely ambiguous about whether
  the very first arrival on any one source alone should emit a partial
  join. Resolved as: the first emission still requires every declared
  source to have arrived at least once (the same completion condition
  `FireOnce` uses) — only once that baseline exists does any later
  single-source arrival re-emit, looked up directly against `StoredEvent`
  rather than a rebuilt in-memory cache (so a worker restart needs no
  warm-up step). Documented as a stated simplification, not silently
  picked.

All three are written up in `docs/data/schema-registry.md`'s new
"Derived/materialized event types (deferred, `ADR-007`)" section
alongside `DerivationDefinition`/`JoinCondition`/`SelectField` (the
shapes `ADR-007` *did* specify), and `StoredEvent.DerivationHopCount` in
`docs/data/event-log.md` — landed in the same pass as the EF Core
migration, per the standing rule.

**Registration** (`DerivationRegistrationService`, new `EventStore.
Derivation` project): `$from`/`$on`/`$select` carried as request-body
fields on `POST /create/{event-type}`, not literal query-string
operators — the same adaptation `EventStore.Follow.Api.FollowRequest`
(`ADR-012`) already made for `$filter`, for the same reason (avoids
PII/PHI in a query string), applied here for consistency rather than
parsing `ADR-007`'s literal prose syntax. `OnClauseParser`/
`SelectClauseParser` are small hand-rolled, safe-identifier-chain-
restricted grammars (same restriction principle as `JsonPathValidation`
— an unrestricted grammar reaching the worker's own queries would be an
injection surface). The derived type's `JsonSchema` is auto-composed
from `$select` against each source's currently-active schema (a
`DeepClone` of the matched source field's own schema node, falling back
to `{"type":"string"}` only if the referenced field can't be resolved).
Derivation-definition cycles are rejected `400` via a plain DFS with a
visited-set over the small derivation-definition graph — confirmed
distinct from `ADR-005`'s runtime `CycleGuard`, which guards a different,
inert graph (already-published events' parent DAG) for a different
reason. Registration is **two sequential saves, not one transaction**:
`SchemaRegistryService.RegisterAsync` already owns and commits its own
internal transaction, so wrapping a second `BeginTransactionAsync` around
calling it would nest transactions on the same connection, which most
ADO.NET providers reject — a crash between the two leaves a registered
`EventTypeDefinition` with no matching `DerivationDefinition`, harmless
(nothing publishes to it) rather than a correctness gap, and explicitly
documented as this pass's chosen seam rather than a refactor of
`SchemaRegistryService` to accept an external transaction.

**The worker** (`DerivationWorker : BackgroundService`) is architecturally
"an internal follower" per `ADR-007`: it reads `StoredEvent` directly
with **no claims filtering of its own** — a server-side process producing
new data, not exposing existing data to an external caller, so `Read`-
direction `RequiredClaims` never applies to it; `Publish`-direction
claims are always empty for a derived type (`DerivationRegistrationService`
always registers one with `RequiredClaims: null`), so an empty system
`ClaimsPrincipal` always satisfies `PublishService`'s own gate. Every
tick's actual work is factored into a public `RunOnceAsync(db,
schemaRegistry, publishService, ct)`, separate from `ExecuteAsync`'s own
scope-creation loop, specifically so tests can drive one tick directly
against a provider-backed context — the same "exercise the underlying
service directly, not the ASP.NET host" pattern every other item's tests
already use. `FireOnce` mode persists `PendingJoinState` (durable,
TTL-bounded, per `ADR-007`); an expired or hop-capped row is **kept with
a recorded `ExpiredReason`, never deleted** — a minimal dead-letter
record, exactly matching `ADR-007`'s own "worth a dead-letter-style
record... though the exact shape isn't designed further here" note.
`ContinuousEnrichment` mode never touches `PendingJoinState` at all.
`BackfillThroughDerivedSources` is implemented at the per-source cursor
level: when the overall `BackfillMode` is `FromHistory`, a source that is
itself a registered `DerivationDefinition` gets its own cursor started at
0 (full replay) only if `BackfillThroughDerivedSources` is `true`;
otherwise that one source starts from the current max `SequenceNumber`
like a `FromNow` source would, while other, non-derived sources still
backfill fully — `FromNow` overall already starts every source from now
regardless of this flag.

**Two real bugs, both found only by actually running the tests, not by
reading the code back — this item's own instance of the discipline every
prior item has already paid off**:
1. `PendingJoinState.ExpiresAt <= now` failed to translate at all on
   SQLite: "The LINQ expression... could not be translated" — SQLite's
   EF Core provider does not support relational operators other than
   equality on `DateTimeOffset` columns. Fixed by fetching `ExpiredReason
   == null` candidates (a translatable null check) and filtering
   `ExpiresAt <= now` client-side afterward — a small, bounded set at this
   build stage, not a real cost.
2. A `PendingJoinState` row `Add()`ed while processing one event in a
   multi-event batch was invisible to the *next* event's own
   `SingleOrDefaultAsync` lookup in the same tick — `SaveChangesAsync` was
   originally deferred to once per whole batch, and `DbContext.Add()`
   alone never makes a new row visible to a subsequent LINQ query against
   the same context. Concretely: publishing both halves of a `FireOnce`
   join in the same tick produced **two separate** `PendingJoinState` rows
   for the same key (one per half) instead of one row completing the
   join — caught by a diagnostic dump showing exactly that, not by
   guessing. Fixed by saving after each event in the batch, not once
   at the end.

A **third, smaller fix** surfaced by the second bug's own reproduction:
the `(AppId, DerivationName, JoinKeyValue)` index was originally unique,
but a straggling source arriving *after* its join's row already expired
starts a **fresh** row with the identical key (deliberately, per the TTL-
expiry scenario's own design) — a real `UNIQUE constraint failed` on
SQLite once that path was actually exercised. Dropped to a plain
(non-unique) index; "at most one *active* (`ExpiredReason IS NULL`) row
per key" is an application-level invariant (every lookup already filters
on it), not a database constraint — documented as such in `EventStoreContext`.

**Test design note, not a product bug**: `DerivationScenarioAssertions`'s
10 scenarios share one `db` per provider test class, same as every other
item — but this item's own background worker processes *every* active
derivation on *every* tick, regardless of which scenario registered it,
matching source events purely by bare `EventType` name (the same pre-
existing `AppId`-ambiguity gap `docs/10-open-questions.md` row 1 already
documents). An earlier scenario's still-active derivation would
otherwise pick up a later scenario's identically-named source events too
and emit its own duplicate derived event, breaking single-result
assertions — worked around by giving every scenario its own uniquely-
suffixed source/derived type names (`OrderPlaced5`/`PaymentReceived5`/
`OrderPaid5`, ..., `OrderPlaced10`/...) rather than reusing one shared
set, which side-steps the collision entirely instead of scoping every
assertion around it.
