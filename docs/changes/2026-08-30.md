# 2026-08-30

## Fixed: cross-service HttpClients faulting under Polly's default resilience timeouts; Polly removed from this solution

Direct report while running the real `AppHost`: "I am getting this
error `Resilience event occurred. EventName: 'OnTimeout', Source:
'-standard//Standard-AttemptTimeout'...` as well as many others. Do this
correctly.. it should not fault for no reason. On top of that polly is
changing their licensing so unless absolutely necessary should be
replaced or removed."

**Diagnosis, corrected once before shipping — recorded honestly rather
than only presenting the final answer.** `EventStore.ServiceDefaults`'s
`AddServiceDefaults()` calls `AddStandardResilienceHandler()`
(`Microsoft.Extensions.Http.Resilience`/Polly v8) inside
`ConfigureHttpClientDefaults`, applied to every `HttpClient` in every
service that calls it — confirmed to be Aspire's own unmodified
project-template default, never a decision this project actually made.
An initial theory placed the fault in `FollowClient.TailAsync`'s
long-lived SSE body read (the Follow API tail connection genuinely
stays open indefinitely) — reasonable-sounding, but wrong: `TailAsync`
uses `HttpCompletionOption.ResponseHeadersRead`, so `SendAsync` (the only
call Polly's `DelegatingHandler` pipeline actually wraps) returns as
soon as headers arrive, well before the long idle-streaming phase even
begins. A test built against that theory — driving a real Follow tail
idle for 12 seconds mid-stream — **passed even with the old, buggy
resilience handler still in place**, a genuinely useful negative result
rather than a bug in the test: it disproved the theory instead of
confirming it, exactly the kind of check this project's own "verify
before citing" habit exists to force. Corrected theory, verified
directly: a minimal `HttpClient` whose primary handler simply delays 12
seconds before responding at all (simulating a backend that's slow to
even start responding — real, under this project's own 8-concurrent-
tail-loop `RbacProjectionWorker` startup contention against a
cold-starting `DevIdp`/`eventstore` pair) reproduced the **exact**
reported log line, including both `Standard-Retry` and
`Standard-TotalRequestTimeout` events.

**Fix**: removed `AddStandardResilienceHandler()` and the
`Microsoft.Extensions.Http.Resilience` package entirely from
`EventStore.ServiceDefaults`, rather than retuning its timeout values —
every real cross-service retry need this project actually has already
owns its own purpose-built, correctly-tuned mechanism (`ADR-033`'s
outbox/inbox, `ADR-060`'s webhook dispatcher, `FollowClient`/
`EventTailReader`'s own reconnect loops, EF Core's
`EnableRetryOnFailure`); a generic HTTP-level wrapper was never adding
non-redundant value, only an arbitrary 10s ceiling wrong for this
project's own real topology.

**Polly removed wherever it was a deliberate dependency, per direct
request about its new Open Source Maintenance Fee** (a per-organization
usage fee tied to revenue, not to which Polly package/version is used,
effective 2026-11-16 —
[thepollyproject.org](https://thepollyproject.org/2026/07/14/polly-osmf-announcement.html)):
the only other deliberate Polly usage in this solution,
`ADR-063`'s `Polly.Contrib.Simmy`-based in-process fault injection
(`EventStore.UnitTests`), is replaced with a minimal hand-rolled
`FaultInjector` (`tests/EventStore.UnitTests/FaultInjector.cs`) — both
real call sites always used `InjectionRate(1.0)` (unconditional), never
the partial, configurable rate that was the original "worth buying"
reasoning, so the replacement is a same-size, dependency-free
equivalent, not a regression in capability. **Stated honestly, not
overclaimed**: Polly is not fully eliminated from the dependency graph —
`Aspire.Hosting.*` (`ADR-026`) and `OpenIddict.*.SystemNetHttp`
(`ADR-006`) both depend on it internally for their own unrelated
purposes; dropping either would be disproportionate to this
consideration alone.

**Regression tests, verified red/green via a temporary `git stash` of
the fix, not assumed**:
- `tests/EventStore.UnitTests/ServiceDefaultsHttpResilienceTests.cs` —
  drives a real `AddServiceDefaults()`-built `HttpClient` against a
  primary handler that delays 12 real seconds before responding
  successfully. Red against the old resilience handler (reproduced the
  exact reported log line, request ultimately thrown as canceled); green
  against the fix (the full ~12s delay elapses, 200 returned).
- `PublishCrashRecoveryFaultInjectionTests.cs`'s two `ADR-063` tests pass
  unchanged against the new `FaultInjector`.
- Full `EventStore.UnitTests` (48/48) and the full SQLite
  `EventStore.IntegrationTests` (159/159, including
  `RbacProjectionWorkerHttpSqliteTests`) green; full solution build
  clean.

**Docs updated in the same pass**: filed
`docs/bugs/framework/service/follow-client-faults-under-default-http-
resilience-timeout.md` (the first entry under a new `service` tier,
including the wrong-theory-then-corrected narrative in full, not just
the final answer); `ADR-063` gained an additive implementation note
(the decision itself — staged escalation toward `Testcontainers`+
`Toxiproxy` — is unaffected, only the fault-injection *mechanism*
changed); `docs/libraries/dotnet/polly-simmy.md`,
`docs/libraries/README.md`, and `docs/references.md` all updated to
record the removal as explicitly as the original adoption, per this
project's own "a rejection is recorded as explicitly as an adoption"
convention. Found, but out of scope to fix this pass:
`docs/references.md`'s "Chaos Engineering" row has pointed at
`docs/patterns/fault-injection-chaos-engineering.md` since `ADR-063`,
but that file was never actually written — a pre-existing dangling
reference, now tracked in `TODO.md` rather than silently left.

No ADR reversal for the `AddStandardResilienceHandler()` half:
it was never itself the subject of any ADR — an unexamined template
default, not a decision — so there is nothing to formally supersede.

## Fixed: RbacProjectionWorker logging a routine, expected 404 as an Error-level lost connection, forever; bound its reconnect loop into Aspire/OTel

Found while the previous fix was being verified: the user pasted two
real OTLP log records from a genuinely running `EventStore.DevIdp`
process showing `Error`-severity `"RBAC fold for trial1/RoleRevoked lost
its connection; reconnecting"` (and the same for
`AppTrustRootRegistered`), both carrying a plain `HttpRequestException:
404 (Not Found)` — nothing to do with Polly at all, a second, genuinely
independent defect surfaced only by reading the real running app's own
logs.

**Root cause**: `RbacProjectionWorker` runs one tail loop per (AppId ×
reserved event type) unconditionally at startup — 8 concurrent loops (2
AppIds × 4 types). A reserved event type (`RoleGranted`/`RoleRevoked`/
`PermissionGranted`/`AppTrustRootRegistered`) only gets a registered
schema for a given AppId once something of that kind actually happens
there (`ADR-067`) — an AppId that's only ever had roles *granted*,
never *revoked*, genuinely has no `RoleRevoked` type registered yet, and
`FollowClient.TailAsync` surfaces that as an ordinary 404. `Tail
ForeverAsync`'s single `catch (Exception ex)` treated that exactly like
a lost connection: `Error`-level log, retried every 2 seconds, forever,
for as long as the combination simply never occurs — asked directly:
"what is the thought behind trying to get an event that has nothing
registered?" The answer: the worker can't know in advance when the
*first* such event will ever happen, so it optimistically retries a
fixed cadence on all 8 possible combinations rather than needing a
separate "a type just became available" signal — a deliberate
simplicity trade-off for a low-volume administrative mechanism
(`ADR-067`'s own scoping), not itself a bug. The actual defect was only
that an expected "nothing here yet" state and a genuine dropped
connection were indistinguishable in the logs.

**Fix**: a specific `catch (HttpRequestException ex) when
(ex.StatusCode == HttpStatusCode.NotFound)` branch ahead of the generic
one, logged at **Warning** (direct request — not `Debug`, since a
combination that never resolves is still worth a human noticing
eventually in a real deployment's default log level) with an honest
"has no registered schema yet; will retry" message.

**Also bound into Aspire/OTel directly, direct request** ("bind to
aspire/otel... so bugs can be logged correctly... consider this an
exception... instead of just a[n unremarkable log line]"): added
`DuplexInstrumentation.WorkerTailReconnects` (`ADR-088`'s shared Meter,
a new `Counter<long>` tagged `worker`/`app.id`/`event.type`/`reason`,
graphable/alertable with no log-grepping) and, for a genuine reconnect,
`Activity.AddException(ex)` on a `DuplexInstrumentation.ActivitySource`
-scoped Activity wrapping each tail attempt — a real .NET 9+ BCL method
(verified before using it; no `OpenTelemetry` package dependency
needed), producing the standard OTel `"exception"` event the Aspire
dashboard's own Traces view surfaces automatically. `EventStore.DevIdp`
gained an explicit `EventStore.Domain` project reference for this
(already transitively available via `EventStore.ServiceDefaults`, added
directly for clarity) — still never referencing
`EventStoreContext`/`Persistence`/`SchemaRegistry`, preserving this
project's own documented "DevIdp never depends on the core engine"
boundary.

**A related, separate finding corrected the same pass**: while checking
whether newly-registered event types can be subscribed to while the app
is running (a question this investigation raised directly), found
`AppHost.cs`'s own comment claiming `FollowSubscriptionTypeModule`
"only builds the GraphQL Subscription schema ONCE, at host warmup...
no hot-reload" was stale — `FollowSubscriptionTypeModule`'s own header
comment documents a real, later-fixed, and verified hot-reload path
(`docs/changes/2026-08-13.md`): a type registered after Host warmup
becomes queryable and deliverable via a live Subscription within about
150ms, no restart. Corrected `AppHost.cs`'s comment in place rather than
leaving the contradiction for a future reader to trip over — the
`WaitForCompletion(vitalsSeed)`/`(meridianSeed)` ordering on `eventstore`
itself is unchanged (still needed so the seeders' own schema/data exists
before anything queries for it), only the stated *reason* was wrong.

**Verification**: new test
`RbacProjectionWorkerHttpSqliteTests.CatchUpOnceAsyncThrowsAnHttpRequestExceptionWithNotFoundStatusForAGenuinelyUnregisteredEventType`
confirms the real exception shape (`StatusCode == NotFound`) the new
catch filter depends on, rather than assuming it from the fix's own
code. Full `EventStore.UnitTests` (48/48) and the full SQLite
`EventStore.IntegrationTests` (160/160) green; full solution build
clean. See `docs/bugs/framework/service/rbac-fold-404-logged-as-error-
forever.md` for the full write-up, including an honest note that
`TailForeverAsync`'s own infinite retry loop still isn't exercised
end-to-end by any test (a documented, pre-existing `WebApplicationFactory`
hazard for driving the real `BackgroundService.ExecuteAsync`), only the
exception-shape assumption the fix depends on.

**Re-verified against a real, running app with real UI automation, per
direct request** — ran `VitalsWorkflowBAdverseEventPlaybookTests` and
`MeridianWorkflowBRelyingPartyAccessPlaybookTests` (Playwright + a real
`AppHost`: Postgres, migrator, DevIdp, eventstore, simulators, Vite dev
servers) end to end. Zero occurrences of either target error string
across both full captured resource logs; the second run's own devidp
log shows real `QUERY /follow/RoleGranted` traffic completing cleanly,
positively exercising the exact mechanism fixed, not just an absence of
errors. Both runs regenerated their own playbook docs/screenshots as a
side effect (their own header's documented, expected behavior) — found
and fixed a related, real gap doing this: regenerating a playbook doc
overwrites the whole file from `PlaybookRecorder`'s own output, silently
dropping `extract-diagrams.mjs`'s inserted `![diagram](...)` line, since
the two pipelines aren't coordinated. Worked around by re-running
`node scripts/extract-diagrams.mjs` (its own idempotency guard restores
it safely); tracked as a real `TODO.md` item for a proper fix.

## Added a coding-standard pattern doc: Known Outcomes Are Not Exceptions

Direct request, generalizing the RBAC 404 bug above into a named,
citable standard: `docs/patterns/known-outcomes-are-not-exceptions.md` —
a well-understood, expected outcome should be a named result a caller
branches on, never a thrown-and-caught exception, since the two lose
different information when conflated (severity, and visible control
flow). Cited real prior art, verified before writing: Microsoft's own
.NET Framework Design Guidelines ("do not use exceptions for the normal
flow of control") and Scott Wlaschin's Railway Oriented Programming (the
standard "return the outcome as data" alternative shape). Documents this
project's own strong existing local convention (`PublishResult`/
`RegisterEventTypeResult`/`RegisterDerivationResult`/`FollowResult`, all
already discriminated-result-shaped, never thrown) alongside the one
found counterexample (`FollowClient.TailAsync` throwing for the
already-named `FollowResult.UnregisteredEventType`) as the concrete
"why this matters" illustration. `docs/patterns/README.md`'s catalog and
`docs/references.md` updated in the same pass, matching every other
pattern doc's own convention; a new `TODO.md` item tracks the pattern's
own named, not-yet-done follow-on (`FollowClient` itself returning a
discriminated result instead of throwing, benefiting all three of its
callers, not just `RbacProjectionWorker`'s own `catch` filter).
