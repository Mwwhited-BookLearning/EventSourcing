## `/events/verify` across SequenceNumber gaps

The AppHost run showed gaps in `Events.SequenceNumber` (rolled-back/retried appends consume identity values). Added `HashChainStillVerifiesAcrossAGapInSequenceNumbers` to the provider e2e suite: publish 3, burn 1000 identity values directly in the database (Postgres `nextval`, SQL Server `DBCC CHECKIDENT RESEED`), publish 3 more, verify. Passes on both providers -- as the code implies: `ChainVerificationService` walks rows in order and hashes each row's own SequenceNumber, never assuming consecutive numbers. Not a defect.

## Concurrent load run of the real AppHost (all three providers)

New `src/EventStore.LoadTest` driver (usage in its `Program.cs`): concurrent registrations, a publish burst with mid-burst registrations, `/events/verify`, and GraphQL polling of routed entities. Three real defects found and fixed:

- `docs/bugs/framework/service/wake-signal-fault-stops-host.md` (Postgres `too many clients` stopped the host; wake signals now never throw; AppHost Postgres `max_connections=300`).
- `docs/bugs/framework/service/router-unbounded-tick-batch.md` (Router ticks are now bounded and committed per page).
- `docs/bugs/framework/service/chain-verify-unbounded-in-clause.md` (verify pages instead of one giant `IN`).

Result with fixes (3000 publishes, concurrency 64): Postgres 119/s, SQLite 73/s (p99 ~10s, single-writer), SQL Server 69/s; all 202, verify clean on all three; entities routed 200/200 on Postgres and SQLite. SQL Server routing was the outlier (~9 events/s); root-caused afterwards, see below. Unit and integration suites pass (273 integration); two Playwright playbook E2E tests failed in the full run and were not triaged.

### SQL Server Router throughput

Root cause was missing indexes on `Events` plus a reconcile query that ran on every tick: `docs/bugs/framework/database/events-table-missing-worker-indexes.md`. Added migration `AddEventsWorkerIndexes` (all three providers), reworked `UpcastMaterializer.ReconcileBacklogAsync` into a paged database anti-join, and throttled it to every 30 s. `EventStore.LoadTest` gained a `routeTimeoutSeconds` argument (default 60). Re-run (3000 publishes, concurrency 64): Postgres and SQLite 200/200 routed within 2 s of the burst; SQL Server 200/200 but ~96 s after the burst (publishes 60/s, Router ~100/s, still slower than Postgres; Service Broker log flushes). Integration suite 273 passed.

Environment note: restarting the AppHost repeatedly left stale `Created` Docker containers pointing at deleted Aspire networks and the DCP proxy ports dead; `aspire stop`, kill `dcp`/`EventStore.AppHost`, `docker rm -f` the stale `sqlserver-server*`/`postgres-server*` containers and `docker network rm` the `aspire-session-*` networks before `aspire start` fixed it.

### Playwright playbook failures triaged

`RecordDecidePendingMatchPlaybook` / `RecordDecidePendingAlertPlaybook` failed with "element(s) not found 'accepted'": after Accept, the live subscription removes the decided row (the documented behaviour), so `tbody tr` `.First` re-resolved to another row with no status span, or the status vanished before the first poll. A test race, not a product defect. Both tests now pin the row by its Meaning input test id and assert it leaves the queue; both pass.
