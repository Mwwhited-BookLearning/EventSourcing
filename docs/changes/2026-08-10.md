## Two architecture-vs-ADR conflicts, found before writing any code

`ADR-057` assumed the pre-"Entity-Centric Core Rebuild" synchronous
validate-then-persist pipeline. The actual architecture is always-202
Inbox + async Router (`ADR-023`) — encryption still has to happen
synchronously at publish time (this ADR's own explicit ordering
requirement, before `Payload` is persisted and hashed), so
[`PublishService.cs`](../../src/EventStore.Inbox/PublishService.cs)
independently resolves `EntityId` for encryption-scoping purposes only,
via the same `EntityIdResolver` pure function `RouterWorker` uses —
`StoredEvent.EntityId` itself is unaffected, still starting empty and
still filled in only by the Router.

Random-nonce AES-GCM would have broken `ADR-011`'s publish-idempotency
hash-matching — retrying an identical logical publish containing a
classified field would encrypt differently each time (a fresh random
nonce), making `PayloadHash` differ and falsely reporting `409 Conflict`
instead of an idempotent replay. Resolved via deterministic/convergent
encryption before writing any integration test: an HMAC-derived nonce for
`LocalErasureKeyStore` (`DeriveNonce(key, plaintext)`), and Vault's own
`ConvergentEncryption`+`Derived`+a fixed `Base64EncodedContext` for
`HashiCorpVaultErasureKeyStore` — verified via a standalone probe that
determinism actually holds, not assumed.

## Fold-time and registration-time validator changes

[`JsonSchemaInstanceValidator.cs`](../../src/EventStore.SchemaRegistry/JsonSchemaInstanceValidator.cs)
(shared by `RouterWorker`'s fold-time re-validation and
`UpcastMaterializer`'s upcast-result check) gained one exemption: a field
carrying `x-masking.regulatoryClassification` is always stored (and
re-derived) as ciphertext — always a string — regardless of its
originally-declared type, so type-checking it against that declared type
is expected to "fail" and must be skipped. Fixed in the one shared
validator, not taught to each caller individually.

[`MaskingSchemaValidator.cs`](../../src/EventStore.SchemaRegistry/MaskingSchemaValidator.cs)
gained format validation for the new optional `x-masking.erasureScope`
field, reusing `JsonPathValidation`'s existing safe-subset grammar
(`EntityIdField`'s own injection-surface protection).

## A doc bug found and fixed via reflection, not guessed

[`docs/libraries/dotnet/hashicorp-vault.md`](../libraries/dotnet/hashicorp-vault.md)'s
own usage snippet named a non-existent
`vaultClient.V1.System.DeleteTransitKeyAsync` method. The real API,
confirmed against the actual installed VaultSharp assembly via a
throwaway reflection probe, is
`ITransitSecretsEngine.DeleteEncryptionKeyAsync` (requires
`UpdateEncryptionKeyConfigAsync(..., DeletionAllowed: true)` first, since
Vault refuses key deletion otherwise). Fixed in the same pass.

## The reserved event, and how it's actually triggered

`EntityErasureRequested` is registered lazily, the first time a given
`AppId` ever creates its first DEK
(`ErasureKeyService.GetOrCreateAsync`) — the same "not seeded up front"
treatment `ADR-031`'s `ChannelLagDetectedEventType` already established
— rather than at Host startup (no `AppId` is known then). Requesting
erasure is an ordinary publish of this reserved type through the SAME
Publish API any other event type uses — no bespoke DELETE-shaped
endpoint — gated by an ordinary `requiredClaim` (`erasure:request`,
`ADR-050`'s existing mechanism). `RouterWorker`'s existing
"special-purpose reactor" shape (`AuthorityDecisionResolver`'s own
precedent) folds it into its own entity like any other type, then
performs the additional side effect: destroying the target entity's DEK.

**A real bug caught while writing the erasure test suite, not by reading
the code back**: `RequiredClaimRequest.Direction` only parses to
`"Publish"` or `"Read"` (`ClaimDirection`'s two actual enum members) — an
initial `"Write"` value silently failed `Enum.TryParse` inside
`SchemaRegistryService.RegisterAsync`, which records a validation error
rather than throwing, so the reserved type's own registration would have
quietly stored no required claim at all. Caught because the erasure-
request test scenario explicitly asserted claim enforcement, not because
registration itself failed loudly — fixed by using `"Publish"`.

## Two different test-migration strategies for two different signature changes

`PublishService` gained a new `PayloadEncryptor` constructor parameter.
Made **optional** (`= null`), matching `IOptions<OriginIdOptions>?`'s own
established precedent immediately above it in the same file, for the
identical reason: ~37 pre-existing test files construct `PublishService`
directly and never register a classified field, so a null encryptor
correctly means "nothing to encrypt," not a missing dependency — avoiding
a 37-file mechanical sweep for a concern almost none of those files
exercise.

`IPayloadMasker.MaskAsync` (renamed from `Mask`, now `async`, now taking
`entityId`) has no such escape — every real caller needs real
decrypt/erasure-check behavior. Confirmed via `grep` that
[`EventTailReader.cs`](../../src/EventStore.Follow.Api/EventTailReader.cs)'s
`MaskPayload` is the ONLY real production call site (`PartialRevealStreamRedactionStrategy`'s
similarly-named `.Mask(...)` call is a *different* interface,
`IMaskingStrategy`, unaffected) — updated directly. `MaskingTestSupport.
CreatePayloadMasker` was changed to take the caller's own already-
constructed `db`/`registry` (needed to resolve the new `ErasureKeyService`
dependency `PayloadMasker` now has), with a handful of call-site fixes
across `Masking*Tests`/`Follow*Tests`/`Replication*Tests` (the last three
needed their `IOptions<OriginIdOptions>` argument moved from positional
to named, since a new optional parameter was inserted before it in the
constructor) — not a large sweep.
