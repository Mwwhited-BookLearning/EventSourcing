## Two architecture-vs-ADR conflicts, found before writing any code

`ADR-057` assumed the pre-"Entity-Centric Core Rebuild" synchronous
validate-then-persist pipeline. The actual architecture is always-202
Inbox + async Router (`ADR-023`) — encryption still has to happen
synchronously at publish time (this ADR's own explicit ordering
requirement, before `Payload` is persisted and hashed), so
[`PublishService.cs`](../../src/EventStore.Inbox/PublishService.cs)
independently resolves `EntityId` for encryption-scoping purposes only,
via the same `EntityIdResolver` pure function `RouterWorker` uses —
`StoredEvent.EntityId` itself is unaffected, still starting empty and
still filled in only by the Router.

Random-nonce AES-GCM would have broken `ADR-011`'s publish-idempotency
hash-matching — retrying an identical logical publish containing a
classified field would encrypt differently each time (a fresh random
nonce), making `PayloadHash` differ and falsely reporting `409 Conflict`
instead of an idempotent replay. Resolved via deterministic/convergent
encryption before writing any integration test: an HMAC-derived nonce for
`LocalErasureKeyStore` (`DeriveNonce(key, plaintext)`), and Vault's own
`ConvergentEncryption`+`Derived`+a fixed `Base64EncodedContext` for
`HashiCorpVaultErasureKeyStore` — verified via a standalone probe that
determinism actually holds, not assumed.

## The reserved event, and how it's actually triggered

`EntityErasureRequested` is registered lazily, the first time a given
`AppId` ever creates its first DEK
(`ErasureKeyService.GetOrCreateAsync`) — the same "not seeded up front"
treatment `ADR-031`'s `ChannelLagDetectedEventType` already established
— rather than at Host startup (no `AppId` is known then). Requesting
erasure is an ordinary publish of this reserved type through the SAME
Publish API any other event type uses — no bespoke DELETE-shaped
endpoint — gated by an ordinary `requiredClaim` (`erasure:request`,
`ADR-050`'s existing mechanism). `RouterWorker`'s existing
"special-purpose reactor" shape (`AuthorityDecisionResolver`'s own
precedent) folds it into its own entity like any other type, then
performs the additional side effect: destroying the target entity's DEK.

**A real bug caught while writing the erasure test suite, not by reading
the code back**: `RequiredClaimRequest.Direction` only parses to
`"Publish"` or `"Read"` (`ClaimDirection`'s two actual enum members) — an
initial `"Write"` value silently failed `Enum.TryParse` inside
`SchemaRegistryService.RegisterAsync`, which records a validation error
rather than throwing, so the reserved type's own registration would have
quietly stored no required claim at all. Caught because the erasure-
request test scenario explicitly asserted claim enforcement, not because
registration itself failed loudly — fixed by using `"Publish"`.

## A real, pre-existing bug found and fixed while building this item's own mechanism

`payloadTypeName`/`subscriptionFieldName` never lowercased the event type
before sanitizing it, but `SchemaRegistryService.RegisterAsync` always
stores `EventTypeDefinition.Name` lowercased
(`normalizedName = eventTypeName.ToLowerInvariant()`) before
`FollowSubscriptionTypeModule` ever builds a field name from it
server-side. Every existing client call site (including this item's own
new `EntityErasureRequested` subscription, which would have failed

silently subscribing to a GraphQL field name that never matched anything
the server actually exposes — a `data[fieldName]` lookup that's simply
always `undefined`, no error, no crash, just no data ever arriving. Fixed
by lowercasing the event type (never `AppId`, which the server never
lowercases) inside those two functions; the existing
`subscriptionBuilder.spec.ts` assertions that had encoded the wrong
(mixed-case) expected behavior were corrected in the same pass.

# Item 29, "Digital Sign-Off for Regulated Actions (Step-Up Authentication)," is Done

Four real bugs found while verifying this item's own exit criteria, same
day — none assumed satisfied without actually checking.

## Bug 1: `ActorId on Every Event` was never actually built, despite this diagram's own `#palegreen` claim

`PublishService` hardcoded the literal string `"unauthenticated"` for
every publish, regardless of the caller's real, already-verified
identity — contradicting `docs/data/event-log.md`'s own "ALWAYS
populated, blocking, not advisory" text and the build-plan diagram's own
fill color for this item's named dependency. Fixed by reusing
[`AccessLogReaderContext.Resolve`](../../src/EventStore.Domain/AccessLog/AccessLogReaderContext.cs)'s
existing claim resolution verbatim — the same JWT, the same claims, no
reason for a second implementation.

## Bug 2: the hash chain never actually covered `Signature`, despite `ADR-066`'s own claim

`ADR-066`'s Decision text says "non-repudiation reuses the existing hash
chain, no new primitive... exactly as tamper-evident as everything else
in the log." Checked, not assumed: `ChainHash`/`PayloadHash` only ever
cover `{EventType, Payload, parentEventIds}` — `Signature`, like every
other envelope field, sat completely outside what either hash actually
protects. A direct-database edit to a stored `Signature` would have gone
completely undetected.

Fixed by extending
[`EventChainHash.Compute`](../../src/EventStore.Domain/EventLog/EventChainHash.cs)
specifically, not `PayloadHash`: `PayloadHash` is also `ADR-011`'s own
idempotency-comparison basis, and `Signature.SignedAt` is genuinely
wall-clock-real at each publish attempt, not deterministic the way
`ADR-057`'s classified-field ciphertext had to be made — including
`Signature` there would make every legitimate retry of a signed publish
look like different content. `ChainHash` is never compared for
idempotency (only `PayloadHash` is), so extending it costs nothing there
while still making a tamper to `SignerId`/`SignedAt`/`Meaning`/`Acr`
diverge the chain at exactly that `SequenceNumber`. `Signature` is
omitted entirely (not hashed as a literal `null`) for an unsigned event,
so every event type that never uses `RequiredSignature` computes
byte-identical `ChainHash` values to before this parameter existed.
[`ChainVerificationService.cs`](../../src/EventStore.Inbox/ChainVerificationService.cs)
and
[`EventAppender.cs`](../../src/EventStore.Persistence/EventAppender.cs)
both updated to pass the row's own `Signature` through.

## Bug 3: `RequiredSignature`/`Signature` were the only two JSON-converted envelope fields missing an EF `ValueComparer`

Found while writing the `ChainHash` tamper-detection test itself: a
direct in-place mutation of an already-tracked `Signature.Meaning`
(`target.Signature!.Meaning = "TAMPERED"`) silently never reached the
database at all. Every list-typed JSON-converted property in
[`EventStoreContext.cs`](../../src/EventStore.Persistence/EventStoreContext.cs)
already has a `ListComparer<T>` attached; `RequiredSignature`/`Signature`
(both single class instances, not `IEnumerable`, so `ListComparer`'s own
constraint doesn't fit) were the only two missing the equivalent.  EF's
default reference-equality change detection for a converted class-typed
property never notices an in-place mutation of the SAME instance — only
assigning a NEW instance would have been detected. Fixed by adding
[`JsonValueConverter.NullableComparer<T>`](../../src/EventStore.Persistence/JsonValueConverter.cs),
the single-object counterpart to the existing `ListComparer<T>`, and
wiring it onto both properties.

## Bug 4: two real OpenIddict/JWT claim quirks, found only by running the actual RFC 9470 round trip over real HTTP

`EventStore.DevIdp` gained a dev-only step-up simulation: an opt-in `acr`
form parameter on the ordinary `client_credentials` flow, the same
"opt-in, every existing caller unaffected" shape `app_id`/`ADR-046`
already established — a real IdP only ever grants a given `acr` value
after actually performing that authentication method; this dev/POC IdP
has no interactive login for a machine caller to step up through at all,
so it just takes the caller's word for it, the same posture it already
takes for several other dev-only simplifications.

Running this against OpenIddict's real pipeline surfaced two distinct
failures, peeled back one at a time: (1) `ValidateSignInDemand` requires
`auth_time` to carry a genuinely numeric `ClaimValueType` — the plain
`SetClaim(string, string)` overload threw `"the auth_time claim...  is
malformed or isn't of the expected type"`; fixed via the dedicated
`SetClaim(string, long?)` overload (confirmed via a reflection probe
against the actual installed `OpenIddict.Abstractions` assembly, not
guessed). (2) Even after that fix, a step-up token that genuinely carried
`acr` was still rejected by `PublishService` — `JwtBearer`'s own default
`MapInboundClaims=true` remaps `acr` to
`http://schemas.microsoft.com/claims/authnclassreference` before any
resolver ever sees it (confirmed against
`JwtSecurityTokenHandler.DefaultInboundClaimTypeMap` via a second
reflection probe), the exact same remapping class
`AccessLogReaderContext.Resolve`'s own comment already documents for
`"sub"`/`ClaimTypes.NameIdentifier`. Fixed by checking both claim names,
the same way that resolver already does.

# Item 30, "Control-Plane Actions as Reserved Events," is Done

`ADR-067` treats control-plane mutations (schema registration, RBAC grants,
trust-root registration) as ordinary, reserved, hash-chained events in the
same Event Log — built in two stages.

## Stage 1: `SchemaRegistered`

`SchemaRegisteredEventType` (new, `EventStore.SchemaRegistry`) is a
reserved event type, registered lazily on the first registration for a
given `AppId` (the same precedent `ChannelLagDetectedEventType`/
`EntityErasureRequestedEventType` already established).
`SchemaRegistryService.RegisterAsync` appends this event immediately after
every successful registration — guarded against recursing into itself
during its own bootstrap registration — carrying `ActorId` resolved via
`AccessLogReaderContext.Resolve` (reused a third time, after AccessLog and
`PublishService`). Deliberately narrower than the ADR's own literal text:
`EventTypeDefinition`'s own write path is **not** rearchitected onto this
event — it stays a direct, synchronous write, because dozens of pre-existing
tests across the whole build assume synchronous read-your-own-write
registration, which an async fold would break. `SchemaRegistered` is a
genuine, hash-chained, lineage-traceable audit record layered alongside the
unchanged write, not a replacement for it.

Found and fixed one real regression in the same pass:
`SchemaRegistryService.ListAsync` didn't exclude this new reserved type,
so any `AppId`'s own type listing/pagination silently gained one extra row
the moment it registered its first real type — caught by
`ListingSupportsTopAndSkipPagination`'s own count assertion breaking.
Fixed by excluding the reserved name from `ListAsync`'s query; the same
latent gap for the three older reserved types is tracked in `TODO.md`
rather than silently widened beyond this item's own regression.

## Stage 2: RBAC grants and trust-root registration

A cross-process design, resolved by direct user consultation after research
surfaced that neither `ADR-067`, the build plan, nor `auth.md` committed to
*where* the RBAC write path should live or how DevIdp should observe the
folded state: **"fold into DevIdp via Follow."** A new Host-side project,
`EventStore.Rbac`, defines the 4 remaining reserved event types
(`RoleGrantedEventType`/`RoleRevokedEventType`/`PermissionGrantedEventType`/
`AppTrustRootRegisteredEventType`) and `RbacEndpoints.cs` — real, Bearer +
scope-gated Minimal API endpoints (`POST /rbac/roles/{roleName}/assignments`,
matching `DELETE`, `POST /rbac/permissions`, `PUT
/rbac/trust-roots/{issuerDid}`), gated by `registry:admin`/
`registry:trust-admin` + `AppIdScopeEvaluator.CanAdminister` for the
`admin`-scoped ones, mirroring `SchemaRegistryEndpoints.cs`'s own pattern.
Wired into all 3 `EventStore.Host.{Sqlite,Postgres,SqlServer}` projects.
`registry:trust-admin` needed a brand-new ASP.NET Core authorization policy
in `HostCoreExtensions.cs` — it existed only as a seeded OAuth scope before,
with no policy backing it at all (a real, if latent, gap: a
`registry:trust-admin`-scoped caller had nothing to actually authorize
against). `AppIdScopeEvaluator.CanAdminister` is deliberately **not**
applied to the trust-root endpoint — it only recognizes
`registry:admin`-shaped scopes, and `ADR-044` has never modeled an
AppId-scoped `registry:trust-admin:{appId}` variant; found by running a
real `registry:trust-admin`-scoped call and getting wrongly `403`'d.

`RoleGranted`/`RoleRevoked`/`PermissionGranted` use a synthetic composite
`EntityIdField` (`AssignmentKey`/`GrantKey`, computed by the endpoint as
`actorId:roleName`/`actorId:permission`) rather than the ADR's own literal
`{appId}:role:{roleId}`-shaped example — a role or permission can be
granted to many actors independently, and the generic patch-merge fold
semantics that shape implies would let one actor's grant silently overwrite
another's. `AppTrustRootRegistered` fits the literal example directly
(`$.IssuerDid`, one record per `(AppId, IssuerDid)`).

`EventStore.DevIdp` gained `RbacProjectionWorker`, a `BackgroundService`
that follows all 4 RBAC event types cross-process (via
`EventStore.Projections.Host.FollowClient`, the same client
`ProjectionHost<T>` uses, referenced directly rather than through the
higher-level generic engine, which is upsert-only with no delete concept —
a real mismatch for `RoleRevoked`) and folds them into DevIdp's OWN
existing `Role`/`RoleAssignment`/`UserPermission`/`AppTrustRoot` tables via
`RoleService`/`TrustRootService`'s own already-idempotent methods, reused
verbatim — only the caller changes, from an inbound HTTP request to a
Follow consumer. No persisted checkpoint: every (re)connect always replays
from `SequenceNumber 0`, accepted as a simple, low-risk choice for a
dev/POC, low-volume administrative stream, since the fold methods are
already no-ops on repeat. 4 of DevIdp's 6 old direct-write `/oauth/*`
endpoints are retired (`PUT /oauth/trust-roots`, `POST`/`DELETE
/oauth/role-assignments`, `POST /oauth/user-permissions`); `PUT
/oauth/roles` (what a role NAME bundles) and `PUT /oauth/federation-issuers`

# Item 32, "Leader Election via Database-Backed Lease," is Done

`ADR-078` resolves whether more than one `Router`/`UpcastMaterializer`/
outbox-pump instance can run per site (never stated either way before):
exactly one instance of each singleton worker *role* runs at a time,
enforced by a database-backed lease row per role — the one piece of
shared infrastructure every deployment already has, not a new quorum/
consensus dependency (etcd/ZooKeeper/Consul explicitly rejected).

`LeaderLease` (`EventStore.Domain.LeaderElection`, primary key
`WorkerRole` alone, deployment-wide, not `AppId`-scoped) plus its
migration across all 3 providers landed first — the one piece `ADR-078`'s
own Consequences flagged as not yet built. A new
`EventStore.LeaderElection` project holds the actual mechanism:

- `LeaderElectionService.TryAcquireOrRenewAsync(workerRole, holderId,
  leaseDuration, ct)` — a compare-and-swap over one role's own
  `LeaderLease` row via EF Core's `ExecuteUpdateAsync`. **A real bug found
  and fixed while building this**: the first version combined "renew if
  I'm already the holder" and "steal if it's expired" into ONE `Where`
  clause (`LeaseHolderId == holderId || LeaseExpiresAt <= now`) updated in
  one `ExecuteUpdateAsync` call — EF Core's SQLite provider failed to
  translate this AT ALL ("could not be translated," a genuine, narrower-
  than-documented limitation of that provider's `ExecuteUpdate` support,
  not a bug in the query itself). Splitting into two separate,
  equality-only statements (renew first; if that matched zero rows, read
  the current row, decide expiry in memory, then compare-and-swap on the
  EXACT `LeaseExpiresAt` value just observed) resolved it and is arguably
  clearer besides — no inequality comparison ever appears inside an
  `ExecuteUpdate` WHERE clause now.
- `LeaseHolderId.Current` — `{MachineName}:{ProcessId}`, ADR-078's own
  suggested identity shape, computed once per process.

Wired into the two worker roles that exist today:

- `RouterWorker` (`WorkerRole: "Router"`) and `PeerSyncWorker`
  (`WorkerRole: "PeerSyncOutboxPump"`) each attempt acquisition/renewal
  before doing any real work per tick, skip the tick entirely when they
  don't hold the lease, and log on every leader/non-leader transition (not
  every tick, to keep the log readable). **Renewal happens at roughly half
  the lease's own duration (2.5s of a 5s lease), not on every 200ms/500ms
  poll tick** — renewing every tick was the first version built, and it
  measurably slowed down the real fold work under this repo's own heavy
  parallel test load (32-way MSTest class parallelism, many Hosts sharing
  one machine) enough to make several OTHER tests' own fixed wait margins
  (e.g. "wait 500ms for RouterWorker's own poll") intermittently miss —
  found only by running the full suite, not by reasoning about it in
  advance. A failed acquisition attempt still retries every ordinary poll
  tick (200ms/500ms), not the slower renewal cadence, so recovery from
  "never held it yet" or "just lost it" stays fast.

**One deliberate narrowing, found only by actually building this**:
`UpcastMaterializer` does NOT get its own separate `LeaderLease` row,
despite `ADR-078`'s own Decision text naming it as one of exactly 4
independent worker roles. Reading `RouterWorker.cs` closely (it predates
this item by several build-plan items) showed `UpcastMaterializer.
ReconcileBacklogAsync`/`TryMaterializeAsync` are called INLINE, directly
from `RouterWorker`'s own tick — there is no separate, independently-
schedulable `UpcastMaterializer` process to protect with its own lease at
all; it can never run except as part of `RouterWorker`'s own execution,
under `RouterWorker`'s own lease. A second lease row would have protected
nothing. The webhook outbox pump (`ADR-078`'s 4th named role) stays
deferred to "Outbound Webhooks," exactly as this item's own Depends-on
paragraph already anticipated — that item will call
`EventStore.LeaderElection` the same way once its own worker exists.

Verified with `LeaderElectionScenarioAssertions.cs` across SQLite,
PostgreSQL, and SQL Server: first-ever acquire, a second holder blocked
while still valid, self-renewal, claiming an expired lease, two roles held
completely independently, and a direct, deterministic reproduction of the
"lost update" hazard this item prevents — two uncoordinated
`EventStoreContext` instances, each holding a stale read of the same
`EntityStoreRow`, both saving, one silently overwriting the other's own
contribution — standing in for a genuine multi-threaded race against
`RouterWorker` itself, which would be flaky to assert on directly.
`EventStore.IntegrationTests` gained 3 new `[TestMethod]`s (one per
provider, each running all 6 scenarios in sequence).

security or authorization decision.

lease across all three limiter types would carry `Retry-After` (the

version. `RateLimiterPolicies.OnRejected` already guarded with

only the build-plan's own exit-criteria text and this item's tests were
corrected to stop asserting a header this library never sends for those
two policies. A second, smaller correction from the same pass:
`TokenBucketRateLimiterOptions.TokensPerPeriod` must be `> 0` — a test
attempting `TokensPerPeriod: 0` to mean "never replenish" threw
`ArgumentException` at first use; fixed by using `TokensPerPeriod: 1`
with a 1-hour `ReplenishmentPeriod` instead, which achieves the same
"won't replenish within this test's own lifetime" effect legally.

**ADR-037 complementarity, decided via the lightweight option.** Rather

proving the Host's own depth limiter end-to-end, unchanged by this item),

`docs/08-build-plan.md`'s status table and `BuildPlan_All` diagram fill

New [`EventStore.Domain/Webhooks/`](../../src/EventStore.Domain/Webhooks/)
shapes (`WebhookSubscription.cs`/`WebhookOutbox.cs`/
`WebhookDeliveryCursor.cs`, migrated across all 3 providers as
`AddWebhooks`) and a new `EventStore.Webhooks` project:

- [`WebhookSubscriptionService.cs`](../../src/EventStore.Webhooks/WebhookSubscriptionService.cs) —

  caller's own current claims (`ADR-008`'s "type:value" primitive, JSON-
  serialized as a string array), never re-evaluated afterward.
- [`WebhookEnqueueResolver.cs`](../../src/EventStore.Webhooks/WebhookEnqueueResolver.cs) —

  for every event, the same shape `AuthorityDecisionResolver`/

- [`WebhookOutboxPump.cs`](../../src/EventStore.Webhooks/WebhookOutboxPump.cs) —
  the 4th of `ADR-078`'s 4 named worker roles, its own genuinely

  (Standard Webhooks' HMAC-SHA256 construction, used as specified), and
  retries with exponential backoff+jitter tracked by
  [`WebhookRetryTracker.cs`](../../src/EventStore.Webhooks/WebhookRetryTracker.cs)
  (deliberately in-memory/per-process).
- [`WebhookDeliveryFailedEventType.cs`](../../src/EventStore.Webhooks/WebhookDeliveryFailedEventType.cs) —
  the reserved dead-letter event, `FailureKey` a synthetic
  `"{SubscriptionId}:{SequenceNumber}"` field (`RoleGranted`'s own
  `AssignmentKey` precedent — a bare `SubscriptionId` would let a second
  exhausted delivery for the same subscription silently overwrite the
  first's `EntityStoreRow`).
- [`WebhookEndpoints.cs`](../../src/EventStore.Webhooks/WebhookEndpoints.cs) —
  `POST /webhooks/subscriptions`, gated by a new `webhooks:admin` scope
  (`webhooks.md`'s own illustrative choice — `03-api-contracts.md` never
  enumerated a webhook-management endpoint at all).

**Decision 1 — `WebhookOutbox` gained a `SourceSequenceNumber` column
this section's own schema text never named, found necessary before
writing any code, not patched in after a test failure.** `ADR-060`'s
Consequences require a retry after erasure to "correctly re-mask...
against the now-erased key," but `IPayloadMasker`'s reveal path decrypts
the ORIGINAL ciphertext live, checking the erasure key's CURRENT state
each call (`ADR-057`) — a value already baked into `EventPayloadSnapshot`
at enqueue time can't be re-derived from itself. `SourceSequenceNumber`
lets `WebhookOutboxPump` re-fetch the originating `StoredEvent` and
re-run `IPayloadMasker.MaskAsync` fresh on every delivery attempt.
`docs/data/schema-registry.md`'s "Webhook outbox and delivery cursor"
section was updated in the same pass, per this repo's own "the ADR that
adds a field is that field's shape authority" rule — a stale note in
that same file's "Webhook subscriptions" section (claiming the outbox/
cursor shapes were "not yet placed... remaining propagation work," when
that section already existed further down the same file) was also found
and corrected while touching it.

**Decision 2 — a real circular-project-reference bug, caught by the
build itself (`MSB4006`), before any test ran.** `EventStore.Router`
needs `EventStore.Webhooks` for `WebhookEnqueueResolver`; the first
implementation had `WebhookOutboxPump`'s dead-letter publish going
through `PublishService` (`EventStore.Inbox`), which itself references
`EventStore.Router` (`EntityIdResolver`) — a genuine cycle. Fixed by
having `WebhookOutboxPump` append `WebhookDeliveryFailed` via
`EventAppender` directly instead, with `Status: "received"` (Router's
own next tick folds/validates it exactly like any ordinary publish,
resolving `EntityId` per the reserved type's own `EntityIdField`) — the
same lower-level primitive `UpcastMaterializer`/`PeerSyncReceiver`
already bypass `PublishService` for, for their own, different reasons.
This also required setting the manually-constructed `StoredEvent`'s
`EntityId = ""` explicitly (PublishService's own "starts empty, Router
fills it in" convention) — a real `NOT NULL constraint failed` caught
only by running the dead-letter test, not by reading the code back.

**A deliberate scoping decision, stated rather than left implicit**: an
event whose own declared schema version isn't registered
(`SchemaStatus: "unknown"`) is never enqueued for webhook delivery at
all — there is no schema to safely mask an unknown shape's sensitive
fields against.

**A narrowing beyond a single dead-lettered row**: a permanently-broken
target's cursor still advances past the poison row after `MaxAttempts`,
so one broken subscriber can never head-of-line-block every later event
behind it forever — the failure itself is never silently dropped (the
`WebhookDeliveryFailed` event is the permanent, queryable record), only
the blocking is relieved.

**A real test-isolation bug found while writing
`WebhookDeliveryHttpSqliteTests.cs`, not a production bug**:
`WebhookOutboxPump.RunOnceAsync` deliberately queries every Active
subscription with no `AppId` scope at all (the correct, real
production shape for a deployment-wide pump) — unlike every other
service in this repo's own tests, which always scope their own queries
to one caller-chosen `AppId`/key and can safely share one SQLite file
under MSTest's 32-way parallelism. Sharing one file made one test's own
tick pick up and attempt delivery against a DIFFERENT, concurrently-
running test's own subscription and backend, inflating request counts
in ways that only made sense once traced back to the shared file.
Fixed by switching this one test class to a per-test-method database
file (`[TestInitialize]`/`[TestCleanup]`, not `[ClassInitialize]`/
`[ClassCleanup]`) — a deliberate, documented departure from every other
`*SqliteTests.cs` file's own shared-class-file convention. A second,
smaller timing issue in the same file: a fixed inter-tick delay shorter
than the worst-case backoff+jitter window (up to 250ms of jitter alone)
sometimes left a scheduled retry not yet due, landing one attempt short
of the expected count — fixed by polling until the expected count is
reached (bounded by a 5-second deadline) rather than assuming a fixed
number of ticks always lands exactly on it.

Verified with
[`WebhookScenarioAssertions.cs`](../../tests/EventStore.IntegrationTests/WebhookScenarioAssertions.cs)/
`WebhookSqliteTests.cs`/`WebhookPostgresTests.cs`/`WebhookSqlServerTests.cs`
(claim-snapshot freeze, masked-and-enqueued, non-matching-never-enqueued,
plus a pure `WebhookRetryTracker` backoff-spacing unit test, across all 3
providers) and
[`WebhookDeliveryHttpSqliteTests.cs`](../../tests/EventStore.IntegrationTests/WebhookDeliveryHttpSqliteTests.cs)
(SQLite-only — nothing about HTTP delivery is provider-specific, the same
reasoning `AttachmentHttpSqliteTests`/`ReplicationHttpSqliteTests` already
established for their own real-wire halves): Standard Webhooks header/
signature verification; a failed delivery eventually succeeding with the
cursor advancing only on actual success; exhausted retries dead-lettering
as a `WebhookDeliveryFailed` event confirmed queryable through the
ordinary Lineage API and unblocking the subscription for its next event;
a simulated pump restart (a fresh `WebhookRetryTracker`, same durable
cursor) proving no lost or duplicated delivery; and the crypto-shredding
erasure/retry interaction in both directions. Full SQLite regression
suite re-run clean (65/66 — only the pre-existing, unrelated
`SubscribingOverRealHttpStreamsAMatchingEventAsSse` flake).

- [`RegionOptions.cs`](../../src/EventStore.Replication/RegionOptions.cs) —
  this site's own configured `Region` tag.
- `PeerSyncEndpoints.cs` — `/peer-sync/whoami`'s response gained `region`;
  a new `PUT /replication/residency/{appId}`, gated by `registry:admin`.

**Region propagation reuses two EXISTING mechanisms, adds no new
discovery of its own**: `KnownPeer` (`ReplicatedEventPayload.cs`) gained
an optional third field, `Region`, riding the SAME gossip
`KnownPeers`/`/peer-sync/push` exchange `PeerId` already uses — a
transitively-gossiped peer's own region propagates without this site
ever contacting it directly. `PeerAddressBook` now tracks `(PeerId,
Region)` together per address (`SetPeerIdAndRegion`/`RegionFor`,
replacing the old `PeerId`-only dictionary). `PeerSyncClient.WhoAmIAsync`
now returns `(PeerId, Region?)`.

**Enforcement lands exactly where `ADR-061`'s own text places it** —
`PeerSyncWorker.SyncOnceWithAsync`: loads every `AppResidencyPolicy` once
per tick (a small table, no reason to re-query per address), then
filters the CANDIDATE event window per-event: an unconstrained `AppId`
passes unconditionally; a constrained one only if the destination peer's
own known `Region` is in its `AllowedRegions`. **A peer with no yet-known
region can never receive a constrained `AppId`'s events at all** — the
conservative default this ADR's own "residency wins" priority implies
for an unconfirmed destination, not stated explicitly in the ADR's own
text but a direct consequence of it.

**A narrowing found necessary while building, not just permissive**: a
residency-excluded event still advances `PeerSyncCursor.
LastAckedSequenceNumber` for that specific peer, exactly as if sent —
permanently excluded from that one peer, never retried on a later tick.
Without this, a constrained `AppId` publishing alongside unconstrained
ones would re-evaluate (and re-skip) the same excluded event forever.

**The "surfaced as an operational signal" exit criterion** is a
`LogWarning` inside `RunOnceAsync` (a new optional `ILogger` parameter)
naming any constrained `AppId` whose `AllowedRegions` are satisfied by
fewer than 2 currently-known live sites — checked once per tick, never
blocking the write or the sync itself.

Verified with
[`DataResidencyHttpSqliteTests.cs`](../../tests/EventStore.IntegrationTests/DataResidencyHttpSqliteTests.cs)
(SQLite-only, real HTTP — three real Host TestServers: a sender and two
differently-tagged destinations, `eu-west`/`us-east`, the same real-wire
pattern `ReplicationHttpSqliteTests.cs` already established, since
region is learned over the real `/peer-sync/whoami` handshake, not
something a direct-service-call test could exercise): an
`eu-west`-restricted `AppId`'s event reaches the `eu-west` peer but never
the `us-east` one, even though both are ordinary, reachable, gossip-
configured peers; an unconstrained `AppId` reaches both; and the
under-replication warning fires, naming the `AppId`/region, without ever
rejecting the write. Plus a pure `PeerAddressBook` region-gossip-merge
unit test in `ReplicationScenarioAssertions.cs` (SQLite-only).

**A real test-isolation bug found while writing
`DataResidencyHttpSqliteTests.cs`, the same class item 34 already hit
for `WebhookOutboxPump`**: `StoredEvent.SequenceNumber` is a single
global counter across every `AppId` in one file, and `PeerSyncCursor` is
keyed by `PeerId` alone — three test methods sharing one sender database
under MSTest's 32-way parallelism raced on both, inflating one test's
own expected sequence-number/cursor assertions with another
concurrently-running test's own events. Fixed by giving the sender side
its own per-test database file (`[TestInitialize]`/`[TestCleanup]`); the
two destination Hosts stayed class-level/shared, since every assertion

Full SQLite regression suite re-run clean (68/69 — only the pre-existing

`ADelegatedGrantScopedToOneEntityPassesRequiredReadClaimForThatEntityOnlyNotBlanket`,

## Item 36, "Bulk Ingestion & External Interchange-Format Adapters," is Done (`ADR-072`)

`docs/08-build-plan.md`'s status table and `BuildPlan_All` diagram fill
both updated to Done/`#palegreen` in this pass. `docs/06-solution-
structure.md` gained a propagation note reconciling its own two-project
sketch (`EventStore.InterchangeAdapters`/`.Hl7v2MllpListener`) against
what actually got built.

**Bulk/batch ingestion** — `POST /publish/batch`
([`PublishEndpoints.cs`](../../src/EventStore.Inbox/PublishEndpoints.cs)):
parses the request body as a raw `JsonArray`, not a strongly-typed
`List<BatchPublishItem>`, specifically so ONE malformed item can be
caught and reported per-item without a deserialization failure aborting
the entire batch. Each well-formed item still goes through
`PublishService.PublishAsync`'s own per-event transaction/idempotency/
hash-chain path, one call per item — batching is a transport
optimization, never a shared-transaction guarantee. A batch response can
only ever carry ONE real HTTP status, so every item's own would-be
status (202/409/404/403/400/401) rides inside the response body as an
explicit `httpStatus` field; the outer response is always `202`.

**External interchange-format adapters** — new
[`EventStore.Interchange.Abstractions`](../../src/EventStore.Interchange.Abstractions/)
(just `IInterchangeFormatAdapter.cs` + `InterchangeInboundResult`,
deliberately zero project references) and
[`EventStore.Interchange`](../../src/EventStore.Interchange/) (the
concrete adapters + the MLLP listener):

- [`Hl7V2Adapter.cs`](../../src/EventStore.Interchange/Hl7V2Adapter.cs) —
  real HL7v2 pipe-delimited segment parsing (verified against the actual
  v2.3 message structure before writing this): MSH's own field-1-is-the-
  separator offset quirk, PID-3/PID-5 patient identifier/name extraction.
  Scoped to `ADT^A01` only — an unhandled message type throws
  `NotSupportedException`, never silently ignored.
- [`FhirAdapter.cs`](../../src/EventStore.Interchange/FhirAdapter.cs) —
  real FHIR R4 `Patient` resource JSON parsing (`name[].family`/
  `given[]`). RESTful/JSON-native, no MLLP bridge needed.
- [`Hl7V2MllpListener.cs`](../../src/EventStore.Interchange/Hl7V2MllpListener.cs) —
  a real `BackgroundService` TCP listener speaking actual MLLP framing
  (`0x0B` start block, `0x1C 0x0D` end block, verified against the real
  MLLP spec) and returning a real HL7v2 `ACK` (`MSA|AA|`/`MSA|AE|`).
  Opt-in (`Hl7V2MllpOptions.Enabled`). Resolves its own adapter via the
  SAME `"Hl7V2"` keyed-DI key `AddInterchange` registers, not a
  hardcoded concrete type.
- [`IchE2bR3Adapter.cs`](../../src/EventStore.Interchange/IchE2bR3Adapter.cs)/
  [`Gs1EpcisAdapter.cs`](../../src/EventStore.Interchange/Gs1EpcisAdapter.cs) —
  outbound-only. Root element names/namespaces verified via web search
  against the real ICH/GS1 specifications before writing this
  (`MCCI_IN200100UV01` in `urn:hl7-org:v3` for E2B(R3)'s own batch
  envelope; `EPCISDocument`/`EPCISBody`/`EventList`/`ObjectEvent` in
  `urn:epcglobal:epcis:xsd:2` for EPCIS 2.0) — each an honestly-scoped
  small, representative subset of its real standard's own much larger
  schema, stated explicitly in code comments, never implied as complete
  spec conformance.
- [`InterchangeEndpoints.cs`](../../src/EventStore.Interchange/InterchangeEndpoints.cs) —
  `POST /interchange/fhir/{appId}`, `AddInterchange()`'s keyed-DI
  registrations.

**A circular-project-reference risk avoided by design, not found after
the fact this time** — item 34's own `EventStore.Webhooks`/
`EventStore.Router` cycle was the precedent that made this obvious up
front: `EventStore.Router` already depends on `EventStore.Webhooks`
(`WebhookEnqueueResolver`), and `EventStore.Webhooks` needs
`IInterchangeFormatAdapter` for its own outbound-composition step — so
`EventStore.Interchange.Abstractions` carries zero dependency on
`EventStore.Inbox`'s `PublishEventRequest` at all. `InterchangeInboundResult`
is a plain `(EventType, Payload, ReviewPending)` tuple; the CONCRETE
inbound adapters/endpoints (which CAN depend on `EventStore.Inbox`)
convert it into a real `PublishEventRequest` themselves.

**Outbound composition** lands in `WebhookOutboxPump`
([`EventStore.Webhooks`](../../src/EventStore.Webhooks/WebhookOutboxPump.cs),
extended, not a new mechanism): `WebhookSubscription` gained an
`OutboundAdapterKey` column (migrated across all 3 providers, added to
`docs/data/schema-registry.md` in the same pass). When set, the resolved
adapter's `FormatOutboundAsync` transforms the masked JSON into the
external wire format IMMEDIATELY BEFORE signing/delivery — the masked
JSON itself (`WebhookOutbox.EventPayloadSnapshot`, the delivery-history
record and what re-masking/erasure-retry logic always operates on) is
never replaced, only the bytes actually POSTed and signed are. An
adapter failure (a misconfigured key, or one that throws
`NotSupportedException` for this direction) fails that ONE delivery
attempt exactly like an unreachable target would — retried with
backoff, eventually dead-lettered — never a silent fallback to
untransformed JSON the target isn't expecting, and never an unhandled
exception that would abort every OTHER subscription's own tick.

Verified with
[`BatchPublishHttpSqliteTests.cs`](../../tests/EventStore.IntegrationTests/BatchPublishHttpSqliteTests.cs)
(real HTTP — "outer 202 always" and "malformed item's own 400-shaped
body" are both real HTTP-response-shape facts, not provable via a direct
`PublishService` call),
[`InterchangeAdapterTests.cs`](../../tests/EventStore.IntegrationTests/InterchangeAdapterTests.cs)
(pure adapter-transform units: HL7v2/FHIR parsing, both outbound XML
transforms against their real element names, inbound/outbound direction

[`Hl7V2MllpListenerTests.cs`](../../tests/EventStore.IntegrationTests/Hl7V2MllpListenerTests.cs)
(a real `TcpClient` speaking actual MLLP framing against a real
`Hl7V2MllpListener` bound to an OS-assigned port — `Hl7V2MllpOptions.

[`FhirIngestionHttpSqliteTests.cs`](../../tests/EventStore.IntegrationTests/FhirIngestionHttpSqliteTests.cs)

`AnOutboundAdapterTransformsTheEventIntoItsExternalFormatImmediatelyBeforeDelivery...`
scenario in `WebhookDeliveryHttpSqliteTests.cs` proving the outbound
