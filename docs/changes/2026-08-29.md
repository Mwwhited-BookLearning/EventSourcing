## Investigated Postgres 40001 noise under real concurrent load — root cause found, two fix attempts tried and reverted, not yet safely fixed

Direct report: "I'm getting a ton of errors running the application...
`Npgsql.PostgresException: '40001: could not serialize access due to
read/write dependencies among transactions'`," then "it should not
error this much. it should be much more graceful for retrys and so on."
Confirmed real and routine (not just under heavy load) by running a
live `AppHost` and reading the Postgres container's own logs directly.
Root cause: `EventAppender`/`AccessLogAppender`'s Serializable-isolation
"read tail, insert, compute chain" critical section is exactly the
shape Postgres's SSI flags whenever two appends overlap — already
correctly retried by the existing `EnableRetryOnFailure` config (a
noise problem, not a correctness bug).

Tried a `pg_advisory_xact_lock` (acquired after `BeginTransactionAsync`)
to convert the race into a queue — a dedicated new regression test
(30 concurrent publishers, counting EF's own retry diagnostic event)
proved it didn't actually reduce conflicts at all (~97 retries still
observed). Tried a session-scoped `pg_advisory_lock`/`unlock` pair
acquired *before* the transaction instead — the same test hung
indefinitely, a real deadlock, before it could even be measured. Both
attempts reverted rather than ship an ineffective or unsafe change;
`EventAppender.cs`/`AccessLogAppender.cs` are back to their original,
proven-correct state. Full findings (including precisely why each
attempt failed, and the actual fix this points to — dropping to
`ReadCommitted` + `SELECT ... FOR UPDATE`, not attempted yet) are
tracked as a `TODO.md` item rather than a `docs/bugs/` report, since
this project's own bug-report protocol is for fixed defects and this
one isn't fixed yet — the diagnostic value is preserved there instead
of being lost.

## Built ADR-099 — Naive UI + Vue Router left-hand-nav shell, every existing component restyled

Direct request: adopt Naive UI (`naiveui.com`) and a left-hand-nav shell
"similar to Azure Portal and Azure DevOps," confirmed via
`AskUserQuestion` to restyle every existing component in the same pass
(not just the shell) and to introduce real Vue Router routes (not stay
router-free). Full decision recorded in `ADR-099` (`docs/adrs/
adr-099-naive-ui-router-left-nav-shell.md`); this section covers the
actual build.

`App.vue` no longer owns an `activeTab` ref/template-`v-if` tree.
`appConfig.ts` (per-instance launch config + `queueDomain`, both pure
reads of the URL/env, safe at module scope) and `appState.ts` (a
`provide`/`inject` contract for the business state `App.vue` still owns
— `viewActions`, `currentEntityId`, the amount-dispatch form, etc.) were
extracted so `router.ts`'s own navigation guard can gate `/queue` and
`/relying-party` by domain without depending on component setup timing,
and so six new route-view components under `src/views/` can render the
same tabs as routes. The shell itself is `n-config-provider` wrapping
`n-layout`/`n-layout-sider`/`n-menu` (collapse state in `localStorage`,
try/catch-wrapped) — `n-menu`'s items are render-function `RouterLink`s,
real `<a href>` elements, not a plain click handler, so deep-linking and
screen-reader link semantics both work.

Every existing component was restyled with real Naive UI components in
the same pass: `GenericFallbackView` and both Queue components (via the
shared `AuthorityQueue.vue`) use `n-data-table`; `EventComposer` uses
`n-form`/`n-input`/`n-checkbox` (the event-type picker deliberately kept
as a native `<select>` — `n-select`'s teleported dropdown would have
needed a disproportionate rewrite of `EventComposer.spec.ts`'s own
`find('select').setValue()` interaction for no real UX gain on a short,
keyboard-native list); `RelyingPartyAccessPanel`/
`LineageExportAndPlaybackPanel`/`BitemporalPlaybackControl`/
`OfflineBundleViewer` use `n-card`/`n-form-item`/`n-button`/`n-alert`.

**Five real bugs found only by actually running things — the exact
pattern this project keeps re-learning is its most valuable
verification technique, holding again**:

1. Naive UI's `n-card` `title`/`header` prop renders content wrapped in
   `role="heading"` with **no `aria-level`** in this installed version —
   a genuine, critical axe-core `aria-required-attr` violation. Caught
   by `a11y.spec.ts`'s own real `GenericFallbackView` check the moment
   `n-card`'s `title` prop was used there. Fixed everywhere by using a
   real `<h2>`/`<h3>` instead of the `title` prop.
2. `aria-label` set directly on `n-card`'s own root `<div>` (which
   carries no ARIA role) is a real axe-core `aria-prohibited-attr`
   finding — a `<div>` with no role doesn't support `aria-label`. Fixed
   by moving the label onto a wrapping `<section aria-label="...">`
   everywhere this pattern occurred.
3. `n-form-item`'s `label` prop never actually associates with its
   field via `for`/`htmlFor` in this Naive UI version — confirmed by
   reading `node_modules/naive-ui`'s own `FormItem.mjs` directly, which
   has no such wiring at all. A `label-for` prop does not exist on this
   component either (silently ignored, not an error) — found the hard
   way, having first tried exactly that and watched
   `MeridianWorkflowBRelyingPartyAccessPlaybookTests`'s own
   `GetByLabel("Event ID...")` keep timing out against a live `AppHost`
   even after the "fix." Corrected with an explicit `aria-label` on each
   `n-input`/`n-input-number`'s underlying native input, matching its
   visible label text — applied to every field in
   `RelyingPartyAccessPanel.vue`/`LineageExportAndPlaybackPanel.vue`,
   not just the one field the failing test happened to touch.
4. Naive UI's `input-props`/`inputProps` TypeScript type has no index
   signature for arbitrary attributes — `vue-tsc` rejected `data-testid`/
   `id`/`aria-label` at compile time everywhere they were needed to keep
   an existing Playwright/Vitest selector working. Worked around with an
   explicit `as any` cast at each call site (a real, narrow type-system
   gap in the library, not a design choice worth avoiding the pattern
   over).
5. Adding `n-data-table`'s own pagination (page size 10) to
   `EntityBrowser.vue` made a specific, already-known `EntityId` — the
   Vitals seed data's own continuity subject, `S-0091` — genuinely
   undiscoverable once `Samples.Vitals.Simulator`'s continuous background
   publishing had pushed more than a page of newer entities in front of
   it. Caught by `VitalsWorkflowAPlaybookTests` failing for real against
   a live simulator (not a static fixture, which would never have
   surfaced this). Pagination alone, it turns out, is not usable without
   a way back to a specific row — fixed with a client-side filter box
   (`EntityBrowser.vue`, filtering the same already-loaded array, no new
   server query) and updated 8 of the 12 playbooks' own row-lookup steps
   to fill the filter before asserting a specific row is visible.
   `TODO.md`'s own "real paged server query" item (the actual
   less-data-over-the-wire ask) stays open and separately tracked — this
   fix only restores findability within a page-size-10 render.

Every Vitest spec whose selectors broke against the new markup was
fixed in the same pass (`GenericFallbackView.spec.ts`,
`EventComposer.spec.ts`, `AuthorityQueue.spec.ts`, both directly and via
