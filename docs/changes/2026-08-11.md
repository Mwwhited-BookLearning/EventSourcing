## Full docs-vs-implementation alignment audit (all 39 completed build-plan items)

Direct request: review the implementation against the design docs for
everything built so far (not just the immediately-preceding items 38/39)
and fix any drift found.

**Method**: 4 read-only research agents in parallel (one per item range,
1-10/11-20/21-30/31-39), each reading every relevant ADR/data-model doc/
feature doc/solution-structure passage for its range and comparing it
against the real `src/`/`tests/` code, reporting findings without
editing anything. Findings were explicitly scoped to exclude anything
`docs/08-build-plan.md`'s own text, `TODO.md`, or a `docs/changes/*.md`
entry already honestly narrated as a known narrowing/gap — only genuine,
*silent* drift in some other doc counted. Once all 4 reports were back,
6 fix agents ran in parallel across disjoint file sets (no two agents
ever touched the same file) to apply the corrections: ADRs got additive
strikethrough-and-correct edits per `.claude/protocols/additive-history-
editing.md`; every other doc type got a direct rewrite of the stale
passage.

**Result**: 44 files changed (+1516/-631 lines), zero code files
touched (confirmed via `git status` before committing — every change is
doc-only). `dotnet build EventStore.slnx` reconfirmed clean afterward
(doc changes can't break a build, but confirmed no agent strayed outside
its assigned files anyway).

## Signing Secret Rotation, Dual Signature (build-plan item 40) — webhook half only

Before building, verified `ADR-093`'s own claim that "OpenIddict already
supports a client holding more than one valid credential — no framework
change needed" (the premise the ticket-exchange half of this item rested
on). Searched OpenIddict's own documentation, source, and issue tracker
(`openiddict/openiddict-core`) for a built-in multi-secret-per-client
mechanism — found none; `OpenIddictApplicationDescriptor.ClientSecret`
is a single string per registered application. This repo's own "verify
before citing" standing instruction caught a false premise before
anything got built on top of it, rather than after.

Presented the finding to the user with two options (build a real custom
credential-validation mechanism, or descope and track as follow-up); the
user chose to descope. Corrected `ADR-093` additively (struck through
the false claim in both the Decision and Consequences sections, in both
places it appeared) and narrowed `docs/08-build-plan.md`'s item 40 scope
to the webhook half only. The ticket-exchange rotation mechanism (a
custom OpenIddict event handler, or a stopgap second registered
application) is real, undesigned follow-up work, tracked in `TODO.md`,
not silently dropped.

**Built (webhook half)**: `WebhookSubscriptionService` gained
`RotateSigningSecretAsync` (moves the current `SigningSecret` to
`PreviousSigningSecret`, generates a fresh one) and
`DiscardPreviousSigningSecretAsync` (clears `PreviousSigningSecret`,
ending the overlap window). `WebhookSigner.Sign` gained an optional
`previousSigningSecret` parameter — verified the real Standard Webhooks
multi-signature format directly against the spec text ("both signatures
are sent, space delimited, in the webhook-signature header") before
implementing, rather than assuming the shape `WebhookSigner.Verify`
already tolerated (built ahead of this item, during item 34, on the
receiving side) was necessarily what the spec actually says. Two new
endpoints in `WebhookEndpoints.cs`: `POST /webhooks/subscriptions/{id}/
rotate-secret` and `POST /webhooks/subscriptions/{id}/discard-previous-
secret`.

One comprehensive test in `WebhookDeliveryHttpSqliteTests.cs`
(`RotatingTheSigningSecretEmitsDualSignaturesDuringTheOverlapWindow
ThenASingleSignatureOnceDiscarded`) proves the full lifecycle end to
end: exactly one signature before rotation; two signatures during the
overlap window, each independently verifiable via `WebhookSigner.Verify`
against either the old or the new secret (a receiver caching only the
old secret still verifies successfully); back to exactly one signature
after discarding, verifiable only against the new secret, with the old
secret confirmed to no longer verify. SQLite-only, matching this file's
own established "signing/HTTP delivery mechanics are provider-agnostic"
posture. Full webhook regression suite (12 tests) re-run clean.

## RFC 3161 Trusted Timestamping (build-plan item 42) — Done

Same session, continuing directly from item 41. Two consumers, per
`ADR-086`: Digital Sign-Off's `Signature.RFC3161Timestamp` (opt-in per
event type, `RequiredSignature.EnableRfc3161Timestamp`) and Lineage
Export's `ExportManifest.Rfc3161Timestamp` (always populated when a TSA
is configured, no separate opt-in).

Researched the real client-side API before building anything, per this
repo's "verify before citing" rule: `System.Security.Cryptography.Pkcs`
(BCL, since .NET 5) already ships `Rfc3161TimestampRequest`/
`Rfc3161TimestampToken` — building/encoding a request, and parsing +
cryptographically validating a TSA's response — so no third-party RFC
3161 library is needed for `EventStore.Timestamping`'s
`HttpTimestampAuthorityClient` (the default `ITimestampAuthorityClient`,
`EventStore.Abstractions`, registered only when `Timestamping:TsaUrl` is
configured, the same "no silent fallback" posture `AddErasure`'s Vault
registration already established).

Needed a real TSA to test against, and building one from scratch (not
just consuming one) surfaced real gaps not visible from the client-side
docs alone, each resolved by reading `dotnet/runtime`'s actual source
(sparse-cloned this session) rather than guessing:
- The BCL ships no public API for *acting as* a TSA (issuing a token) —
  only for building a request and parsing/verifying a response. Building
  the fake TSA's `TimeStampResp`/`PkiStatusInfo` wrapper required reading
  the real (internal) ASN.1 templates directly, since no public type
  covers it.
- A first attempt at a signed response was rejected with "not
  understood" — traced to the mandatory `SigningCertificateV2`
  (`ESSCertIDv2`) signed attribute RFC 3161/5035 require, which
  `CmsSigner` doesn't add automatically; hand-encoded via `AsnWriter`
  once found.
- A second attempt was then rejected for carrying an unrequested signer
  certificate — `CmsSigner.IncludeOption` must be `None` to match a
  request that didn't ask for one (`RequestSignerCertificate: false`,
  the client default).
- The full request → fake-TSA-issue → verify round trip was run and
  confirmed working end to end (including reuse across multiple requests
  through the same in-process `TestServer`, proving the signing
  certificate/key survive across calls) *before* any of this shipped as
  either production or test code — `TimestampingTestSupport.cs`'s fake
  TSA is genuine RSA/CMS signing throughout, not a stub returning
  arbitrary bytes.

A second, unrelated cross-language correctness question, needed for
`LineageExportService`'s manifest timestamp to hash the right bytes:
does `System.Text.Json`'s `DateTimeOffset` serialization exactly match
`ManifestHash.Compute`'s own `:"O"`-formatted hash input? Verified
directly (a throwaway C# program) rather than assumed — the two do
*not* always match byte-for-byte (`System.Text.Json` trims trailing-zero
fractional-second digits; `:"O"` never does), the same fact item 41's
own offline-player work had already found and worked around client-side
that same session; this item's server-side code was written already
aware of it.

**One real bug found only by running the real HTTP round trip against
the real fake TSA, not by reading the code back**: `PublishService`'s
first attempt mutated the already-tracked `Signature` object's
`RFC3161Timestamp` property in place. Invisible to EF's change tracker —
`JsonValueConverter.NullableComparer<T>()`'s own snapshot function
returns the same object reference rather than a deep clone, a gap that
file's own comment already documented once before, for the exact same
class of converted property. The publish request still returned `202`
successfully and `Signature` itself was present; only the new field
silently never persisted. Fixed by assigning a **new** `Signature`
instance carrying the token, rather than editing the tracked one.

Tests: `TimestampingHttpSqliteTests.cs` (4 methods, Sqlite-only, same
provider-agnostic reasoning `DigitalSignOffHttpSqliteTests.cs` already
established) — the Signature half wires the real Host's own typed
`HttpClient` to the fake TSA's `TestServer` via
`ConfigurePrimaryHttpMessageHandler` (an in-process, no-real-socket
substitution, the standard technique for testing an `IHttpClientFactory`
typed client against a controlled backend); the Lineage Export half
constructs `HttpTimestampAuthorityClient` directly against the same fake
TSA. Every resulting token is independently decoded and re-verified via
`Rfc3161TimestampToken.VerifySignatureForHash` against the fake TSA's own
certificate — proving actual RFC 3161 compliance, not merely "some bytes
got stored." Full regression suite re-run clean except the two already-
tracked, pre-existing flakes (`TODO.md`): SqlServer-testcontainers
resource contention (worse this session than previously recorded — see
that entry's own severity-update note) and the SSE-subscription timing
flake — neither touches Timestamping, Lineage Export, or Digital
Sign-Off.

New `EventStore.Archival` project. `ChainCheckpoint` (`EventStore.
Domain/EventLog/StoredEvent.cs`) gained a surrogate `Id` (no natural key
survives more than one archival operation) and is registered via EF
Core's "shared-type entity" feature — verified against a real scratch

assumed to work from documentation alone. `EventStoreContext` exposes

`ArchivalService.ArchiveEventLogSegmentAsync`/`ArchiveAccessLogSegmentAsync`:
verify the segment first (never archives anything `ChainVerificationService`/
`AccessLogChainVerificationService` haven't confirmed clean), serialize,
write the blob via `IAttachmentContentStore` (the ONE registered backend
this build stage ships, `InMemoryAttachmentContentStore` — its first
real production consumer; previously built but never actually wired to
a real caller, per item 16's own note), save the checkpoint, THEN detach
(`ExecuteDeleteAsync` on both `Events` and the archived rows' own
`EventParents`, no change-tracker round trip needed for the bulk
delete). That ORDER is deliberate: a crash at any point always leaves
the archived bytes/checkpoint durable BEFORE the only local copy is ever
removed — this design's own "never lose or corrupt data" governing
principle, applied to the archival operation itself, not just the
mechanism it protects.

**`ADR-089`'s own text said to reuse `ADR-068`'s litigation-export
NDJSON format; verified before assuming it fit, and it didn't, fully**:
`ExportedEventLine` is EntityId-scoped (one manifest per single entity)
and deliberately omits `ParentEventIds`/`Signature` — both of which
THIS mechanism's own "re-verify the internal chain" exit criterion
genuinely needs to recompute `PayloadHash`/`ChainHash` exactly. Reused
the FORMAT CONVENTION (newline-delimited JSON, one record per line)
with a new, sequence-range-scoped `ArchivedEventLine` shape instead — an
honest partial reuse, flagged as such in code and here, per this
repo's own "say when something is only partially borrowed" standing
convention, not the ADR's literal types.

`ChainVerificationService`/`AccessLogChainVerificationService`
(`EventStore.Inbox`) now seed live verification from the latest
`ChainCheckpoint`'s own `ChainHashAtRangeEnd` and query only
`SequenceNumber` strictly past it — ordinary, ongoing verification after
an archival never reads the archived segment at all, exactly this
item's own exit criterion, not merely "happens to still work."

**A real, critical, pre-existing-class-of-bug found only by actually
publishing an event immediately after an archival in a test — never
caught by reading the code back**: `EventAppender.AppendAsync`/
`AccessLogAppender.AppendAsync` compute their own next `ChainHash` by
reading the CURRENT highest-`SequenceNumber` LIVE row's own `ChainHash`.
Once that row has been archived (physically deleted by this same
item's own detach step), that query finds nothing, and both appenders
silently fell back to `EventChainHash.Genesis` — restarting the chain
from zero and breaking every `ChainHash` computed from that point on,
in REAL production code, not just a test artifact. Fixed in both
appenders: fall back to the latest checkpoint's own `ChainHashAtRangeEnd`
when no live row exists, mirroring the identical fix the two verifiers
above already needed for the same underlying reason (the live tail's
own "prior state" query silently assuming the tail is never empty).
`LogicalClock` needed no equivalent fix — `HybridLogicalClock.Next` is
wall-clock-anchored, not a pure counter chain, so it stays monotonic
across an archival on its own; checked, not assumed, before deciding it
was safe to leave alone.

A still-live child's own `EventParents` reference to an archived parent
is deliberately left as a tolerated dangling reference — `EventParent`
already carries no FK constraint at all (`ADR-005`'s own Permissive-mode
design), so nothing breaks; only the archived events' OWN parent-link
rows (as the child side) are removed, since that information is
preserved inside the archived bundle itself (`ArchivedEventLine.ParentEventIds`).

**A real test-design bug found while writing these, the same class this
repo's own tests have hit before (`WebhookDeliveryHttpSqliteTests.cs`'s
own header comment names the identical shape)**: one scenario's own
direct-DB payload tamper (proving a refused archival) was never
reverted after its own assertion, permanently poisoning the SHARED
`EventStoreContext` every later scenario in the same test method also
uses — every archival attempt after it failed with `SegmentNotVerified`
for a completely unrelated reason, traced back through several wrong
guesses before finding the actual root cause. Fixed with a `finally`
block restoring the tampered row once that scenario's own assertion is
done with it. Several OTHER scenario assertions also initially
hardcoded an assumed `SequenceNumber`/count as if each scenario started
fresh from `SequenceNumber` 1 — wrong given `SchemaRegisteredEventType`'s
own per-AppId bootstrap event(s) (`ADR-067`) and, separately, archival's
own deliberately GLOBAL (not per-AppId) `SequenceNumber` space meaning
an earlier scenario's own archival history shifts what "starting fresh"
even means for a later one sharing the same context — fixed by deriving
expected values from the checkpoint's own recorded range or a captured
before/after delta instead of a literal.
