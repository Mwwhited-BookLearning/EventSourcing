# 2026-08-28

## Fixed ADR-096's registration guardrail: cardinality check now covers `Equality`, not just `Range`

Found while reviewing Vitals/Meridian (the two proving-ground domains)
for real `x-masking-searchable` candidates the previous session — a
genuine gap in already-shipped, "Done"-marked code: `MaskingSchemaValidator.
ValidateSearchableConfig` only required a `cardinality` hint for `Range`-
kind fields. But [Naveed/Kamara/Wright, CCS 2015](https://www.microsoft.com/en-us/research/publication/inference-attacks-property-preserving-encrypted-databases/)
— the same paper the guardrail already cites — names **deterministic
encryption** as frequency-analysis-vulnerable, and a blind `Equality`
index is deterministic encryption by definition (same plaintext, same
ciphertext, always). A `Low`-cardinality classified field (Meridian's
`MatchedListEntryId` — a bounded, enumerable sanctions-list domain) could
register `Equality` with zero guardrail coverage before this fix.

- `src/EventStore.SchemaRegistry/MaskingSchemaValidator.cs`: the
  cardinality/`acknowledgeLeakageRisk` check now runs for `indexKind is
  "Equality" or "Range"`, not `"Range"` alone; `bucketGranularities` stays
  required for `Range` only.
- `docs/adrs/adr-096-searchable-blind-index-bucketed-range.md` and
  `docs/data/schema-registry.md` corrected in the same pass (additive —
  states the original Range-only scope and why it was widened, not a
  silent rewrite).
- New regression tests in `SearchableEncryptionSqliteTests.cs`: a
  `Low`-cardinality classified `Equality` field is rejected without
  `acknowledgeLeakageRisk`, succeeds with it, and a field with no
  `cardinality` declared at all is rejected regardless of classification
  (matching `Range`'s existing unconditional-requirement behavior). The
  pre-existing equality-query test's own schema needed `cardinality:
  "High"` added (`Email`, genuinely high-cardinality) to keep passing
  under the now-stricter rule.
- Full suite verified: unit (17/17), Sqlite integration excluding the
  known pre-existing auth-flakiness classes (142/142) — no regressions.
- `TODO.md`'s matching item removed.

## Corrected the "ViewDefinition never resolves" finding above — it was a screenshot-timing artifact

Investigated the second finding logged just above by actually measuring
it, rather than leaving it as a guess, per direct request to keep going
on `TODO.md`'s open items. **It was wrong**: `Patient`/`ApplicantIdentity`
Detail `ViewDefinition`s resolve correctly — a direct timing measurement
(a throwaway diagnostic `[TestMethod]`, run once, then deleted) showed
`GenericFallbackView` visible at `t=0ms` and the real templated view
(`TemplateRenderer`, `aria-label="Entity (ViewDefinition-rendered)"`)
visible at `t=500ms`. `EntityView.vue`'s `entry` (from the entity cache)
populates before `loadViewDefinition`'s own async GraphQL round trip
resolves, so the fallback is real but transient — every screenshot this
session and the prior one happened to land inside that ~500ms window
because the test's own wait condition (a heading containing the raw
`EntityId`) only ever matches `GenericFallbackView`'s heading markup,
never `TemplateRenderer`'s template-defined one, so it was structurally
guaranteed to catch the fallback, not prove its permanence.

- All three playbook tests (`VitalsWorkflowAPlaybookTests`, both
  `MeridianWorkflowA*PlaybookTests`) now wait for `aria-label="Entity
  (ViewDefinition-rendered)"` before capturing the Detail step, and all
  three playbooks regenerated with the real templated view instead of
  the transient fallback — `docs/playbooks/vitals/workflow-a-patient-
  enrollment-and-informed-consent.md` and both `docs/playbooks/
  meridian/workflow-a-*.md` files' Step 3.
- **A real, different, smaller gap surfaced instead by looking at the
  corrected screenshots**: both templates render every field label as a
  literal, unresolved `[key]` bracket (`TemplateRenderer.vue`'s own
  documented fallback for a translation key with no entry in the
  `translations` map) — no translation resource registers
  `patient_detail_title`/`subject_id`/etc. or `applicant_detail_title`/
  `applicant_id`/etc. anywhere yet. `TODO.md`'s entry replaced
  accordingly (the mechanism itself works; the resource file for these
  specific keys doesn't exist).
- All three playbook tests re-verified passing against a live `AppHost`
  after this fix.
