# 2026-09-02

## Closed: schema-registry state now replicates across peers (`ADR-103`, resolves `docs/10-open-questions.md` row 1)

Direct request, resolving the fork `docs/10-open-questions.md` row 1
left open after `ADR-102`'s own live cross-provider verification found
it: build a real fold worker, or permanently downgrade `ADR-033`'s own
claim. Built the fold worker.

`SchemaRegisteredEventType.cs`'s own header comment already gives the
real reason `EventTypeDefinition` was never rearchitected onto a
generic Router-fold — every prior build-plan item's tests assume
synchronous, immediately-consistent LOCAL registration, which an async
fold would break. This work respects that boundary: the local,
originating registration is completely unchanged; a **second**,
narrowly-scoped mechanism replicates it to peers that never
independently register it.

**What shipped**:
- `AppendSchemaRegisteredAsync`'s notification payload widened from
  `{EventTypeName, Version}` to the full registration — `JsonSchema`,
  `ChangeKind`, `EntityIdField`, `EntityType`, `ParentValidationMode`,
  `RejectionBehavior`, `RequiredClaims`, `FilterableFields` (including
  `ADR-096`/`097`'s `SearchableIndexConfig`), `RequiredSignature`,
  `ExpectedResponse`, `Upcast`/`DowncastFromPrevious`. Additive only —
  `required` stays `["EventTypeName", "Version"]`.
- **A real, separate bug found while designing this**: the notification
  stamped the literal string `"local"` as `OriginId` for *every* site,
  unlike an ordinary published event's own configurable
  `OriginIdOptions`. Every site's own notification was indistinguishable
  from every other's the moment they synced together — exactly the
  signal a fold reactor needs to tell "mine" from "elsewhere." Fixed via
  a new `SchemaRegistryOriginIdOptions`, duplicated from (not
  referencing) `EventStore.Inbox.OriginIdOptions` — `EventStore.Inbox`
  depends on `EventStore.SchemaRegistry` (`ADR-033`/`090`), so a
  reference the other way would cycle; both bind to the same
  `"OriginId"` configuration section, so a real deployment's one
  configured value resolves identically through either type.
- New `SchemaRegistrationReplicationResolver` (`EventStore.Router`) — the
  same "special-purpose reactor, one event type" shape
  `AuthorityDecisionResolver`/`EntityErasureResolver` already establish,
  deliberately not a generic rearchitecture. Fires only for a
  `SchemaRegistered` notification whose `OriginId` differs from this
  site's own (a peer-synced copy, never the local one, which already
  applied directly and synchronously). **A real bug found only by
  actually running this cross-peer**: had to be checked *ahead of*
  `ADR-038`'s own rollback gate, not after it — that gate treats "this
  deployment has never registered `SchemaRegistered` itself for this
  AppId" as "predates the shape, defer forever," which is exactly true
  and *permanent* for a peer that only ever receives replicated schemas.
  Moved the check earlier, with an early return that skips this
  notification's own otherwise-generic (and, for this reason, otherwise
  perpetually-deferred) entity fold — cosmetic lineage bookkeeping
  nothing in this codebase queries.
- New `SchemaRegistryService.ApplyReplicatedRegistrationAsync` — the
  peer-sync counterpart to `RegisterAsync`: trusts the origin's
  already-validated decision completely (no re-validation, no
  auto-incrementing version — the replicated version is authoritative),
  idempotent on `(AppId, Name, Version)` already present, never
  regresses `IsActive` backward on an out-of-order/late redelivery,
  never re-notifies (would gossip-amplify forever in a full-mesh
  topology), and replicates a `FilterableField`'s own provider-specific
  index DDL too.

**Live-verified cross-provider**, the same bar `ADR-102` set:

## Closed: `PlaybookRecorder` now emits its own diagram image reference, surviving regeneration (TODO.md)

`scripts/extract-diagrams.mjs` inserts a `![...](....svg)` reference
immediately above a fenced diagram the first time it runs — but
`PlaybookRecorder.WriteMarkdownAsync` regenerates a whole playbook file
from scratch on every E2E test run, silently dropping that insertion on
the next regeneration, since the two pipelines were never coordinated.
Worked around previously by re-running the extraction script after any
E2E run touching a playbook; fixed for real now: `WriteMarkdownAsync`
computes and emits the exact same reference itself (mirroring
`extract-diagrams.mjs`'s own `processFile`/`slugify` path convention —
a playbook's own sequence diagram is always diagram index 1, heading
"Sequence Diagram", so the target is always
`docs/diagrams/playbooks/{domain}/{role}/{task}/01-sequence-diagram.svg`),
computed purely from `_markdownPath`'s own already-known `docs/...`
shape, no filesystem access needed. A later `extract-diagrams.mjs` run
now recognizes the reference via that script's own idempotency check
and never duplicates it — still needed to keep the underlying `.puml`
extraction current when a diagram's own content changes, but no longer
needed just to restore a reference this method now emits correctly on
its own, every time. Verified live: re-ran a real, already-existing
playbook test (`TasksListPlaybookTests`) end to end and confirmed the
regenerated file carries the correct reference.

**A second, real, previously-undiscovered bug found while verifying
this fix, affecting every playbook doc, not just the one touched
first**: `extract-diagrams.mjs`'s own heading-detection regex
(`/^#{1,6}\s+(.+)$/`) never matched a heading at all in a Windows-CRLF
file — every `PlaybookRecorder`-generated playbook doc, since C#'s
`StringBuilder.AppendLine` uses `Environment.NewLine`. A bare `$`
anchor only special-cases a trailing `"\n"` as end-of-line, per the
ECMAScript spec, never a trailing `"\r"` left over from splitting a
CRLF file on `"\n"` alone. `lastHeading` silently stayed at its own
initial `"diagram"` default for every fence in every such file,
regardless of that file's real heading text — every playbook's own
diagram had always been extracted as `01-diagram.svg`, never the
heading-derived name (`01-sequence-diagram.svg`) the feature actually
promises. Not a broken output (still a unique, valid path) but a real,
silent defect, invisible until this pass's own reference computation
gave something to cross-check the script's real behavior against.

Fixed by stripping a trailing `"\r"` for the heading match only (not
from the line itself, so a CRLF file's own line endings are completely
unaffected on write). Closing the loop required updating every
already-affected doc, not just the two touched directly this pass —
left half-fixed, the corrected script would keep silently generating an
orphaned, differently-named `.puml` duplicate next to each doc's still-
stale reference every time anyone re-ran it. Fixed for good: all 12
pre-existing playbook docs (`vitals`/`meridian`) plus `docs/mental-
vision.md` (an unrelated, separately-found doc that had simply never
been run through the extraction pipeline at all until this pass's
repo-wide verification) had their own stale `![diagram](.../01-
diagram.svg)` reference corrected to the real, heading-derived name,
and each superseded `01-diagram.{puml,svg}` pair deleted. Confirmed
fully idempotent afterward: three consecutive `node scripts/extract-
diagrams.mjs` runs produce zero further changes across all 103 `docs/`
files carrying a diagram.

One real, hands-on mistake made and caught during this cleanup, worth
recording: an overly-broad `rm -rf` on a batch of "stale" diagram
directories briefly deleted several genuinely pre-existing, unrelated,
already-committed files alongside the intended ones (including a real,
independently-authored `VitalsAdverseEvent_Playbook_Sequence.svg` with
no connection to this bug at all) — caught immediately via `git status`
showing tracked deletions, restored via `git checkout --` before
proceeding, and the cleanup redone file-by-file instead of by directory.
