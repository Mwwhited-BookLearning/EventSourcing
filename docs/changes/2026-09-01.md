# 2026-09-01

## Added: real end-to-end test coverage for the flow engine/`myTasks` (ADR-101)

Two new automated tests, both driving the real thing rather than a
synthetic double:

- `tests/EventStore.IntegrationTests/PendingTaskProjectionSqliteTests.cs`
  — the same real, two-`WebApplicationFactory`-TestServer HTTP bar
  `ProjectionsSqliteTests.cs` already established for
  `OrderSummaryProjection`, applied to `FlowProjection`/`PendingTask`
  instead: registers `VitalsWorkflowB`'s real schemas via the Host's own
  `SchemaRegistryService` (no hand-duplicated schema JSON), publishes a
  real `AdverseEventReported` over HTTP, drives the real embedded
  `VitalsWorkflowBFlow.Build()` through `ProjectionHost<PendingTask>
  .CatchUpOnceAsync`, and confirms the row appears — then publishes a
  real step-up-satisfying `authorityDecision` as `vitals-pi-client` and
  confirms the row disappears. One test method (`AllPendingTaskScenarios`,
  matching `ProjectionsSqliteTests.AllProjectionScenarios`' own shape) —
  found the hard way that splitting it into two separate `[TestMethod]`s
  hits a real `UNIQUE constraint failed: Checkpoints.ProjectionName`
  the moment a second, independently-built `ProjectionHost` targets the
  same physical checkpoint database a first one already checkpointed.

- `tests/EventStore.E2ETests/TasksListPlaybookTests.cs` — a genuine,
  full-`AppHost`-driven Playwright playbook (`docs/playbooks/vitals/
  my-tasks/discover-and-open-a-pending-task.md`), the same shape as
  `VitalsPrincipalInvestigatorQueuePlaybookTests.cs`. Opens "My Tasks",
  waits for a real task raised from `Samples.Vitals.Simulator`'s
  continuously-published `IonmAlertRaised` (walked through
  `VitalsWorkflowDFlow`'s real embedded `.puml` by a real `vitals-flows`
  worker resource), clicks "Open", confirms it lands on the existing
  Principal Investigator Queue. Passed against a real Postgres-backed
  `AppHost` (Docker), 1/1.

**Writing that E2E playbook required actually wiring the flow engine
into `EventStore.AppHost` for the first time** — until this pass,
neither `Samples.Vitals.Flows`/`Samples.Meridian.Flows` nor even the
pre-existing `Samples.Orders.Projections` had ever been registered as
an AppHost resource, so `/tasks` would have shown nothing at all under
a real orchestrated run. Added, completing a meaningful slice of the
still-open "Postgres/SqlServer host wiring" punch-list item along the
way:

- `EventStore.Host.Postgres` gained the same `PendingTasksDbContext`
  (read-only) + `myTasks` wiring `EventStore.Host.Sqlite` already had —
  always SQLite regardless of the write-side provider, the same "one EF
  Core provider is sufficient for a read model" posture
  `OrdersProjectionsDbContext` already established.
- `EventStore.AppHost/AppHost.cs` gained two new resources,
  `vitals-flows`/`meridian-flows`, each a real `ProjectionHost
  <PendingTask>` worker pointed at `eventstore`'s Follow API and
  `devIdp`, sharing one physical `../pending-tasks.db` file with
  `eventstore` itself (the same relative-path convention already used
  standalone) so the cross-domain `myTasks` query actually sees both
  domains' tasks under a real orchestrated run, not just in isolated
  tests.

SqlServer host wiring remains genuinely open — `AppHost` only ever
targets one `Host.<Provider>` at a time (`ADR-001`, currently Postgres),
so it has no consumer forcing that provider's own equivalent wiring yet.

Full solution build clean; `EventStore.UnitTests` (86/86) and
`EventStore.IntegrationTests` (245/247, the 2 non-PendingTask failures
reproduced as pre-existing parallel-load flakiness, confirmed passing
individually) unaffected.

Still open from the ADR-101 punch list: SqlServer host wiring, and the
full docs pass (ADR-101 itself, `docs/10-open-questions.md` row 1,
`docs/data/*.md`, `docs/patterns/README.md`, `docs/08-build-plan.md`,
the domain README `.puml` embeds, `docs/07-adrs.md`'s index row).
