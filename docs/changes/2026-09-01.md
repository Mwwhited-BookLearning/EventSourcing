## Added: real end-to-end test coverage for the flow engine/`myTasks` (ADR-101)

Two new automated tests, both driving the real thing rather than a
synthetic double:

- `tests/EventStore.IntegrationTests/PendingTaskProjectionSqliteTests.cs`
  — the same real, two-`WebApplicationFactory`-TestServer HTTP bar
  `ProjectionsSqliteTests.cs` already established for
  `OrderSummaryProjection`, applied to `FlowProjection`/`PendingTask`
  instead: registers `VitalsWorkflowB`'s real schemas via the Host's own
  `SchemaRegistryService` (no hand-duplicated schema JSON), publishes a
  real `AdverseEventReported` over HTTP, drives the real embedded
  `VitalsWorkflowBFlow.Build()` through `ProjectionHost<PendingTask>
  .CatchUpOnceAsync`, and confirms the row appears — then publishes a
  real step-up-satisfying `authorityDecision` as `vitals-pi-client` and
  confirms the row disappears. One test method (`AllPendingTaskScenarios`,
  matching `ProjectionsSqliteTests.AllProjectionScenarios`' own shape) —
  found the hard way that splitting it into two separate `[TestMethod]`s
  hits a real `UNIQUE constraint failed: Checkpoints.ProjectionName`
  the moment a second, independently-built `ProjectionHost` targets the
  same physical checkpoint database a first one already checkpointed.

- `tests/EventStore.E2ETests/TasksListPlaybookTests.cs` — a genuine,
  full-`AppHost`-driven Playwright playbook (`docs/playbooks/vitals/
  my-tasks/discover-and-open-a-pending-task.md`), the same shape as
  `VitalsPrincipalInvestigatorQueuePlaybookTests.cs`. Opens "My Tasks",
  waits for a real task raised from `Samples.Vitals.Simulator`'s
  continuously-published `IonmAlertRaised` (walked through
  `VitalsWorkflowDFlow`'s real embedded `.puml` by a real `vitals-flows`
  worker resource), clicks "Open", confirms it lands on the existing
  Principal Investigator Queue. Passed against a real Postgres-backed
  `AppHost` (Docker), 1/1.

**Writing that E2E playbook required actually wiring the flow engine
into `EventStore.AppHost` for the first time** — until this pass,
neither `Samples.Vitals.Flows`/`Samples.Meridian.Flows` nor even the
pre-existing `Samples.Orders.Projections` had ever been registered as
an AppHost resource, so `/tasks` would have shown nothing at all under
a real orchestrated run. Added, completing a meaningful slice of the
still-open "Postgres/SqlServer host wiring" punch-list item along the
way:

- `EventStore.Host.Postgres` gained the same `PendingTasksDbContext`
  (read-only) + `myTasks` wiring `EventStore.Host.Sqlite` already had —
  always SQLite regardless of the write-side provider, the same "one EF
  Core provider is sufficient for a read model" posture
  `OrdersProjectionsDbContext` already established.
- `EventStore.AppHost/AppHost.cs` gained two new resources,
  `vitals-flows`/`meridian-flows`, each a real `ProjectionHost
  <PendingTask>` worker pointed at `eventstore`'s Follow API and
  `devIdp`, sharing one physical `../pending-tasks.db` file with
  `eventstore` itself (the same relative-path convention already used
  standalone) so the cross-domain `myTasks` query actually sees both
  domains' tasks under a real orchestrated run, not just in isolated
  tests.

SqlServer host wiring remains genuinely open — `AppHost` only ever
targets one `Host.<Provider>` at a time (`ADR-001`, currently Postgres),
so it has no consumer forcing that provider's own equivalent wiring yet.

Full solution build clean; `EventStore.UnitTests` (86/86) and
`EventStore.IntegrationTests` (245/247, the 2 non-PendingTask failures

## Closed: `EventStore.Host.SqlServer` wiring for the flow engine (`ADR-101`)

The last open item from the punch list. A mechanical copy of the same
three changes already made twice (`EventStore.Host.Sqlite`,
`EventStore.Host.Postgres`): `EventStore.Flows` project reference,
`ConnectionStrings:PendingTasks` in `appsettings.json`, and the
`AddDbContext<PendingTasksDbContext>` call in `Program.cs` (always
SQLite, regardless of write-side provider). Verified by booting the real
host process against an intentionally-unreachable SQL Server connection
string: the DI container built cleanly through to `app.Run()`'s first
real database call, which failed with a genuine `SqlException` (no SQL
Server instance was stood up for this check) rather than a container-
build-time registration error — confirming the wiring itself is sound
without needing a full SQL Server Testcontainer/AppHost run. `08-build-
plan.md`'s item 57 marked Done (all three providers now carry this read
model); its own `TODO.md` item deleted. `EventStore.AppHost` still only
targets Postgres (`ADR-001`), so this is the one provider without a
live, AppHost-driven verification the way SQLite/Postgres both have —
noted honestly in the item's own Status text, not hidden.

## Added: cross-provider peer sync, proven real, and a configurable multi-provider Aspire topology (`ADR-102`)

Direct follow-up request, closing the exact gap the previous entry above
flagged: "get real, live Aspire-orchestrated dev/test environments for
SQL Server and SQLite too... an explicitly *configurable* database type...
a real cross-platform data-sync service if that's what it takes."
Investigated before building anything new: `ADR-033`'s peer-sync
mechanism (`PeerSyncClient`/`PeerSyncReceiver`) already moves events as
plain JSON over HTTP, provider-agnostic by construction — confirmed
directly in the code, not assumed. Nothing new needed to be invented;
this session exercises and proves that existing mechanism cross-provider
for the first time.

- `EventStore.AppHost` now runs a real three-node peer-sync mesh:
  `eventstore` (Postgres, unchanged), `eventstore-sqlite`
  (`EventStore.Host.Sqlite`, a local file), `eventstore-sqlserver`
  (`EventStore.Host.SqlServer`, a real container via Aspire's
  first-party `Aspire.Hosting.SqlServer`). `Topology:EnableSqlitePeer`/
  `EnableSqlServerPeer` config flags (default `true`) make the topology's
  own node roster genuinely configurable — orchestration-level, not a
  reversal of `ADR-001`'s per-process provider decision (each peer still
  hardcodes exactly one provider internally).
- `EventStore.Migrator` generalized to a `Database:Provider`-switched
  tool (`Postgres`/`SqlServer`/`Sqlite`) so all three peers get the same
  one-shot, ADR-076-compliant migration step, not just Postgres.
- New `tests/EventStore.IntegrationTests/ReplicationCrossProviderHttpTests.cs`
  — a real SQLite `WebApplicationFactory` and a real SQL Server one
  (backed by a genuine `MsSqlContainer`), proving an event published at
  one replicates to the other over real HTTP with `OriginId` preserved.
  Found and fixed two real, unrelated startup defects while building
  this: SQL Server's password-complexity policy rejected the AppHost's
  existing Postgres-shaped dev password outright, and this is the first
  test in the suite to boot the *full* real host (with `RouterWorker`/
  `WebhookOutboxPump`/`PeerSyncWorker` all genuinely running) against SQL
  Server rather than calling `EventStoreContext` directly — surfacing
  `ADR-095`'s own documented `master`-database Service Broker gap for
  the first time in that combination. Fixed by mirroring
  `WorkerWakeSignalSqlServerTests.cs`'s own already-established
  named-database workaround.
- **Live-verified against a real, fully orchestrated three-node mesh**
  (Docker): one event, published once against the real Postgres node,
  confirmed present — independently, by direct database inspection, not
  just from logs — in both the real SQLite peer's own file and the real
  SQL Server peer's own database, each with genuine `PeerSyncCursor` rows
  showing real, timestamped sync activity. The topology toggle was
  verified too: with both new peers disabled, only the Postgres
  container starts and the other two peers' ports never bind.
- Docs: new `docs/adrs/adr-102-cross-provider-peer-sync-and-multi-provider-topology.md`,
  indexed in `docs/07-adrs.md`; additive notes on `ADR-001` (orchestration-
  level configurability doesn't reverse its per-process decision),
  `ADR-033`, and `08-build-plan.md`'s "Sharding & Replication" item.

Full solution build clean; `EventStore.UnitTests` (86/86) and
`EventStore.IntegrationTests` (247/247, including the new cross-provider
test) pass.
