## ADR-009's revealOnDemand built directly, after re-reading the ADR closely

Direct request ("Yes," continuing "picking specific findings... to
resolve"). Re-reading `ADR-009`'s own Decision text (not just the audit's
summary of it) surfaced a real nuance that changed the risk assessment:
`revealOnDemand` is explicitly an **opt-in per-field annotation** — the
ADR's own words, "the general (non-`revealOnDemand`) masking wrapper is
unchanged... a field without `revealOnDemand` still returns
`{"value": ...}` directly to a claim-holder... exactly as originally
decided." Since zero fields in this codebase used `revealOnDemand`
before this fix (confirmed by the audit), building the missing branch
could not break any existing behavior — a materially lower-risk build
than "change how every masked field behaves for every claim holder,"
which is what the audit's own summary read like in isolation.

Built: `PayloadMasker.MaskLeafAsync` (`EventStore.Masking`) now checks
for a `revealOnDemand` sub-object when a claim holder would otherwise see
the real value; if present, computes a display mask by reusing
`PartialRevealMaskingStrategy` directly against that sub-object (exactly
as the ADR's own text specifies — "computed the same way
`PartialRevealMaskingStrategy` already computes its output... independent
of whatever `strategy` a non-claim-holder would otherwise see") rather
than returning the real value; `RevealFieldMutation.cs` (`EventStore.
GraphQL`) needed no changes at all — it already generically reads
`x-masking.requiredClaim` and returns the real value on the explicit
round trip, unaware of `revealOnDemand` either way, which is exactly
right. `MaskingSchemaValidator` gained a structural check that
`revealOnDemand`, when present, is an object.

New test: `MaskingScenarioAssertions.
ARevealOnDemandFieldStaysDisplayMaskedForAClaimHolderUntilRevealFieldIsCalled`,
run across all 3 providers — confirms a claim holder sees the
`revealOnDemand`-shaped display mask (not the real value) in the ordinary
Follow response, and a non-claim-holder is completely unaffected (still
the field's own ordinary `FixedValue`/etc. mask) — added as a new
scenario call inside each provider's existing `AllMaskingScenarios`
`[TestMethod]` (`EventStore.IntegrationTests` stays at 187
`[TestMethod]`s total, matching this repo's own convention that a new
item usually adds scenarios to an existing method rather than a new
method per scenario). Full SQLite regression subset re-run clean except
the one already-documented, pre-existing load flake
(`SubscribingOverRealHttpStreamsAMatchingEventAsSse`).

5 of the 12 re-audit findings are now fully resolved. 7 remain
(`ADR-036/043/048/055/057/065/080`).
