## Rejection behavior: adopted the targeted-rebuild refinement as the real Annotate default

Direct decision, resolving `docs/10-open-questions.md`'s row on which
document was authoritative: `docs/comparisons/authority-rejection-
behavior.md`'s own "annotate-only-plus-targeted-rebuild" refinement was
recommended but never actually built — `ADR-035`, `docs/data/
schema-registry.md`, and the feature doc's own Gherkin all still
described/tested the plain "leave the Entity Store exactly as it was"
shape. Direct reasoning that resolved which was correct: the Event Log
is the immutable record; the Entity Store is explicitly a derived,
recomputable cache — so it's not just safe but *correct* for a rejection
to trigger a real rebuild of that cache, never touching the Event Log.

Built: `RouterWorker.RebuildEntityFromAcceptedEventsAsync` (`EventStore.
Router`) — re-folds one entity's full event history from a blank slate,
including only events whose *current* `AuthorityStatus` is `accepted`
(re-evaluated fresh, not each event's status at its own original
processing time), reusing the same `SplitByConformance`/`EntityDataMerger`/
late-arrival-guard mechanics `FoldAsync` already uses, but deliberately
never reassigning `ConflictFlag`/`LateArrivalFlag` on the replayed source
events themselves — those stay a permanent record of what happened at
each event's own original processing time, not overwritten by a later
rebuild's own bookkeeping. Zero surviving accepted contributions removes
the Entity Store row entirely, matching `ADR-042`'s own "no accepted
events, no authoritative row" gate. `AuthorityDecisionResolver.
ProcessAsync`'s Annotate branch now calls this instead of doing nothing;
`RejectionBehavior.Compensate` is completely unaffected — it still emits
an explicit, visible compensating-patch event for domains that want that
shape. One real bug caught by the test suite, not by reading the code
back: the rebuild's own `AsNoTracking` query re-reads `AuthorityStatus`
from the database, which doesn't yet reflect this same `DbContext`'s
own not-yet-flushed `target.AuthorityStatus = "rejected"` change (`RunOnceAsync`
only calls `SaveChangesAsync` once, after the whole batch) — fixed by
flushing with `SaveChangesAsync` immediately before the rebuild query,
the same mid-batch-save pattern `AppendCompensatingPatchAsync`'s own
`EventAppender.AppendAsync` call already relies on.

Docs corrected in the same pass: `ADR-035` (struck-through + corrected
Decision bullet), `docs/data/schema-registry.md`'s `RejectionBehavior`
enum comment, `docs/features/non-authoritative-capture.md` (sequence
diagram + two Gherkin scenarios replacing the one whose own expected
outcome changed), `docs/comparisons/authority-rejection-behavior.md`

## `ADR-095`: a push-notification wake-up layer, proven on RouterWorker first

Direct decision, resolving `docs/10-open-questions.md`'s last remaining
row (that file is now empty). Scoped explicitly to `RouterWorker` only,
per direct choice between three offered scopes ("prove it on RouterWorker
first" vs. "wire all 6 workers" vs. something else) — the other five
background workers (`DerivationWorker`, `WebhookOutboxPump`,
`PeerSyncWorker`, `ChannelDerivationWorker`, `ExpectedResponseWatcher`)
still poll on a fixed interval alone, a named, mechanical follow-up, not
built this pass.

Built: a new shared project, `EventStore.WorkerWakeSignal`
(`IWorkerWakeSignal`: `NotifyAsync(topic, ct)` / `WaitForWakeAsync(topic,
maxWait, ct)`), plus a `WakeSignal` domain entity (`Topic` PK,
`LastSignaledAt`) migrated uniformly across all three providers. Three
real, provider-native implementations:
- **`SqliteWorkerWakeSignal`** — an in-process `Channel<T>` per topic
  (SQLite has no cross-process notification primitive at all), backed by
  the durable `WakeSignal` row so a worker that's never yet observed a
  wake since its own process started can still notice one that already
  happened, without waiting out a full poll interval on its first tick.
- **`PostgresWorkerWakeSignal`** — real `LISTEN`/`NOTIFY` via a dedicated,
  process-lifetime `NpgsqlConnection` per topic (`LISTEN` is
  session-scoped; a fresh connection per call could miss a `NOTIFY` in
  the gap). `NotifyAsync` uses `pg_notify(@topic, '')`, parameterized, on
  `EventStoreContext`'s own connection.
- **`SqlServerWorkerWakeSignal`** — real Service Broker: a message type/
  contract/queue/service created by a new migration
  (`AddWorkerWakeSignal`), `WAITFOR (RECEIVE ...), TIMEOUT n` for the
  wait, `BEGIN DIALOG`/`SEND`/`END CONVERSATION` for the notify.
  Deliberately without internal/external activation — direct decision:
  `RouterWorker`'s own C# `WAITFOR` loop IS the active listener the whole
  time it runs, so activation would just race it for the same messages;
  external activation is named as the real mechanism for a genuinely
  separate, non-polling consumer, not needed here since every consumer in
  this build already is a live worker.

`RouterWorker.ExecuteAsync` now calls `WaitForWakeAsync("router",
PollInterval, ct)` in place of an unconditional `Task.Delay` between
ticks that found nothing; `PublishService.PublishAsync` calls
`NotifyAsync("router", ct)` immediately after `EventAppender.AppendAsync`
succeeds (a new optional constructor param, `null` for every pre-existing
test construction site, matching this class's own established
optional-dependency convention). The poll loop itself is completely
unchanged and stays the sole correctness guarantee on every provider —
a missed/dropped signal just means a worker waits its old, already-safe
full interval, never worse than before this ADR.

Three real bugs found only by actually running this, not by design review:
1. **`SqliteWorkerWakeSignal`'s static state, keyed by topic alone, let
   totally unrelated `WebApplicationFactory`-hosted test processes cross-
   talk through the same in-memory `Channel`** — this suite's own MSTest
   32-way parallelism runs many independent Hosts (each its own SQLite
   file) in one shared test process, and a topic-only key let one Host's
   publisher wake a DIFFERENT Host's `RouterWorker`, occasionally
   "stealing" a wake meant for the real target and leaving it to fall
   back to its full poll interval — a real, load-dependent flake,
   confirmed by running the full SQLite suite repeatedly, not assumed.
   Fixed by keying on `(connection string, topic)` instead; changes
   nothing about the real single-process, single-connection-string
   production shape this class exists for.
2. **One existing test's own timing assumption broke once `RouterWorker`
   got faster**: `BatchPublishHttpSqliteTests.
   ASchemaInvalidButNotMalformedEventInsideABatchStillPersistsWithAnAdvisorySchemaStatus`
   asserted `Status == "received"` immediately after a publish, relying
   on `RouterWorker` not having processed it yet — now sometimes already
   "applied." Fixed by polling for the real condition it actually cared
   about (`SchemaStatus` set) instead of racing an implicit timing
   assumption; audited the rest of the suite for the same pattern (only
   this one test had it, confirmed by grep across every `Http*Tests.cs`
   file).
3. **`ALTER DATABASE ... SET ENABLE_BROKER` cannot target the `master`
   system database, and every pre-existing `*SqlServerTests.cs` file
   migrates against Testcontainers' own default `master` connection** —
   the established convention long before this ADR, never designed
   around. A hard migration failure here broke roughly two dozen
   pre-existing SQL Server test classes across the whole suite, confirmed
   by actually running it, not assumed from the DDL alone. Fixed by
   wrapping the `ENABLE_BROKER` attempt in `TRY`/`CATCH` and gating the
   `CREATE MESSAGE TYPE`/`CONTRACT`/`QUEUE`/`SERVICE` statements on
   `is_broker_enabled` actually being true, so a `master`-connected
   migration now just skips creating Service Broker objects entirely.
   `WorkerWakeSignalSqlServerTests.cs` creates and connects to a real,
   named, non-system database instead, specifically so Broker really is
   active where the mechanism is actually exercised end to end.

New tests: `WorkerWakeSignalSqliteTests.cs` (3 tests, direct), the fixed
`WorkerWakeSignalPostgresTests.cs`/`WorkerWakeSignalSqlServerTests.cs`
(Testcontainers-backed, proving both halves — a `NotifyAsync` during an
active wait wakes it well before its own timeout, and a wait with
genuinely nothing to receive still runs out its full timeout). Verified:
full `dotnet build` clean; full Postgres suite (25 tests) and a full
SQL Server sweep (in batches, to avoid this host's own already-documented
`fs.aio-max-nr` container-exhaustion ceiling under back-to-back
`MsSqlContainer` starts) both clean; SQLite regression suite re-run
repeatedly (0-2 failures per run, matching this project's own established

`TODO.md`'s own investigation note named the next concrete thing to try:
`IRequestExecutorManager.EvictExecutor(schemaName)` alongside
`ISchemaChangeNotifier.NotifyChanged()`, since `TypesChanged` alone

- **It's unsafe to ship as-is.** Run alongside this suite's own

  its concrete failure mode are recorded in both the class's own code
  comment and `TODO.md`, so this specific dead end doesn't get re-walked

## Fixed `EventStore.AppHost`'s Postgres database-creation race

`TODO.md` had this tracked as a confirmed, reproducible gap: Aspire's
`AddDatabase("Postgres")` creates the named database asynchronously off
the Postgres server resource's own `ResourceReadyEvent`
(confirmed against Aspire's own hosting docs), and `WaitFor(db)` waits
for the database *resource* to be registered, not for that `CREATE
DATABASE` to have actually committed — a real, reproducible race
`EventStore.Migrator`/`EventStore.Host.Postgres` could both lose,
surfacing as `PostgresException: 3D000: database "Postgres" does not
exist` with no retry.

Fixed with `EnableRetryOnFailure(maxRetryCount: 10, maxRetryDelay:
TimeSpan.FromSeconds(2), errorCodesToAdd: ["3D000"])` on both
projects' `UseNpgsql` registrations — `3D000` (Postgres's own SQLSTATE
for `invalid_catalog_name`) added explicitly since it isn't one of
Npgsql's own built-in transient error codes (a real "database does not
exist" is normally permanent; it's only transient here because of
Aspire's own async creation timing).

**Verified against real infrastructure, not just compiled**: started a
bare Postgres 18 container directly (no Aspire involved, to isolate the
mechanism itself), scheduled a deliberately-delayed `CREATE DATABASE`
in the background, and raced an ordinary EF Core `DbSet` query (the
exact call shape both real projects use) against it:
- Without the fix: fails instantly (~0.4s) with the exact `3D000` error
  from the bug report, no recovery.
- With the fix: retries automatically (visible per-attempt logging
  confirmed 7 attempts with increasing backoff) and succeeds the moment
  the delayed `CREATE DATABASE` lands.

**Two real EF Core nuances found only by testing this directly, not
assumed from the API docs**: `Database.CanConnectAsync()` swallows the
connection exception and returns `false` — it never invokes the
configured retry execution strategy at all. `Database.ExecuteSqlRawAsync`
also does not auto-wrap itself in the strategy (a manual
`CreateExecutionStrategy().ExecuteAsync(...)` around it was needed to
observe retries). An ordinary `DbSet` LINQ query (`CountAsync`, and by
extension `SaveChangesAsync`/`MigrateAsync`) *does* auto-wrap itself —
confirmed by the same test — which is what actually makes
`EnableRetryOnFailure` effective for `EventStore.Host.Postgres`'s and
`EventStore.Migrator`'s real code paths, both of which use ordinary
`DbSet`/`DbContext` operations, never raw SQL or `CanConnectAsync`.

Not re-verified via a full live `aspire run` this pass (the fuller
orchestration graph's simulators never exit, making a bounded,
cleanly-torn-down check impractical here) — the specific race named in
`TODO.md` is fixed and directly verified against the real mechanism;
`docs/08-build-plan.md`'s own note says so explicitly rather than
implying a full end-to-end round trip was re-run. `TODO.md`'s item
removed. Full solution build clean.

## Subscription resume cursor: server-side half built, two real bugs found and fixed along the way

`TODO.md`'s "`client-web` opens every Subscription hardcoded `mode:
TAIL`, no persisted resume cursor" gap needed a server-side prerequisite
first: a way for a delivered event to tell the client what cursor value
to reconnect with. Built:

- `FollowSubscriptionTypeModule.BuildEnvelopeFlagFields` gained a new
  `sequenceNumber` field on every dynamic Subscription payload type,
  String-typed (the common GraphQL int64-as-string convention — a raw
  64-bit sequence number isn't safely representable in JS's `Number`
  past 2^53).
- `GraphQlHttpSqliteTests.
  ReconnectingWithReplayFromLastSeenSkipsAlreadyDeliveredEventsAndPicksUpTheNext`
  (new) proves the actual reconnect contract end to end: a first
  connection (`mode: REPLAY, fromSequenceNumber: 0`) reads one event,
  disconnects, a second event is published, and a second connection
  reconnecting with `mode: REPLAY, fromSequenceNumber: <first's own
  sequenceNumber>` skips the first event and delivers only the second.

**Getting this test right surfaced three real, unrelated bugs, not one**:

1. **A test-authoring off-by-one, not a server bug.**
   `EventTailReader.TailAsync`'s own predicate is `SequenceNumber >
   lastSeen` — `fromSequenceNumber` is the *last-seen* value, inclusive,
   and the reader excludes it itself. An early version of this test
   reconnected with `fromSequenceNumber: first.SequenceNumber + 1`,
   which skipped the just-published second event too (its own sequence
   number equaled `first + 1` exactly) and hung waiting for a THIRD event
   that never came. This looked, for a long time, like a serious
   HotChocolate defect (see point 3) before the actual arithmetic was
   checked directly against a real row in the database.
2. **A real, confirmed cross-application event leak**, previously
   documented in `TODO.md` as found-but-not-yet-fixed:
   `EventTailReader.TailAsync` filtered `db.Events` by `EventType` name
   alone, with no `AppId` filter, even though `EventTypeDefinition`'s own
   primary key `(AppId, Name, Version)` explicitly allows two different
   AppIds to share a name. Fixed: `TailAsync` now takes an explicit
   `appId` parameter and filters on it directly; both call sites
   (`FollowSubscriptionTypeModule.SubscribeAsync`,
   `FollowService.ConnectAsync`) already had a real AppId in scope to
   pass. The two schema-version lookups `TailAsync` itself calls
   (`SchemaRegistryService.GetActiveDefinitionByNameAsync`/
   `GetVersionsByNameAsync`) had the identical bare-name gap — a name
   collision could resolve upcast/downcast against the WRONG AppId's
   schema, a shape-corruption risk on top of the confidentiality one.
   Fixed the same way: `GetActiveDefinitionByNameAsync` became
   AppId-scoped and renamed `GetActiveDefinitionAsync`;
   `GetVersionsByNameAsync` was removed outright once both its callers
   (`TailAsync`, `FollowService.ConnectAsync`) had a real AppId to pass
   to the pre-existing AppId-scoped `GetVersionsAsync` instead — no
   caller needed the bare-name version anymore, so it wasn't kept around
   as dead code.
3. **A misdiagnosis, now corrected in code comments.** Before finding
   (1) and (2), an earlier version of the `sequenceNumber` field returned
   a raw `long` typed `"Long"` (HotChocolate's built-in scalar), and the
   whole SSE stream appeared to hang indefinitely with no error surfaced
   — extensive layer-by-layer elimination (direct DB queries, manually
   driving `TailAsync`'s own enumerator, diagnostic `GraphQLException`
   throws carrying live variable state) seemed to rule out everything
   except the scalar itself, and the field was shipped as `String`
   instead on that theory. Revisiting it after fixing (1) and (2): the
   *actual* cause was almost certainly (1) compounding with (2) and with
   this class's own already-documented hot-reload gap (a type registered
   after the schema's first lazy build never gets a subscription field,
   confirmed exactly reproducing this test's own instant-failure mode
   when it wasn't the first test to touch the GraphQL endpoint in this
   class's shared, static Host — fixed by seeding the test's own AppId
   in `ClassInit`, the same pattern the class already uses for its other
   seeded AppId). The `String` type is kept regardless — it's the more
   correct choice on its own merits — but the code comment overclaiming
   a "confirmed HotChocolate output-scalar bug" has been corrected to
   describe what was actually found.

This class's tests also gained `[DoNotParallelize]`: several of its
methods (now including the new resume-cursor one) subscribe against the
class's one shared, static Host, and MSTest's method-level parallelism
made the same class of interference documented for tasks #113/#119
possible here too, confirmed by the new test flaking only when run
alongside the rest of the class, not alone.

Verified (server-side): the fixed test, the rest of
`GraphQlHttpSqliteTests` (11 tests), and the broader Follow/GraphQL/
masking/upcasting/lineage set (45 tests) all pass; the full non-SqlServer
integration suite (196 tests) passes. Full solution build clean.

**Client side, same pass**: `useEntityViewActions.ts`'s `subscribeToEntity`
