## Hash-chained tamper evidence (`ADR-019`)

Code was already in place from the prior session
([`EventChainHash.cs`](../../src/EventStore.Domain/EventLog/EventChainHash.cs),
[`PublishService.cs`](../../src/EventStore.Inbox/PublishService.cs),
[`ChainVerificationService.cs`](../../src/EventStore.Inbox/ChainVerificationService.cs))
but had **no test coverage at all** — this pass wrote it
([`HashChainScenarioAssertions.cs`](../../tests/EventStore.IntegrationTests/HashChainScenarioAssertions.cs))
and, while doing so, found a real gap against this item's own exit
criterion ("deliberately corrupting one historical `Payload` ... is
detected by the verification endpoint"): `ChainVerificationService`
recomputed the chain from the **stored** `PayloadHash` column, never from
`Payload` itself — a direct-database edit to `Payload` alone (leaving
`PayloadHash` untouched) would have gone completely undetected, silently
failing the one scenario this item's exit criteria explicitly names.
Fixed by extracting the payload-hash formula into a shared
[`EventPayloadHash.cs`](../../src/EventStore.Domain/EventLog/EventPayloadHash.cs)
(`PublishService` now calls it too, instead of duplicating it) and having
[`ChainVerificationService.cs`](../../src/EventStore.Inbox/ChainVerificationService.cs)
re-derive `PayloadHash` from each row's own `EventType`/`Payload`/parent
links before folding it into the chain — corrupting `Payload` alone now
correctly diverges the chain at exactly that `SequenceNumber`, with every
earlier event still verifying clean.

## Publish-time upcast validation + `EventUpcastFailed` dead-letter (`ADR-020`)

Built from scratch this pass:
- [`PublishService.cs`](../../src/EventStore.Inbox/PublishService.cs) —
  when `schemaVersion` is behind the type's active version,
  `CheckUpcastCompatibilityAsync` runs the caller's real payload through
  `UpcastChain` up to the active version, **then validates the result
  against the active schema** (`UpcastChain.Apply` alone only proves the
  expressions ran, not that their output is usable). On success: stored
  exactly as declared, unchanged from before this item. On failure:
  `PublishUpcastFailedAsync` stores the reserved `EventUpcastFailed` type
  in the original event's place (original `eventType`/`schemaVersion`/
  payload verbatim, plus which hop failed and why), and `PublishResult.
  Created` gained an `EventType` field so the response can name
  `EventUpcastFailed` as what was actually stored, not the caller's own
  type — a new field, not a new result case, since "stored some event
  successfully" is still the right response shape either way.
  `SchemaRegistryService.GetVersionsAsync` (AppId-scoped, unlike the
  existing bare-name `GetVersionsByNameAsync` Follow uses) was added to
  fetch the version range needed.
- [`PublishResult.cs`](../../src/EventStore.Inbox/PublishResult.cs),
  [`PublishEndpoints.cs`](../../src/EventStore.Inbox/PublishEndpoints.cs) —
  `eventType` added to the `201 Created` response body.
- Tests: two new scenarios in
  [`PublishScenarioAssertions.cs`](../../tests/EventStore.IntegrationTests/PublishScenarioAssertions.cs)
  (compatible upcast stores unchanged; failing upcast dead-letters as
  `EventUpcastFailed`). One **pre-existing, never-before-exercised**
  scenario broke under the new check and needed fixing, not working
  around: `PublishingValidatesAgainstTheDeclaredVersionNotWhicheverIsActive`
  registered a v2 with `UpcastFromPrevious: null` while adding a new
  *required* field — exactly the incompatible-upcast shape this item now
  correctly dead-letters, which masked the scenario's own actual assertion
  (declared-version, not active-version, validation). Fixed by giving that
  v2 a real mapping that actually supplies the new field, restoring the
  original assertion's intent.

**Accepted v1 limitation, not a gap**: a retry of a request whose upcast
still fails dead-letters again each time (a fresh `EventId`, not
deduplicated against the earlier `EventUpcastFailed` row) — `ADR-020`
doesn't specify idempotent-retry semantics for the dead-letter path
itself, and deduplicating it would need either reusing the caller's
`EventId` for a *different* stored type (breaking the existing
`ComputeHash`-based replay check, which hashes the original content) or a
second lookup mechanism this item's exit criteria never asked for. Left
as documented, repeatable behavior (see the comment on
`PublishUpcastFailedAsync` in
[`PublishService.cs`](../../src/EventStore.Inbox/PublishService.cs)),
matching `ADR-020`'s own "no proactive check, only discovered when
actually hit" posture rather than over-building this v1.

## DPoP-bound access tokens (`ADR-017`)

Built from scratch — the largest, most security-sensitive part of this
item. New project
[`EventStore.Dpop`](../../src/EventStore.Dpop/EventStore.Dpop.csproj)
(EC P-256 only, no algorithm agility asked for), shared by
`EventStore.DevIdp` (token issuance) and `EventStore.Host.Core` (API
validation) rather than duplicated:
- [`DpopKeyPair.cs`](../../src/EventStore.Dpop/DpopKeyPair.cs) — key-pair
  generation + signed proof-JWT creation (`typ: dpop+jwt`, embedded
  `jwk`, `htm`/`htu`/`iat`/`jti`, optional `ath`).
- [`JwkThumbprint.cs`](../../src/EventStore.Dpop/JwkThumbprint.cs) — RFC
  7638, the `jkt` value embedded in issued tokens and recomputed from
  each proof to confirm the same key.
- [`DpopProofValidator.cs`](../../src/EventStore.Dpop/DpopProofValidator.cs) —
  self-contained validation (RFC 9449 §4.3: the proof's own embedded
  `jwk` is both what's checked against and what verifies its signature):
  `typ`, signature, `htm`/`htu`, `iat` freshness (±60s), `jti` replay
  (`DpopReplayCache.cs`), and `ath` when a token is being presented.
- [`DevIdpSeeder.cs`](../../src/EventStore.DevIdp/DevIdpSeeder.cs) —
  generates one key pair per seeded client, exposed via
  `GetClientKeyPair(clientId)`. No separate client *process* exists in
  this repo for `publisher-client`/`follower-client`/`operator-client` —
  every one of them is only ever driven from test code — so this seeder
  plays the "client generates its own key" role from `ADR-017`'s own text
  for those three; the token endpoint itself never reads this map, it
  validates whatever proof is actually submitted, exactly like a real
  deployment would.
- [`Program.cs`](../../src/EventStore.DevIdp/Program.cs) — `/connect/token`
  now requires and validates a `DPoP` header proof (RFC 9449 §5's own
  OAuth2 error shape on failure — `400`, `invalid_dpop_proof` — not RFC
  9457 Problem Details, which is this project's contract for the
  `EventStore.Host.<Provider>` API surface, not this OAuth2 endpoint) and
  embeds the result's thumbprint as a flat `cnf.jkt` claim on the issued
  token (`ADR-017`'s own phrasing — a flat claim, not RFC 9449's nested
  `cnf: {jkt: ...}` JSON-object shape).
- [`DpopValidationMiddleware.cs`](../../src/EventStore.Host.Core/DpopValidationMiddleware.cs),
  wired into
  [`HostCoreExtensions.cs`](../../src/EventStore.Host.Core/HostCoreExtensions.cs)
  between `UseAuthentication()` and `UseAuthorization()` — a request with
  no bearer token is left alone (the existing JwtBearer challenge already
  401s it, unrelated to DPoP); a request with a validated bearer but a
  missing/invalid/mismatched-key DPoP proof is rejected `401`
  (`dpop-proof-invalid`, `reason` extension — `ADR-013`'s own table row
  for exactly this case).
- [`FollowClient.cs`](../../src/EventStore.Projections.Host/FollowClient.cs) —
  `projections-client` is the **one** seeded client with real, running
  production code in this repo (`ProjectionHost`'s own Follow consumer),
  so it generates and holds its own `DpopKeyPair` for real, exactly as
  `ADR-017` describes, rather than borrowing the seeder's simulated one.
- Tests:
  [`AuthScenarioAssertions.cs`](../../tests/EventStore.IntegrationTests/AuthScenarioAssertions.cs) —
  every token request and every API call now carries a real, freshly
  generated DPoP proof; three new scenarios, matching
  [`docs/features/dpop-and-tamper-evidence.md`](../features/dpop-and-tamper-evidence.md)'s
  own Gherkin one-for-one: `ARequestWithAValidBearerTokenButNoDpopProofIs
  RejectedWith401`, `ARequestWithADpopProofSignedByADifferentKeyIsRejected
  With401` (the actual value this ADR buys: a leaked bearer token alone is
  useless without the private key it's bound to), and
  `ReplayingAnAlreadyUsedDpopProofIsRejectedWith401` (the same proof's exact
  bytes, same `jti`, reused on a second request).
  [`ProjectionsScenarioAssertions.cs`](../../tests/EventStore.IntegrationTests/ProjectionsScenarioAssertions.cs)
  updated to the same `(token, key)`-pair pattern via a shared, now-public
  `AuthScenarioAssertions.AttachAuth`.

### Real bugs found only by running the real HTTP round trip, not by reading the code back

1. **Header-claim serialization**: `AdditionalHeaderClaims["jwk"] =
   PublicJwk` (the `EcJwk` record) threw `IDX11025` — the JWT header
   writer only serializes a fixed set of primitive shapes, not an
   arbitrary POCO. Fixed by passing a plain `Dictionary<string, object>`
   instead (see the comment in
   [`DpopKeyPair.cs`](../../src/EventStore.Dpop/DpopKeyPair.cs)).
2. **Parallel-test database race**: `EventStore.DevIdp`'s EF Core
   InMemory database used a fixed name (`"EventStore.DevIdp"`) — EF
   Core's InMemory provider keys databases by name **process-wide**, not
   per `WebApplicationFactory` instance, so `AuthSqliteTests` and
   `ProjectionsSqliteTests` running concurrently (MSTest's default
   method-level parallelization) silently shared one store and raced on
   `DevIdpSeeder`'s seeding (`"An application with the same client
   identifier already exists"`).
3. **Self-inflicted regression fixing bug 2**: the first fix
   (`UseInMemoryDatabase($"EventStore.DevIdp-{Guid.NewGuid():N}")`) put
   the `Guid.NewGuid()` call **inside** the `AddDbContext` options
   delegate — which EF Core re-invokes on every scoped `DbContext`
   instantiation, i.e. on every single HTTP request, handing each request
   its own fresh, empty, unseeded database (`invalid_client` on the very
   first token request in a freshly-fixed test run). Fixed by computing
   the name once, outside the delegate (see
   [`Program.cs`](../../src/EventStore.DevIdp/Program.cs)'s comment) —
   caught only by re-running the full suite after the first fix, not
   assumed correct from the diff.

## Two real design gaps found and fixed while wiring `RouterWorker`, both while writing tests, not by reading the code back

1. **`StoredEvent` carried no `AppId`.** `docs/10-open-questions.md`'s
   former row 1 already named this exact ambiguity for read-side claim
   checks, and predicted its own resolution: "until either `EntityId`
   populates... or a dedicated fix lands." `EntityId` populating is
   exactly this item's own job, and constructing it correctly turned out
   to *need* a real `AppId` — the bare-name/tie-broken-by-`AppId`-ordering
   workaround Follow/Lineage already use is fine for *visibility* (worst
   case: a caller sees or doesn't see something) but actively corrupts
   *identity* when two different `AppId`s register the same event-type
   name (exactly what the row's own text warned the DB schema permits).
   Fixed by adding [`StoredEvent.AppId`](../../src/EventStore.Domain/EventLog/StoredEvent.cs)
   (set by `PublishService` from the request's own `AppId`), migrated
   across all 3 providers, and used directly by `RouterWorker` instead of
   any bare-name lookup. The former open-questions row is deleted (the
   fork is genuinely decided now); a residual, scoped follow-up — rewiring
   Follow/Lineage's *own* bare-name claim lookups to use this same field
   directly instead of their tie-break — is tracked in `TODO.md`, not
   silently dropped.
2. **`EventTypeDefinition` had no field grouping multiple event types
   under one logical entity.** `OrderPlaced` and `OrderShipped` are two
   different event types that both patch the same `Order` entity — first
   attempt constructed `EntityId` from each event's own `EventType`
   directly, which gave `OrderPlaced` and `OrderShipped` events for the
   *same* order two different `EntityId`s entirely (caught by
   `PublishingASecondEventForTheSameEntityIdUpdatesTheRowAndIncrementsVersion`
   asserting `Version 2` and getting `1` — the second event silently
   folded into a *different*, newly-created row instead). Fixed by adding
   [`EventTypeDefinition.EntityType`](../../src/EventStore.Domain/SchemaRegistry/EventTypeDefinition.cs)
   (defaults to the type's own normalized name — a genuinely *safe*
   default, unlike `EntityIdField`/`ChangeKind`'s "no safe default"
   posture, since a type trivially patches "itself" unless told to share),
   migrated across all 3 providers, documented in
   `docs/data/schema-registry.md`.

**A real correctness bug found only by running the full suite, not by
reading the code back**: `EventTailReader` originally queried
`db.Events.Where(e => e.EventType == eventTypeName && ...)` with no
`EventKind` filter at all, so once a materialization existed it was
delivered over Follow/SSE as an independent new event — double-delivering
one logical fact. This stayed invisible through every scenario this item's
own tests constructed (each registers exactly one v1-to-v2 pair once), and
only surfaced when the full suite ran: `ProjectionsSqliteTests` — a test
this item never touched — calls its own `RegisterTheFourOrderEventTypesAsync`
helper at the top of every scenario in that file, with the byte-identical
schema each time; `SchemaRegistryService.RegisterAsync` unconditionally
bumps the version on every call regardless of whether the schema actually
changed, so by the sixth scenario those four event types were sitting at
`Version` 6+, `IsActive`, still with no real `UpcastFromPrevious`. That's
exactly `ReconcileBacklogAsync`'s trigger condition (`IsActive && Version >
1`) — for the first time in the whole suite, Trigger 2 fired for real,
walked every historical event for orders `o-1` through `o-6` (each hop's
`UpcastFromPrevious` being empty just passes the payload through
unchanged, so every materialization trivially succeeded), and
`IncrementalResumeAfterDowntimeDeliversNoGapAndNoDuplicate` started
observing 2 delivered events where it expected 1. `ADR-027`'s own
Consequences already named the fix, unbuilt until now: Follow's default is
"consuming only originals and always upcasting live remains equally
correct" — serving a materialization instead is an optional, opt-in
optimization for other readers, never something the live tail should do
unprompted. Fixed by adding `e.EventKind == EventKind.Original` to
`EventTailReader`'s own query
([`EventTailReader.cs`](../../src/EventStore.Follow.Api/EventTailReader.cs)) —
confirmed by re-running the full suite twice in a row afterward, clean
both times.

## Downcast (`ADR-028`)

- [`DowncastChain.cs`](../../src/EventStore.Upcasting/DowncastChain.cs) —
  mirrors `UpcastChain`'s shape exactly, walking backward (`fromVersion`
  down to `toVersion`), but with no safe pass-through: a hop with no
  registered `DowncastToPrevious` is a hard `UpcastOutcome.Failed`, per
  this ADR's own "no guessing" stance (unlike upcasting's "no upcaster
  registered — pass through unchanged").
- [`FollowRequest.cs`](../../src/EventStore.Follow.Api/FollowRequest.cs)
  gained `AsOfSchemaVersion` — GraphQL doesn't exist at this build stage,
  so this is Follow's own SSE-surface translation of the doc's literal
  transport, the same translation every prior item has made.
- [`FollowService.cs`](../../src/EventStore.Follow.Api/FollowService.cs) —
  validates at connect time, before the tail loop ever starts: every hop
  between the requested version and the active one must have a registered
  `DowncastToPrevious`, or the request fails `ValidationFailed` (400)
  immediately, matching the Gherkin's "the request should fail with a 400"
  rather than discovering the gap mid-stream.
- [`EventTailReader.cs`](../../src/EventStore.Follow.Api/EventTailReader.cs) —
  applies `DowncastChain` after `UpcastChain` (an event can need upcasting
  to the active version, then downcasting again to the caller's requested
  older one, in the same pass), and masks against the requested version's
  schema, not the active one — a downcasted payload's field names belong
  to the old shape, so masking must check the old shape's own `x-masking`
  annotations, not the active version's.

## `ADR-053`'s second engine: `Jsonata.Net.Native`

[`JsonataUpcastExpressionEvaluator.cs`](../../src/EventStore.Upcasting/JsonataUpcastExpressionEvaluator.cs) —
`Jsonata.Net.Native` has its own JSON DOM
(`Jsonata.Net.Native.Json.JToken`), unrelated to `System.Text.Json`, so
rather than hand-writing a CLR-object bridge the way
`CelUpcastExpressionEvaluator` does for Cel.NET's variable bindings, this
implementation round-trips through the JSON text form — simpler, and
equally correct since `JsonataQuery.Eval` only ever needs a `JToken` in
and a `JToken` out. The harder part: making the same registered
`UpcastFromPrevious` string genuinely evaluate identically under both
engines, not just produce visually similar output for one hand-picked
example. CEL's own evaluator binds the source payload to a variable named
`event` (`Decls.NewVar("event", Decls.Dyn)`), so expressions read
`event.Amount`; JSONata has no equivalent concept — its input is the
context itself, so a bare payload would need `Amount` with no prefix at
all, which would make the registered expression text engine-specific
despite `ADR-053`'s own "engine-agnostic text" framing. Fixed by wrapping
the source payload under a synthetic top-level `"event"` key
(`{ "event": <payload> }`) before evaluating — `event.Amount` then
resolves as an ordinary JSONata path segment, identically to CEL's own
variable binding, for the exact same source text.
[`UpcastExpressionEvaluatorTests.cs`](../../tests/EventStore.IntegrationTests/UpcastExpressionEvaluatorTests.cs)
proves this directly: the same `"event.Amount as Amount, 'Unknown' as
Status"` string run through both evaluators produces byte-identical JSON
output, for both a single-hop and a two-hop chain, plus a JSONata-only
`$sum()` array-aggregation test (`ADR-053`'s own stated reason CEL can't
cover this case) and a compile-rejection test for both engines.

## New `EventStore.Streaming` project

- [`ChannelRegistryService.cs`](../../src/EventStore.Streaming/ChannelRegistryService.cs) —
  registration (`PUT /telemetry/channels/{channelId}`); deliberately no
  version history the way `EventTypeDefinition` has — a channel's declared
  shape doesn't evolve the way a payload schema does.
- [`TelemetrySampleWriter.cs`](../../src/EventStore.Streaming/TelemetrySampleWriter.cs) —
  batch ingestion (`POST /telemetry/{channelId}/samples`), both the
  fixed-rate (`startTimestamp`+`sampleIntervalMicros`+`values[]`) and
  irregular (`samples: [{timestamp, value}]`) shapes. `ADR-029`'s high-
  water-mark mechanism reused per-channel for `LateArrivalFlag` — a late
  sample is still written, never dropped, never reordered, and never
  moves the mark backward. Slow-upload detection compares the gap since
  the channel's own `LastBatchReceivedAt` against `SampleIntervalMicros`
  (its `ExpectedInterArrivalInterval`) x a configurable multiplier
  (`TelemetryIngestOptions.LagThresholdMultiplier`, default 3.0);
  exceeding it publishes a reserved, lazily-registered `ChannelLagDetected`
  event through the completely ordinary `PublishService.PublishAsync`
  path (unlike `ADR-027`'s `UpcastMaterializer`, there's no claims-bypass
  concern here — `ChannelLagDetected` declares no `RequiredClaims`).
- [`TelemetryTailReader.cs`](../../src/EventStore.Streaming/TelemetryTailReader.cs) —
  `ADR-010`'s tail/replay shape reused for `TelemetrySample` (`GET
  /telemetry/{channelId}/samples?mode=&fromTimestamp=`), plus `ADR-081`'s
  `ThreadId`-grouped session view (`GET /telemetry/sessions/{threadId}/
  samples`) presenting every channel sharing one `ThreadId` as a single
  merged stream, not N unrelated ones. Applies `RedactedRange` substitution
  at read time (never materialized) via the resolver below, plus the
  mandatory sideband existence flag (`TelemetrySampleView.
  RedactionAppliedFlag`) — structurally the same shape `LateArrivalFlag`
  already uses.
- [`IStreamRedactionStrategy.cs`](../../src/EventStore.Streaming/IStreamRedactionStrategy.cs) +
  [`ZeroFillStrategy.cs`](../../src/EventStore.Streaming/ZeroFillStrategy.cs)/
  [`ToneStrategy.cs`](../../src/EventStore.Streaming/ToneStrategy.cs)/
  [`BlankFrameStrategy.cs`](../../src/EventStore.Streaming/BlankFrameStrategy.cs) —
  `ADR-052`'s `ContentKind`-appropriate defaults, honestly scoped: with
  zero codec knowledge, `Tone`/`BlankFrame` substitute a fixed, distinctive
  byte pattern rather than a real decoded tone/frame, documented as such
  in each class's own comment.
- [`PartialRevealStreamRedactionStrategy.cs`](../../src/EventStore.Streaming/PartialRevealStreamRedactionStrategy.cs) —
  genuinely reuses `PartialRevealMaskingStrategy`'s reveal computation (not
  a second implementation) via a UTF-8 decode/re-encode round trip, since
  that strategy's own shape operates on `JsonNode`, not raw bytes.
- [`StreamRedactionResolver.cs`](../../src/EventStore.Streaming/StreamRedactionResolver.cs) —
  resolves the concrete keyed strategy from `(RedactedRange.Strategy,
  TelemetryChannel.ContentKind, MimeType)` — `"Default"` doesn't name one
  fixed class the way `IPayloadMasker`'s config does; it means "whichever
  substitution `ADR-052` designates for this channel's own shape."
- [`ChannelDerivationWorker.cs`](../../src/EventStore.Streaming/ChannelDerivationWorker.cs) —
  the `ADR-007`/`ADR-015`/`ADR-027` "internal follower" shape, applied to
  telemetry: tails a `Derived` channel's source(s), applies the transform,
  appends through the same ingestion path any other writer uses. Only
  `Resample` is implemented (decimation — keep the last source sample per
  target-rate bucket); `Filter`/`Aggregate`/`Transcode` are accepted values
  the worker takes no action for, flagged explicitly in `08-build-plan.md`'s
  own section rather than silently no-opped without a trace. Progress is
  tracked via the derived channel's own `LastAppliedLogicalTime` — the
  same field ingestion already maintains, no new checkpoint shape needed.
- [`MediaFragmentUri.cs`](../../src/EventStore.Streaming/MediaFragmentUri.cs)/

  the W3C Media Fragments URI temporal syntax (`#t=10,20`), resolved
  against a channel's own earliest sample as the time-zero reference,
  returning the interconvertible `TelemetryPointerEntry` shape directly.
  Exposed as a plain service, not an HTTP endpoint — a URI *fragment* is
  never sent to a server by a browser, so there is nothing for an endpoint

- [`StreamingEndpoints.cs`](../../src/EventStore.Streaming/StreamingEndpoints.cs) —
  one GET route dual-modes by `Range` header presence, ordinary HTTP
  conditional-request semantics: with it, `Results.Bytes(...,

  range playback over the channel's concatenated chunk bytes (RFC 7233);
  without it, the live JSON/SSE tail/replay stream, matching
  `FollowEndpoints`'s own SSE-writing shape exactly.

New `telemetry:ingest`/`telemetry:read` auth policies/scopes
(`HostCoreExtensions.cs`, `DevIdp/Program.cs`) and a seeded

## Two real bugs found only by running the tests, not by reading the code back

**SQLite's EF provider cannot translate a `DateTimeOffset` relational
comparison (`>`/`<`), a `MIN`/`MAX` aggregate, or an `ORDER BY`** — the
exact same class of gap already found once before, for `PendingJoinState`'s
TTL sweep ("Derived/Materialized Event Types"). This time it hit three
separate spots, each caught by an actual failing test run, not inspection:
`TelemetryTailReader`'s own cursor/poll queries, `MediaFragmentResolver`'s
earliest-sample lookup, and `StreamingEndpoints`'s Range-request byte-
concatenation ordering. Fixed identically each time — filter on the
translatable column (`ChannelId`) in the query, then compare/aggregate/
order the results client-side.

**A real DI wiring bug, not SQLite-specific — just first surfaced by the
one test using the real Host composition root instead of a hand-built
test container**: `EventStore.Masking.AddMasking()` registers
`PartialRevealMaskingStrategy` **keyed** (`"PartialReveal"`, for
`IPayloadMasker`'s own resolution), not as a plain unkeyed service.
`PartialRevealStreamRedactionStrategy` originally took it as an injected
constructor dependency, unkeyed, and failed to resolve against the real
Host's DI graph (`StreamingHttpSqliteTests`'s `ClassInit` threw). Fixed by
constructing it directly instead (`new PartialRevealMaskingStrategy()`) —
that class has no dependencies of its own, so injecting it was never
actually necessary.

## One real test-design bug, not a production bug

Two `StreamingScenarioAssertions` methods
(`ADeliberatelyReorderedSampleSetsLateArrivalFlagWithoutMovingTheHighWaterMark`
and `ASlowUploadingProducerTriggersAChannelLagDetectedEvent`) originally
shared one literal `"streaming-app"` `AppId`, and each makes two sequential
`IngestAsync` calls against a 4000-microsecond-interval channel. On
SQLite's fast in-process round trips this never mattered; against a real
Postgres/SQL Server Testcontainer, the genuine wall-clock gap between two
awaited calls routinely exceeds the 3x-interval lag threshold, so BOTH
methods' own incidental `ChannelLagDetected` events collided under one
shared `AppId` — `SingleOrDefaultAsync` threw "Sequence contains more
than one element" on `StreamingSqlServerTests` specifically (SQLite's own
faster round trips happened not to trigger it, making this provider-
dependent in practice, not provider-specific in cause). Fixed by giving
every scenario method its own unique `AppId` — the convention every other
`*ScenarioAssertions.cs` file in this repo already follows (e.g.
`entity-demo-1`, `entity-demo-2`, ...); this file should have followed it
from the start rather than reusing one shared literal.
