# Change log — 2026-08-04

New session, new branch (`design/service-level-agreement`), started from a
conversation about mixed-SLA telemetry consumers rather than a `TODO.md`
pass.

## Mixed near-real-time/delayed-review SLA: confirmed no design change needed, then named two concrete use cases

Walked through whether this design already supports telemetry consumers
with genuinely different latency tolerances (near-real-time vs. minutes'
delay acceptable) in one deployment. Confirmed it does, already
composably: `ADR-031`'s Streaming Channels plus the clinical-trials
domain's existing "Dual-channel live-safety vs. standard persistence"
special concern (a device publishing to two separate `Origin`
`TelemetryChannel`s — reduced-fidelity/fast vs. full-fidelity/archival)
already covers this without any change.

Two real use cases were then named — Intraoperative Neurophysiological
Monitoring (IONM, the low-latency end: a surgical-team alert during the
case) and polysomnography/sleep-study EEG (the delayed-review end: an
overnight capture scored by a technologist afterward, per the AASM
Scoring Manual's 30-second-epoch convention). `docs/domains/clinical-
trials-device-telemetry/README.md`'s "Special concerns" section now
names both concretely under the existing dual-channel bullet, and its
glossary gained `Intraoperative Neurophysiological Monitoring (IONM)`
and `Polysomnography (PSG)` entries. No ADR needed — this is existing
mechanism, newly documented against real cases, not a new decision.

## New question surfaced: tracked event acknowledgment — deferred, not built

Naming IONM surfaced a related but genuinely different question:
delivery latency isn't the same property as "did a human actually see
and act on this alert in time." Walked through what this design already
has for acknowledgment at the transport layer (publish's synchronous
`202`, `ADR-011`/`ADR-023`; Follow's checkpoint-is-the-ack shape,
`ADR-010`; webhooks' at-least-once retry plus `WebhookDeliveryFailed`
dead-letter, `ADR-060`) versus the human/business layer, where the
existing adverse-event-review workflow (`authorityDecision` referencing
a `targetEventId`, `ADR-035`/`ADR-066`) already gives the building
blocks with no new mechanism.

Whether "this event type expects a tracked response within a window"
deserves to become a first-class, opt-in registry capability (an
`ExpectedResponse` field on `EventTypeDefinition`, mirroring
`RequiredSignature`'s shape, paired with a reserved
`ExpectedResponseMissing` detector event mirroring `ADR-031`'s
`ChannelLagDetected`) or should stay a pure application convention was
weighed in full in a new comparison doc:
[`docs/comparisons/event-response-acknowledgment.md`](../comparisons/event-response-acknowledgment.md).
Recommendation: **defer** — IONM's same-session clinical ack and
pharmacovigilance's calendar-day 15-day regulatory clock
(`docs/domains/pharmacovigilance/README.md`, previously noted as having
"no owning ADR") are the only two concrete cases so far, and their
deadline semantics look different enough that generalizing from just one
risks guessing wrong about the other. Added to the comparisons catalog
(`docs/comparisons/README.md`) and as row 1 of `docs/10-open-questions.md`
(now non-empty again), marked **Back-burnered** with the explicit
revisit trigger — build both cases out for real, check whether the
watcher logic actually converges, decide then.
