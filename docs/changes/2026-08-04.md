# Change log — 2026-08-04

New session, new branch (`design/service-level-agreement`), started from a
conversation about mixed-SLA telemetry consumers rather than a `TODO.md`
pass.

## Mixed near-real-time/delayed-review SLA: confirmed no design change needed, then named two concrete use cases

Walked through whether this design already supports telemetry consumers
with genuinely different latency tolerances (near-real-time vs. minutes'
delay acceptable) in one deployment. Confirmed it does, already
composably: `ADR-031`'s Streaming Channels plus the clinical-trials
domain's existing "Dual-channel live-safety vs. standard persistence"
special concern (a device publishing to two separate `Origin`
`TelemetryChannel`s — reduced-fidelity/fast vs. full-fidelity/archival)
already covers this without any change.

Two real use cases were then named — Intraoperative Neurophysiological
Monitoring (IONM, the low-latency end: a surgical-team alert during the
case) and polysomnography/sleep-study EEG (the delayed-review end: an
overnight capture scored by a technologist afterward, per the AASM
Scoring Manual's 30-second-epoch convention). `docs/domains/clinical-
trials-device-telemetry/README.md`'s "Special concerns" section now
names both concretely under the existing dual-channel bullet, and its
glossary gained `Intraoperative Neurophysiological Monitoring (IONM)`
and `Polysomnography (PSG)` entries.

## ADR-094: expected-response tracking, adopted

Naming IONM surfaced a related but genuinely different question:
delivery latency isn't the same property as "did a human actually see
and act on this alert in time." A first pass at this (weighed in
`docs/comparisons/event-response-acknowledgment.md`) framed the fork as
"does IONM's same-session ack converge with pharmacovigilance's 15-day
regulatory clock" and recommended waiting for a second worked example
before generalizing. **That framing turned out to be wrong** — direct
correction received this session: IONM and polysomnography are domain-
level *example instances*, not the shape of a framework decision; a
plain `TimeSpan` already covers both a 300-second and a 15-day window
without strain, so "do the two examples' numbers match" was never the
right test. The actual test is whether the underlying *relationship*
("this event is a reply to that event") generalizes cleanly on its own —
and it does, directly via Hohpe & Woolf's **Correlation Identifier**
pattern, searched for and verified as real prior art before designing
anything bespoke (per `.claude/protocols/verify-before-citing.md`).

**`ADR-094`** adopts, on that basis:
- `StoredEvent.RespondsToEventId` — a new envelope field, the **eighth**
  distinct relationship-shaped one this design has (`CLAUDE.md`'s
  standing convention), answering a question none of the other seven do:
  "which prior event does this one satisfy a declared response
  expectation for." Not existence-validated at publish time, deliberately.
- `EventTypeDefinition.ExpectedResponse { ResponseEventType, Within }` —
  a nullable, opt-in registry declaration on the *request* event type,
  same shape `RequiredSignature` already established.
- `ExpectedResponseTracker` + a new singleton `ExpectedResponseWatcher`
  — architecturally an internal follower (`ProjectionHost`'s shape),
  leader-lease-gated (`ADR-078`), publishing a reserved
  `ExpectedResponseMissing` event (mirroring `ChannelLagDetected`'s
  treatment) exactly once per unmet expectation, late responses always
  recorded rather than treated as errors.
- Escalation policy itself stays explicitly out of framework scope — the
  same boundary `ADR-031` already draws for telemetry detection.

Propagated in the same pass, per `CLAUDE.md`'s standing rule that the
ADR introducing a persisted field is that field's naming authority:
`docs/data/event-log.md` (the new envelope field + an "Expected-response
tracking" section), `docs/data/schema-registry.md`
(`EventTypeDefinition.ExpectedResponse`, the `ExpectedResponseTracker`
entity), `CLAUDE.md`'s and `.claude/templates/adr-template.md`'s
repeated-relationship envelope-field bullets (now eight, not seven, with
this field's specific justifying question stated inline), a new pattern
doc (`docs/patterns/request-reply-correlation.md`, cataloged in
`docs/patterns/README.md`), a `references.md` row for Correlation
Identifier/Request-Reply, a named `08-build-plan.md` item ("Expected-
Response Tracking," including both its prose dependencies and its
PlantUML addition to the "additions since `ADR-050`" diagram), and the
clinical-trials domain doc's special concern updated from "deliberately
left to the application" to IONM's actual concrete configuration.

`docs/10-open-questions.md`'s row (added earlier this session) is
resolved and deleted accordingly — the file is empty again.
`docs/comparisons/event-response-acknowledgment.md` keeps its original
pros/cons for teaching value, per `docs/comparisons/README.md`'s own
stated purpose, with an "Update, same session" note explaining why its
original Recommendation was superseded rather than silently rewritten.

**Lesson worth carrying forward**: when a comparison doc's own
Recommendation is later overturned, the interesting content is *which
test the comparison used to decide, and why that test was wrong* — not
just "the decision changed." Recorded explicitly in the amendment rather
than only in this changelog, since the comparison doc is where a future
reader will actually look.

## Follow-up: worked feature doc, and a real pre-existing propagation bug caught in passing

Added `docs/features/expected-response-tracking.md` — the worked example
`08-build-plan.md`'s new item is built against (sequence diagrams for
tracking/on-time/escalation/late-response, the ER diagram, an ops-facing
Salt mockup, seven Gherkin scenarios) — closing the one real gap found
when auditing "what's left" against this design's own convention that
every core-engine capability gets one.

While grounding that doc's auth section, found `ADR-094`'s own claim that
`ADR-015` had already added a seeded OAuth2 client for `ProjectionHost`
to `docs/features/auth.md`'s table was false — that row had never
actually landed, despite `09-cqrs-read-models.md` saying for several
sessions that it would. Fixed directly: both `projections-client` (the
old gap) and `expected-response-watcher-client` (the new one) are now in
that table, and the inaccurate claims in `ADR-094`/`09-cqrs-read-
models.md` are corrected to describe what actually happened. A real
instance of this project's own repeated lesson — verify a propagation
claim against the actual file, never trust an ADR's Consequences section
saying something "is done."

A second follow-up audit caught one more stale enumeration:
`LeaderLease.WorkerRole`'s documented value set (`docs/data/schema-
registry.md`) still listed only the original four roles —
`ExpectedResponseWatcher` was missing. Fixed, and `RespondsToEventId`
gained a `docs/glossary.md` entry to match most of the other seven
envelope-metadata relationship fields.

## Workflow D: Intraoperative Monitoring and Alert Response, added on direct request

The clinical-trials + device-telemetry domain's target depth had been 4
feature docs/3 workflows since 2026-07-30. Direct request this session
grew it to 5/4: `docs/domains/clinical-trials-device-telemetry/features/
intraoperative-monitoring-and-alert-response.md` is a new, full-depth
feature doc (two sequence diagrams, an ER diagram, a state machine, a
3-screen Salt mockup, eight Gherkin scenarios) giving `ADR-094` its first
real domain-level exercise — chosen over a polysomnography workflow
specifically because IONM's same-session alert genuinely needs
`ExpectedResponse` tracking, while polysomnography's async scoring
workflow doesn't.

The workflow's real content: two `Origin` `TelemetryChannel`s (`ADR-031`)
provisioned for the trial's continuity subject (`S-0091`, continuing the
same patient Workflows A/B/C already follow); a detector's non-
authoritative `IonmAlertRaised` alert (`ADR-035`), tracked via
`EventTypeDefinition.ExpectedResponse`; a neurotechnologist's real-time
`IonmAlertAcknowledged` (`RespondsToEventId`, `ADR-094`) or, if missed, a
reserved `ExpectedResponseMissing` escalation; and, independently, an
attending neurologist's later, signed `authorityDecision` — reusing
Workflow B's exact mechanism unchanged (`ADR-042`/`ADR-066`) — as the
actual authoritative clinical interpretation. The doc is explicit that
the real-time acknowledgment and the authoritative interpretation are two
separate, never-conflated facts: a case can be acknowledged promptly and
still await the neurologist's own signed decision.

Propagated in the same pass: the domain `README.md`'s Workflows/Feature
docs/Special concerns sections and IONM glossary entry now point at the
real worked example instead of describing it abstractly; `CLAUDE.md`'s
domain-doc bullet now states the two proving-ground domains' feature-doc
counts explicitly rather than claiming they match (they no longer do,
and were never required to); `ADR-094`'s own Consequences bullet updated
to point at the worked example instead of promising a future one.
