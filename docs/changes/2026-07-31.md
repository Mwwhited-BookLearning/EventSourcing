## Ten new ADRs (`ADR-076`–`ADR-085`), resolving ten open-questions rows

Direct instruction: "create/update the ADRs based on your answers so far
so that open questions can be cleaned up," followed by a rapid working
session through the remaining rows, applying one recurring triage
principle throughout — **an ops/runbook concern can be deferred; only a
genuine dev/design decision needs resolving now** — plus, separately,
**a question resolvable with an existing mechanism (an ordinary API
call, an existing auth flow) doesn't need new framework machinery
invented for it.**

- **`ADR-076`** — EF Core migration bundles (`dotnet ef migrations
  bundle`) applied as a single deploy-time step, never `Database.
  Migrate()` at app startup; a provider-native declarative tool (DACPAC/
  `SqlPackage`, or **pgschema** — not `pgpkg`, a near-miss caught by
  checking the actual project — for Postgres) may apply the generated
  SQL instead. Resolved former row 12.
- **`ADR-077`** — instant feature-flag toggles via a chained, reload-
  token-based `IConfigurationProvider` (flag state as a reserved Event
  Log event per `ADR-067`'s pattern, polled every few seconds, `AppId`-
  scoped). Not actually a contradiction with `ADR-041`/`ADR-058`, once
  traced through .NET's own configuration-reload model. Resolved former
  row 13, this session's flagged highest-priority row.
- **`ADR-078`** — single-active-worker leader election via a database-
  backed lease per worker role (Router, UpcastMaterializer, each outbox
  pump), not a quorum system (etcd/ZooKeeper) — unnecessary, since each
  site already has one trusted database (`ADR-075`'s silo model) and
  production is Docker Compose (`ADR-026`), not an orchestrator with a
  native election primitive. Resolved former row 14.
- **`ADR-079`** — pluggable sanctions/watchlist screening
  (`ISanctionsScreeningProvider`, shaped like `ADR-057`'s
  `IErasureKeyStore`), scoped to the KYC/Meridian application's own
  composition root, not core Duplex — the first domain-scoped extension
  point in this design. Resolved former row 1.
- **`ADR-045`'s addendum** — GDPR Art. 33/34 breach-notification
  workflow ruled deliberately out of framework scope, an external legal/
  business process; `ADR-045`/`ADR-019` already supply the forensic
  inputs such a process would need. Resolved former row 2.
- **`ADR-080`** — dependency-vulnerability scanning (Dependabot,
  `dotnet list package --vulnerable`, `npm audit`) and build provenance
  (NuGet author signing, `npm publish --provenance`, targeting SLSA
  Level 2 now, Level 3 a named future escalation) on top of `ADR-074`'s
  SBOM. Resolved former row 6.
- **`ADR-081`** — `TelemetryChannel.ThreadId` groups multiple
  simultaneous channels under one session (a 32-electrode EEG montage
  case); `TelemetryPointer` generalizes from a single object to a list,
  for a detection spanning multiple channels at once. Revises `ADR-031`.
  Resolved former row 20.
- **`ADR-082`** — tenant-to-tenant federation is just an ordinary
  `client_credentials`-authenticated API call (`ADR-006`, no new auth
  mechanism); the actual event-shape mapping stays accepted as bespoke
  per tenant pair, optionally as a custom `IInterchangeFormatAdapter`
  implementation (`ADR-059`'s composition-root pattern) — no new adapter
  category, no shared interchange schema. Resolved former row 22.
- **`ADR-083`** — optional `TelemetrySample.MonotonicElapsedMicros`,
  captured by the client-side recording agent alongside wall-clock
  `Timestamp`, makes a lying device wall-clock detectable for `ADR-070`-
  sourced telemetry. Partially resolved row 11 — the RFC 3161 half is
  still open.
- **`ADR-084`** — readiness fails only when the instance's *own* core
  dependency is down, never merely because a peer/replica is degraded —
  failing readiness for a degraded peer would silently reintroduce the
  "block on trouble" behavior `ADR-023`'s never-block posture already
  rejected. A deployment may configure stricter semantics on top.
  Resolved row 8.
- **`ADR-085`** — performance-regression testing is its own decision
  (BenchmarkDotNet now, NBomber named as the escalation once a real
  deployment target exists — the same staged shape `ADR-063` already
  uses), but no framework-wide numeric throughput/latency targets are
  set — those are deployment-specific capacity planning, the same
  posture `ADR-058` already takes for per-tenant rate limits. Resolved
  row 10.

- **`ADR-086`** — RFC 3161 trusted timestamping for `ADR-066` signatures
  and `ADR-068` litigation exports (a TSA's `TimeStampToken` over an
  event's `ChainHash`), via a pluggable `ITimestampAuthorityClient`
  (`ADR-059`'s composition-root pattern, core-Duplex-scoped). Direct
  standing principle applied: prefer a real RFC/web standard over a
  custom mechanism whenever one is genuinely available — a restatement
  of `CLAUDE.md`'s existing "never invent a bespoke mechanism when a
  real standard already fits" convention, not a new one. Fully resolved
  former row 11 (no residual left).

- **`ADR-087`** — i18n/l10n is in framework scope as an *architectural
  requirement* (locale negotiation via `Accept-Language`, RFC 9110 §12;
  structural string-externalization in `ADR-039`'s view-definition
  format; culture-aware formatting via built-in `System.Globalization`/
  `Intl` APIs; RTL layout via W3C CSS Logical Properties) — the same
  requirement-vs-implementation split `ADR-073` already established for
  accessibility. The actual translated *content* is domain-owned, the
  same shape domain vocabulary/glossaries already are. Resolved row 19.

- **`ADR-088`** — the framework (and domains, by the same convention)
  emits detailed custom OpenTelemetry metrics/traces for its own async
  mechanisms (router fold lag, peer-sync outbox depth/age, webhook
  delivery lag, hash-chain verification outcomes) via `System.
  Diagnostics.Metrics`/`ActivitySource`, extending `ADR-026`'s existing
  pipeline with one additional `.AddMeter` call — no new observability
  stack. Narrowed row 7 rather than fully resolving it: the SLI/
  instrumentation half is decided; alert thresholds and the incident-
  response/on-call process itself stay exactly as deferred as before —
  genuine operational policy, not a dev decision.

- **`ADR-089`** — Event Log/`AccessLog` archival: detach a verified
  segment to `ADR-032`'s existing pluggable `IAttachmentContentStore`
  (serialized as the same NDJSON shape `ADR-068`'s export already uses),
  leaving a small `ChainCheckpoint` behind so live verification never
  touches archived data. No new interface — table partitioning is one
  valid backend implementation, not the framework's own decided
  mechanism; tier/backend stays provider-driven exactly like attachment
  tiering already is. Resolved row 18.
- **`ADR-090`** — read-your-writes across `ADR-033`'s multi-site mesh
  stays declined as a built-in guarantee, but is achievable today by the
  caller: filter by the write's own `EventId` for a single check, or by
  the newly-exposed `OriginId`+`SequenceNumber` in the publish response
  for a batch check. No frontier-token abstraction adopted — real prior
  art (Cosmos DB session tokens) was weighed, not dismissed, but this
  design already exposes what a token would otherwise encode opaquely.
  `OriginId`/`LogicalClock` (previously described in `ADR-033` but never
  propagated into `docs/data/event-log.md`) landed in this same pass,
  partially closing an old data-model-drift `TODO.md` item. Resolved
  row 21.
- **`ADR-091`** — CI/CD platform is GitHub Actions, decided purely
  because that's where this repository is hosted today — a deliberately
  low-stakes closure (there's no real pipeline yet to make concrete),
  not a comparative platform evaluation. Revisit for real if the repo
  ever moves hosts. Resolved row 5.
- **`ADR-092`** — the core engine's own trust model assumes non-
  malicious actors; `ADR-035`'s unauthenticated-submitter posture and
  `ADR-023`'s persist-everything exist to serve tolerant capture of an
  honest-but-wrong claim, not to harden against an adversary. Hostile-
  traffic defense (DDoS, credential stuffing) is a deployment-perimeter
  concern — an API gateway/WAF in front of `ADR-049`'s YARP entry point,
  not something the core engine defends against internally. No STRIDE
  threat model/risk register adopted as a framework artifact. Resolved
  row 9.

Row 7's SLO/alert-threshold/on-call half — left as "still deferred" in
this file's earlier draft — was confirmed as **not actually a framework-
level question at all**: pure operations/deployment-process policy with
no architecture or development decision embedded. Row 7 is now fully
removed rather than back-burnered, and `docs/10-open-questions.md`
gained a new standing exclusion category for this shape of concern.

- **`ADR-093`** — the last row. Row 16 (secret rotation for `ADR-040`'s
  ticket-signing and `ADR-060`'s webhook-signing secrets) was raised as
  a possible pure-ops question — resolved by splitting it the same way
  row 8 (readiness probes) split earlier: whether the schema/code can
  support a rotation window at all is a real capability decision (both
  secrets become a current+previous pair; `ADR-060`'s dispatcher emits
  dual signatures via Standard Webhooks' own already-adopted mechanism;
  the ticket-exchange verifier accepts either secret during the overlap
  window) — a schema change no amount of ops configuration could
  substitute for. The rotation *cadence* itself stays ops-configurable,
  unchanged, the same policy-vs-mechanism split `ADR-058`/`ADR-077`
  already use.
