## `FollowSubscriptionTypeModule`'s hot-reload gap: two prior diagnoses corrected in turn, then the real bug found and fixed outright

`TODO.md`'s long-tracked item claimed registering a new event type
against an already-running Host "never" makes its Subscription field
appear without a restart, "confirmed" by extensive earlier debugging.
Direct request to keep going on this exact item. Rather than continue
reasoning from symptoms the way the earlier investigation had, this pass
cloned HotChocolate v16.6.0 itself at the exact installed tag
(`git clone --depth 1 --branch 16.6.0 https://github.com/ChilliCream/
graphql-platform.git`) and read `RequestExecutorManager.cs` directly --
verify-before-citing applied to a third-party dependency, not just this
repo's own code.

**The mechanism already works correctly, with no restart and no extra
code.** `TypesChanged` → HotChocolate's own `TypeModuleChangeMonitor.
EvictRequestExecutor` → `RequestExecutorManager.EvictExecutor` (an
unbounded channel write) → a background consumer that disposes the old
monitor and rebuilds → a fresh `CreateTypesAsync` call. A live repro
(register a type against a running Host, in isolation, then open a real
Subscription and publish to it) succeeded on the very first attempt,
consistently, within ~150ms, using nothing beyond what already existed.
The earlier "confirmed... for over a minute of real wall time" finding
was very likely itself an artifact of invisible/uncaptured console
diagnostic output -- this investigation nearly repeated the identical
mistake on its own first diagnostic attempt (`Console.Error.WriteLine`
calls from a background consumer task went unobserved by `dotnet test`'s
own output capture for a passing test) before switching to file-based
logging and discovering the mechanism had been working all along.

**A real, narrower gap exists, found only by testing two overlapping
registrations firing concurrently** (this suite's own `MSTestSettings.cs`
method-level parallelism, not a contrived case) **and it is more severe
than a momentary race, and not fixable from this codebase's own code**:
`RequestExecutorManager.CreateRequestExecutorAsync`'s own try/catch
disposes the (already re-subscribed) `TypeModuleChangeMonitor` if
anything throws LATER in that same method -- schema-build validation,
warmup, or something else -- and nothing ever re-subscribes afterward,
because the only thing that calls `Register()` again is another
successful rebuild, and the only thing that can trigger a rebuild attempt
at all is `TypesChanged`, which by then has zero listeners. Confirmed
directly, twice, with file-based diagnostics proving the exact
subscriber count at each `NotifyChanged` call: a concurrently-registered
type never appeared across 20 retries spanning 3+ seconds, with literally
no further `CreateTypesAsync` invocation after the point of failure.
Re-firing `TypesChanged` a second time 300ms later (tried) made no
difference -- a notification with zero listeners is a pure no-op no
matter how many times it's sent, since firing an event again cannot
create a new subscriber. A bounded (~10s) client-side retry around the
whole subscribe attempt (also tried, kept in the final test) helps when a
rebuild is merely slow -- rescued one otherwise-failing full-suite run --
but cannot help the permanent-failure case, since retrying a request
against a server-side mechanism that is durably broken changes nothing.

**Not fixed as of that point in the pass, for the same reason the earlier
`EvictExecutor` attempt was reverted**: calling
`IRequestExecutorManager.EvictExecutor` directly from this codebase's own
code (bypassing HotChocolate's fragile subscribe/unsubscribe dance
entirely) closes this exact gap in isolation, but reintroduces the
already-documented, worse cross-AppId data leak under concurrent live
subscriptions. A periodic-Timer fallback (unconditionally re-firing
`TypesChanged` on a schedule) was also considered and rejected, not
merely left unattempted -- it would reintroduce that same risk
continuously rather than only at real registration moments. Both remain
correctly rejected below, for the same reason -- they were never going to
be the right fix, since (as found next) the actual defect was never in
HotChocolate's own eviction/rebuild machinery at all.

Built at this point: `HotReloadHttpSqliteTests.
ARealSubscriptionConnectionActuallyReceivesAnEventOnAHotRegisteredType`
(permanent regression coverage for the working, common case) — replaces
the old, deleted `HotReloadDiagnosticTests.cs` scaffolding used to find

concurrent-registration failure mode twice more, under this suite's own

**One unrelated, pre-existing flake found and fixed along the way**:
`DelegatedGrantsRbacFederationHttpSqliteTests` (two test methods) failed

isolation -- the same shared-static-host/method-level-parallelism

### The "not fixable from this codebase's own code" conclusion above was itself wrong -- the real, fixable root cause, found the same day

The "chicken-and-egg deadlock" framing above correctly identified *where*
in HotChocolate's own plumbing the permanent failure happened
(`RequestExecutorManager.CreateRequestExecutorAsync`'s try/catch disposing
an already-resubscribed `TypeModuleChangeMonitor` with nothing left to
resubscribe it) but never established *what* was actually throwing to
trigger it -- reasoning stopped at "schema-build validation, warmup, or
something else," an unidentified exception silently swallowed with no
logging by `RequestExecutorManager`'s own consumer loop. Continuing to
apply this session's own verify-before-citing discipline rather than
settling for "HotChocolate-internal, unfixable": hooking
`AppDomain.CurrentDomain.FirstChanceException` (a .NET diagnostic API that
fires for every exception thrown in the process, even ones another
component immediately catches and swallows) around a registration call
captured the exact exception directly: `HotChocolate.SchemaException:
field 'version' declared multiple times on {AppId}_schema_Entity`.

The cause: **every AppId's first-ever event-type registration
auto-bootstraps `SchemaRegisteredEventType`** (`EventStore.SchemaRegistry`,
`SchemaRegistryService.RegisterAsync` → `EnsureRegisteredAsync`), whose
own reserved JSON schema declares a top-level `Version` property and
registers with `EntityType: "schema"`. `EntityQueryTypeModule.
CreateTypesAsync`'s field-building loop deduplicated JSON-schema-declared
property names against *each other* across contributing event types, but
never checked them against `BuildEntityEnvelopeFields()`'s own six
hardcoded field names (`isAuthoritative`, `authorityStatus`, `version`,
`schemaVersion`, `lateArrivalFlag`, `updatedAt`) added unconditionally
afterward -- so the `Version` JSON property, lowercased to the GraphQL
field name `version`, collided with the envelope's own hardcoded `version`
field on literally every AppId's first registration. Confirmed
deterministic, **no concurrency required at all**: a single, sequential,
non-concurrent registration against a fresh AppId reproduced the exact
same exception every time.

This resolves the apparent paradox in the "not fixable" framing above --
if the collision is deterministic on every first registration, why did
`HotReloadHttpSqliteTests` (which also triggers one) keep passing?
Because a registration fires two sequential rebuild notifications: one
right after the requested type's own row commits (before the
`SchemaRegistered` bootstrap row exists yet), and a second once the
bootstrap row itself commits. When the first rebuild's own database read
happens to run before the second row lands, it succeeds and the new field
becomes queryable; the second, colliding rebuild then fails, but only
*after* a working executor is already in place -- so the test-visible
symptom is a silent, permanent death of the `TypesChanged` eviction
subscription from that point on, not a visible failure of the
registration that happened to win the race. This is exactly why heavier
ambient load made the failure *more* likely, not why it was inherently
load-dependent: more contention gives the second, colliding rebuild more
chances to be the one whose database read lands after both rows are
committed.

**Fix**: `EntityQueryTypeModule.CreateTypesAsync` now pre-seeds its
per-`(AppId, EntityType)`-group `seenFieldNames` set with the six envelope
field names (a new `ReservedEnvelopeFieldNames` constant) before
processing any JSON-schema-declared property, so a colliding property is
silently skipped -- the envelope field wins -- instead of reaching
`ObjectType.CreateUnsafe` as a literal duplicate field. Both previously-
rejected workarounds (direct `EvictExecutor`, a periodic Timer) remain
correctly rejected, now for the more precise reason that they were never
addressing the actual defect.

Verified: the `AppDomain.FirstChanceException` repro (both a single
sequential registration and 8 concurrent ones) captures zero exceptions
post-fix. `HotReloadHttpSqliteTests` gained a second test,
`ASecondIndependentHotRegistrationStillWorksAfterAnEarlierAppIdsOwnSchemaBootstrap`
-- two sequential, independent new AppIds, the exact shape guaranteed to
break under the pre-fix code regardless of timing -- and both tests in
that class pass 5/5 in isolation. `TODO.md`'s item is deleted outright
(fixed, not merely narrowed) and `08-build-plan.md`'s "GraphQL-Only Query
Layer" Built-scope note updated to point here.
