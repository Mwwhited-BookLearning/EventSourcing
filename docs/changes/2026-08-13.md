## `FollowSubscriptionTypeModule`'s hot-reload gap: two prior diagnoses corrected in turn, then the real bug found and fixed outright

`TODO.md`'s long-tracked item claimed registering a new event type
against an already-running Host "never" makes its Subscription field
appear without a restart, "confirmed" by extensive earlier debugging.
Direct request to keep going on this exact item. Rather than continue
reasoning from symptoms the way the earlier investigation had, this pass
cloned HotChocolate v16.6.0 itself at the exact installed tag
(`git clone --depth 1 --branch 16.6.0 https://github.com/ChilliCream/
graphql-platform.git`) and read `RequestExecutorManager.cs` directly --
verify-before-citing applied to a third-party dependency, not just this
repo's own code.

**The mechanism already works correctly, with no restart and no extra
code.** `TypesChanged` → HotChocolate's own `TypeModuleChangeMonitor.
EvictRequestExecutor` → `RequestExecutorManager.EvictExecutor` (an
unbounded channel write) → a background consumer that disposes the old
monitor and rebuilds → a fresh `CreateTypesAsync` call. A live repro
(register a type against a running Host, in isolation, then open a real
Subscription and publish to it) succeeded on the very first attempt,
consistently, within ~150ms, using nothing beyond what already existed.
The earlier "confirmed... for over a minute of real wall time" finding
was very likely itself an artifact of invisible/uncaptured console
diagnostic output -- this investigation nearly repeated the identical
mistake on its own first diagnostic attempt (`Console.Error.WriteLine`
calls from a background consumer task went unobserved by `dotnet test`'s
own output capture for a passing test) before switching to file-based
logging and discovering the mechanism had been working all along.

**A real, narrower gap exists, found only by testing two overlapping
registrations firing concurrently** (this suite's own `MSTestSettings.cs`
method-level parallelism, not a contrived case) **and it is more severe
than a momentary race, and not fixable from this codebase's own code**:
`RequestExecutorManager.CreateRequestExecutorAsync`'s own try/catch
disposes the (already re-subscribed) `TypeModuleChangeMonitor` if
anything throws LATER in that same method -- schema-build validation,
warmup, or something else -- and nothing ever re-subscribes afterward,
because the only thing that calls `Register()` again is another
successful rebuild, and the only thing that can trigger a rebuild attempt
at all is `TypesChanged`, which by then has zero listeners. Confirmed
directly, twice, with file-based diagnostics proving the exact
subscriber count at each `NotifyChanged` call: a concurrently-registered
type never appeared across 20 retries spanning 3+ seconds, with literally
no further `CreateTypesAsync` invocation after the point of failure.
Re-firing `TypesChanged` a second time 300ms later (tried) made no
difference -- a notification with zero listeners is a pure no-op no
matter how many times it's sent, since firing an event again cannot
create a new subscriber. A bounded (~10s) client-side retry around the
whole subscribe attempt (also tried, kept in the final test) helps when a
rebuild is merely slow -- rescued one otherwise-failing full-suite run --
but cannot help the permanent-failure case, since retrying a request
against a server-side mechanism that is durably broken changes nothing.

**Not fixed as of that point in the pass, for the same reason the earlier
`EvictExecutor` attempt was reverted**: calling
`IRequestExecutorManager.EvictExecutor` directly from this codebase's own
code (bypassing HotChocolate's fragile subscribe/unsubscribe dance
entirely) closes this exact gap in isolation, but reintroduces the
already-documented, worse cross-AppId data leak under concurrent live
subscriptions. A periodic-Timer fallback (unconditionally re-firing
`TypesChanged` on a schedule) was also considered and rejected, not
merely left unattempted -- it would reintroduce that same risk
continuously rather than only at real registration moments. Both remain
correctly rejected below, for the same reason -- they were never going to
be the right fix, since (as found next) the actual defect was never in
HotChocolate's own eviction/rebuild machinery at all.

Built at this point: `HotReloadHttpSqliteTests.
ARealSubscriptionConnectionActuallyReceivesAnEventOnAHotRegisteredType`
(permanent regression coverage for the working, common case) — replaces
the old, deleted `HotReloadDiagnosticTests.cs` scaffolding used to find
and confirm both findings above. Independently reproduced the SAME
concurrent-registration failure mode twice more, under this suite's own
full ~200-test aggregate load, with no second registration needed in the
same test class at all -- heavy ambient CPU/thread-pool/GC contention
from unrelated concurrent tests alone was enough to trigger it.

**One unrelated, pre-existing flake found and fixed along the way**:
`DelegatedGrantsRbacFederationHttpSqliteTests` (two test methods) failed
once each, in two different full-suite runs, both passing cleanly in
isolation -- the same shared-static-host/method-level-parallelism
interference already fixed repeatedly elsewhere this session. Fixed the
same way: `[DoNotParallelize]`.

### The "not fixable from this codebase's own code" conclusion above was itself wrong -- the real, fixable root cause, found the same day

The "chicken-and-egg deadlock" framing above correctly identified *where*
in HotChocolate's own plumbing the permanent failure happened
(`RequestExecutorManager.CreateRequestExecutorAsync`'s try/catch disposing
an already-resubscribed `TypeModuleChangeMonitor` with nothing left to
resubscribe it) but never established *what* was actually throwing to
trigger it -- reasoning stopped at "schema-build validation, warmup, or
something else," an unidentified exception silently swallowed with no
logging by `RequestExecutorManager`'s own consumer loop. Continuing to
apply this session's own verify-before-citing discipline rather than
settling for "HotChocolate-internal, unfixable": hooking
`AppDomain.CurrentDomain.FirstChanceException` (a .NET diagnostic API that
fires for every exception thrown in the process, even ones another
component immediately catches and swallows) around a registration call
captured the exact exception directly: `HotChocolate.SchemaException:
field 'version' declared multiple times on {AppId}_schema_Entity`.

The cause: **every AppId's first-ever event-type registration
auto-bootstraps `SchemaRegisteredEventType`** (`EventStore.SchemaRegistry`,
`SchemaRegistryService.RegisterAsync` → `EnsureRegisteredAsync`), whose
own reserved JSON schema declares a top-level `Version` property and
registers with `EntityType: "schema"`. `EntityQueryTypeModule.
CreateTypesAsync`'s field-building loop deduplicated JSON-schema-declared
property names against *each other* across contributing event types, but
never checked them against `BuildEntityEnvelopeFields()`'s own six
hardcoded field names (`isAuthoritative`, `authorityStatus`, `version`,
`schemaVersion`, `lateArrivalFlag`, `updatedAt`) added unconditionally
afterward -- so the `Version` JSON property, lowercased to the GraphQL
field name `version`, collided with the envelope's own hardcoded `version`
field on literally every AppId's first registration. Confirmed
deterministic, **no concurrency required at all**: a single, sequential,
non-concurrent registration against a fresh AppId reproduced the exact
same exception every time.

This resolves the apparent paradox in the "not fixable" framing above --
if the collision is deterministic on every first registration, why did
`HotReloadHttpSqliteTests` (which also triggers one) keep passing?
Because a registration fires two sequential rebuild notifications: one
right after the requested type's own row commits (before the
`SchemaRegistered` bootstrap row exists yet), and a second once the
bootstrap row itself commits. When the first rebuild's own database read
happens to run before the second row lands, it succeeds and the new field
becomes queryable; the second, colliding rebuild then fails, but only
*after* a working executor is already in place -- so the test-visible
symptom is a silent, permanent death of the `TypesChanged` eviction
subscription from that point on, not a visible failure of the
registration that happened to win the race. This is exactly why heavier
ambient load made the failure *more* likely, not why it was inherently
load-dependent: more contention gives the second, colliding rebuild more
chances to be the one whose database read lands after both rows are
committed.

**Fix**: `EntityQueryTypeModule.CreateTypesAsync` now pre-seeds its
per-`(AppId, EntityType)`-group `seenFieldNames` set with the six envelope
field names (a new `ReservedEnvelopeFieldNames` constant) before
processing any JSON-schema-declared property, so a colliding property is
silently skipped -- the envelope field wins -- instead of reaching
`ObjectType.CreateUnsafe` as a literal duplicate field. Both previously-
rejected workarounds (direct `EvictExecutor`, a periodic Timer) remain
correctly rejected, now for the more precise reason that they were never
addressing the actual defect.

Verified: the `AppDomain.FirstChanceException` repro (both a single
sequential registration and 8 concurrent ones) captures zero exceptions
post-fix. `HotReloadHttpSqliteTests` gained a second test,
`ASecondIndependentHotRegistrationStillWorksAfterAnEarlierAppIdsOwnSchemaBootstrap`
-- two sequential, independent new AppIds, the exact shape guaranteed to
break under the pre-fix code regardless of timing -- and both tests in
that class pass 5/5 in isolation. `TODO.md`'s item is deleted outright
(fixed, not merely narrowed) and `08-build-plan.md`'s "GraphQL-Only Query
Layer" Built-scope note updated to point here.

Verified overall: the full non-SqlServer suite (200 tests) passes clean;
one further, separate, pre-existing flake in an unrelated Timestamping
test was seen once during this pass's own verification runs (confirmed
passing alone, the same already-accepted "SQLite regression suite's own
known load-induced flakiness" category `TODO.md` already tracks
generically -- not a new instance introduced by this pass's own changes).
Full solution build clean.

## Two real, previously-undiscovered bugs in `PublishService`/`AccessLogAppender`/`SchemaRegistryService`'s interaction with Npgsql's retrying execution strategy — found, fixed, and regression-tested in sequence

### Bug 1: manual transactions vs. a retrying execution strategy

Found by actually running the AppHost against real Postgres and watching
`RouterWorker` throw `InvalidOperationException: The configured execution
strategy 'NpgsqlRetryingExecutionStrategy' does not support user-initiated
transactions` — not caught by any of the 224 `EventStore.IntegrationTests`
that existed before this pass, because none of them construct their
`DbContext` with `EnableRetryOnFailure` (only `EventStore.Host.Postgres`'s
real `Program.cs` does). Every event-sourcing site that calls
`db.Database.BeginTransactionAsync(...)` directly hits this the moment a
retrying strategy is active — EF requires the whole retryable unit (every
`Add`/`SaveChanges`, not just `BeginTransaction`/`Commit`) to run inside
`db.Database.CreateExecutionStrategy().ExecuteAsync(...)`, the documented
pattern this repo's own three call sites never used: `EventAppender.
AppendAsync`, `AccessLogAppender.AppendAsync`, and `SchemaRegistryService.
RegisterAsync`. Fixed by wrapping the existing `Add`-through-`Commit`
block of each in that delegate.

### Bug 2: the fix for Bug 1 introduced silent hash-chain corruption under real concurrency

Direct user feedback mid-pass ("you should be creating integration tests
for these bugs as you find/fix them") led to writing a real concurrency
regression test rather than trusting the Bug 1 fix on documentation alone
— `RetryOnFailurePostgresTests.
ManyConcurrentPublishesAgainstTheSameAppIdAllSucceedDespiteRealSerializationConflicts`,
30 genuinely simultaneous (`Task.WhenAll`) publishes against a real
Postgres Testcontainer, configured with the identical `EnableRetryOnFailure`
Program.cs uses. **It failed** — not with an exception, but with
`ChainVerificationResult.Tampered`: `EventAppender.AppendAsync`/
`AccessLogAppender.AppendAsync` naively wrapped their EXISTING bodies in
`ExecuteAsync`, but `storedEvent`/`entry` are constructed ONCE by the
caller and reused across every retry attempt. An attempt whose transaction
later aborted (a real `40001` serialization_failure — Serializable
isolation's own, by-design, "prevents a concurrent appender's own insert
from reading the same prior tail" behavior, exactly as `EventAppender`'s
own pre-existing comment already described) can still leave EF's change
tracker believing the identity-generated `SequenceNumber` was already
assigned; a bare re-`Add()` on the next attempt then skipped
re-generating it, so `ChainHash` got computed from a stale value that no
longer matched the row actually being inserted — corruption, not a crash,
the more dangerous failure mode of the two. Fixed by detaching each shared
entity and resetting its `SequenceNumber` to `default` at the top of every
attempt (`EventAppender.cs`/`AccessLogAppender.cs`), plus defensively
detaching any stale, same-keyed `EventParent` rows a prior aborted attempt
left tracked (not exercised by the test itself, which published with no
parents, but the identical latent defect for any retry with real parent
links). Re-running the same test after the fix passed clean.

Also added while writing this coverage: `EnableRetryOnFailure`'s own
`errorCodesToAdd` never actually included `40001` in `EventStore.
Host.Postgres/Program.cs` before this pass (only Migrator's own `3D000`
database-creation-race code) — without it, Npgsql's retrying strategy
doesn't even recognize a serialization failure as transient, so it would
never have retried at all, retry-loop-correctness bug notwithstanding.
Fixed alongside Bug 1/2's own fixes, not a third separate bug — the three
only became visible in this order because each one blocked the next from
ever being reached.

**`RetryOnFailurePostgresTests.cs`** (new) is now the permanent regression
suite for Bugs 1 and 2: a single schema registration, a single ordinary
publish, and a single AccessLog append, each under a retrying execution
strategy (guards Bug 1 and the missing-`40001` gap), plus the 30-way
concurrent publish test (guards Bug 2). Committed on a new branch,
`fix/postgres-retry-strategy-and-otel-metrics`, per direct request
(`f271b26`).

## A real, previously-undiscovered `client-web`/`client-web-vitals`/`client-web-meridian` bug: none of them could ever bind their own port

Direct report, after the Postgres crash was fixed: "vitals and meridian
also never load" (nor did the base `client-web` instance) — actually
launching the real AppHost and inspecting live process state (not
reasoning from the client-web side alone) found the cause has nothing to
do with Postgres at all. `AddViteApp`'s own dynamically-assigned port gets
passed as `npm run dev -- --port <N>`, but `client-web/package.json`'s
own `"dev"` script is itself a SECOND, nested `npm run dev --workspace=
packages/reference-app` delegation with no `--` separator of its own —
without one, npm's CLI parser two layers down silently swallows the
`--port` FLAG (confirmed directly via npm's own warning: `Unknown cli
config "--port"` / `"<N>" is being parsed as a normal command line
argument`) while letting the bare NUMBER fall through as `vite`'s
positional `root` argument instead of a port. `vite` then ignored that
nonsensical root and fell back to its own default port-conflict
resolution, auto-incrementing PAST 5173/5174/5175 (already claimed by
DCP's own proxy listeners for those exact ports) to whatever was free —
so every client-web instance was always listening on the WRONG port,
unreachable at the URL Aspire's own dashboard/docs advertise, for every
run this design has ever had. Fixed by adding the missing `--` at each
delegation boundary (`"dev": "npm run dev --workspace=packages/
reference-app --"`, same for `dev:vitals`/`dev:meridian`); verified in
isolation first (`npm run dev -- --port 39998` now correctly produces
`vite --port 39998` and binds exactly there), then end-to-end against the
real running AppHost — `curl` to `:5173`/`:5174`/`:5175` all returned a
real `200` after the fix, `000` (connection failure) before it.

**Process-forensics detour worth recording**: diagnosing this required
distrusting the initial assumption (the Postgres retry-budget fix must
not have fully worked) and instead inspecting the actually-running system
directly — `Get-CimInstance Win32_Process` command lines revealed the
exact three-layer npm delegation and the literal bare port number reaching
`vite.js`, and `Get-NetTCPConnection` revealed DCP itself (not Vite) was
the process actually bound to 5173/5174/5175, silently proxying to a
backend that had bound somewhere else entirely — the kind of state no
amount of re-reading the stack trace or the AppHost.cs source would have
surfaced.

## Four new dashboard links on the `eventstore` resource for EventStore.SpecGeneration's existing routes

Direct request: "add the openapi and asyncapi links to the aspire for the
service hosts." `EventStore.SpecGeneration.SpecGenerationEndpoints`
already mapped `/scalar/v1` (interactive OpenAPI UI, `ADR-025`),
`/openapi.json`, `/asyncapi.json`, and `/asyncapi-ui` — verified live
against the running `eventstore` resource (`curl`, all four `200`) before
touching `AppHost.cs`, not assumed from the route-mapping source alone.

Added via `WithUrlForEndpoint("https", ...)` on the `eventstore` builder,
four separate calls. A real API-shape detour: local reflection against
the installed `Aspire.Hosting.dll` was unreliable here too (the same
PowerShell 5.1/.NET Framework host mismatch `ADR-088`'s own GraphQL
detour hit), so the compiler's own overload-resolution errors plus
`dotnet/aspire` PR #8743's actual description became the verification
path instead. Two same-shaped but semantically opposite overloads exist:
a `Func<ResourceUrlAnnotation, ResourceUrlAnnotation>`-style mutate-and-
return callback REPLACES an endpoint's one existing URL on every call
(only the last of four would have survived), while
`Func<EndpointReference, ResourceUrlAnnotation>` — returning a brand
NEW `ResourceUrlAnnotation` via object-initializer, never mutating an
existing one — is the one PR #8743 specifically added to let multiple
calls accumulate. Used the latter for all four calls, confirmed by the
resulting code being unambiguous to the compiler (no more of the
overload-resolution confusion the mutating form produced).

## A real `EventTailReader`/Follow-Subscription bug: a client disconnecting surfaced as an unhandled exception instead of ending the stream

Direct report, pasted stack trace: a live GraphQL Subscription throwing
`System.Threading.Tasks.TaskCanceledException` from `EventTailReader.
TailAsync`'s own idle-poll `Task.Delay(pollInterval, ct)`, propagating
uncaught through `FollowSubscriptionTypeModule`'s pass-through
`Cast()` wrapper into HotChocolate's subscription executor. This is the
ORDINARY way a Subscription ends — a client closing a browser tab/
navigating away cancels `ct` mid-await exactly like this — never a
fault, but nothing in `TailAsync` distinguished "the caller asked to
stop" from a genuine failure. Direct request: "I would like more
graceful exceptions for this stuff."

Fixed by catching `OperationCanceledException` (matching only when
`ct.IsCancellationRequested`, so an unrelated cancellation — e.g. a
timeout on some other token — still propagates) at all three points
`TailAsync`'s single iterator method observes `ct`: the per-tick
`ToListAsync`/schema-lookup reads, the idle-poll `Task.Delay`, and the
per-event `GetVisibleParentEventIdsAsync`/`MaskPayloadAsync` calls inside
the yielding `foreach` — each `yield break`s cleanly instead of letting
the exception escape. The per-event case needed its own small `try` with
no `yield` inside it (C#'s iterator rule: `yield return`/`yield break`
cannot appear inside a `try` that has a `catch`), moving the actual
`yield return` outside the guarded block.

**Regression-tested, not just reasoned about**: added
`FollowScenarioAssertions.
DisconnectingMidTailEndsTheStreamGracefullyRatherThanThrowing` (shared
across `FollowSqliteTests`/`FollowSqlServerTests`/`FollowPostgresTests`,
this repo's own convention for provider-independent scenarios) —
connects with nothing published, lets `MoveNextAsync()` park inside the
real `Task.Delay`, cancels from outside once it's genuinely reached that
await (not before the loop even starts, which would prove nothing), and
asserts the pending call completes cleanly (`false`, no throw). Confirmed
this actually catches the reported bug, not just passes trivially: with
the fix reverted (`git stash`), the test fails with the EXACT reported
stack trace (`TaskCanceledException` at `EventTailReader.cs:85`); restored,
all three provider variants pass.
