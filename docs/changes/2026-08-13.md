## `FollowSubscriptionTypeModule`'s hot-reload gap: the "never works" claim was a misdiagnosis -- corrected, and the real, narrower gap found instead

`TODO.md`'s long-tracked item claimed registering a new event type
against an already-running Host "never" makes its Subscription field
appear without a restart, "confirmed" by extensive earlier debugging.
Direct request to keep going on this exact item. Rather than continue
reasoning from symptoms the way the earlier investigation had, this pass
cloned HotChocolate v16.6.0 itself at the exact installed tag
(`git clone --depth 1 --branch 16.6.0 https://github.com/ChilliCream/
graphql-platform.git`) and read `RequestExecutorManager.cs` directly --
verify-before-citing applied to a third-party dependency, not just this
repo's own code.

**The mechanism already works correctly, with no restart and no extra
code.** `TypesChanged` → HotChocolate's own `TypeModuleChangeMonitor.
EvictRequestExecutor` → `RequestExecutorManager.EvictExecutor` (an
unbounded channel write) → a background consumer that disposes the old
monitor and rebuilds → a fresh `CreateTypesAsync` call. A live repro
(register a type against a running Host, in isolation, then open a real
Subscription and publish to it) succeeded on the very first attempt,
consistently, within ~150ms, using nothing beyond what already existed.
The earlier "confirmed... for over a minute of real wall time" finding
was very likely itself an artifact of invisible/uncaptured console
diagnostic output -- this investigation nearly repeated the identical
mistake on its own first diagnostic attempt (`Console.Error.WriteLine`
calls from a background consumer task went unobserved by `dotnet test`'s
own output capture for a passing test) before switching to file-based
logging and discovering the mechanism had been working all along.

**A real, narrower gap exists, found only by testing two overlapping
registrations firing concurrently** (this suite's own `MSTestSettings.cs`
method-level parallelism, not a contrived case) **and it is more severe
than a momentary race, and not fixable from this codebase's own code**:
`RequestExecutorManager.CreateRequestExecutorAsync`'s own try/catch
disposes the (already re-subscribed) `TypeModuleChangeMonitor` if
anything throws LATER in that same method -- schema-build validation,
warmup, or something else -- and nothing ever re-subscribes afterward,
because the only thing that calls `Register()` again is another
successful rebuild, and the only thing that can trigger a rebuild attempt
at all is `TypesChanged`, which by then has zero listeners. Confirmed
directly, twice, with file-based diagnostics proving the exact
subscriber count at each `NotifyChanged` call: a concurrently-registered
type never appeared across 20 retries spanning 3+ seconds, with literally
no further `CreateTypesAsync` invocation after the point of failure.
Re-firing `TypesChanged` a second time 300ms later (tried) made no
difference -- a notification with zero listeners is a pure no-op no
matter how many times it's sent, since firing an event again cannot
create a new subscriber. A bounded (~10s) client-side retry around the
whole subscribe attempt (also tried, kept in the final test) helps when a
rebuild is merely slow -- rescued one otherwise-failing full-suite run --
but cannot help the permanent-failure case, since retrying a request
against a server-side mechanism that is durably broken changes nothing.

**Not fixed this pass, for the same reason the earlier `EvictExecutor`
attempt was reverted**: calling `IRequestExecutorManager.EvictExecutor`
directly from this codebase's own code (bypassing HotChocolate's fragile
subscribe/unsubscribe dance entirely) closes this exact gap in isolation,
but reintroduces the already-documented, worse cross-AppId data leak
under concurrent live subscriptions. A periodic-Timer fallback
(unconditionally re-firing `TypesChanged` on a schedule) was also
considered and rejected this pass, not merely left unattempted -- it
would reintroduce that same risk continuously rather than only at real
registration moments. A real fix needs eviction deferred until no
subscription may be live against the current executor, which this
codebase has no mechanism to track -- correctly scoped, both times, as
harder than "retry a dropped notification."
