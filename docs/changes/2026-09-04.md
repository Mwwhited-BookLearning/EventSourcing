Design-phase-only restriction lifted (`docs/changes/2026-09-03.md`'s own
last entries); this is real tooling-execution work, not docs. Picked the
one concrete slice named as highest-value: pack `EventStore.Abstractions`

**ADR-062's NuGet distribution story, proven**:
- `dotnet pack src/EventStore.Abstractions -o <local-feed>` — succeeded,
  but `dotnet add package EventStore.Abstractions` into a throwaway
  consumer project failed with `NU1101: Unable to find package
  EventStore.Domain` — a real, previously-unverified gap: `EventStore.
  Abstractions`'s `ProjectReference` to `EventStore.Domain` is
  automatically translated into a NuGet package dependency at pack time
  (confirmed by inspecting the generated `.nuspec`), but nothing had ever
  verified that packing ONE `EventStore.*` project while its own
  `ProjectReference` targets stay unpacked actually breaks restore for a
  real external consumer. `ADR-062`'s "every project becomes a package"
  framing is correct in principle but was never checked against this
  specific failure mode. Fixed by also packing `EventStore.Domain` (a
  leaf project, no further `ProjectReference`s of its own) to the same
  feed — restore then succeeded.
- Also found: `dotnet add package` does **not** persist the
  `PackageReference` into the `.csproj` if the restore it triggers fails
  — confirmed by `cat`-ing the file immediately after a failed `add
  package` and finding zero `<ItemGroup>` at all. Not a bug, just a real
  CLI behavior worth knowing (the failed first attempt's error output
  claims "Adding PackageReference..." which reads as if it already
  happened).
- Real proof, not just a successful restore: wrote a one-line
  `NoopMaskingStrategy : IMaskingStrategy` (the real interface, real
  namespace `EventStore.Masking` — note this differs from the package
  name `EventStore.Abstractions`, a real thing to know when consuming it)
  in the throwaway consumer project, referencing only the packages
  restored from the local feed. `dotnet build` — succeeded, 0 errors.

**ADR-054's Kiota SDK-codegen story, proven — with a real, previously-
unknown contract bug found along the way**:
- Started a real `EventStore.Host.Sqlite` instance. First attempt failed
  outright at startup (`SqliteException: no such table:
  EventTypeDefinitions`) — the fresh `eventstore.db` had no schema at
  all. Found the real mechanism (`ADR-076`, EF Core migration bundles,
  never `Database.Migrate()` at startup) and ran the committed
  `scripts/bundles/sqlite/efbundle` against it.
- **Second real finding**: that committed bundle binary was genuinely
  **stale by 17 days of real migrations** — dated 2026-08-10, but
  `src/EventStore.Persistence.Migrations.Sqlite/Migrations/`'s newest
  file is `20260827204717_AddEncryptedFieldIndexAndSearchIndexKeys.cs`.
  Applying the stale bundle got the Host further but it then crashed at
  GraphQL schema warmup with `SqliteException: no such column:
  e.ExpectedResponse` (`ADR-094`'s own column, added 2026-08-11, after
  the bundle's cutoff). `scripts/bundles/` is gitignored (a local build
  artifact, never committed — confirmed via `git check-ignore`), so this
  is a **local-only staleness**, not a repo defect anyone else would hit
  from a fresh clone — but it's a real, previously-undiscovered gap that
  nothing in this repo currently catches or warns about before a real
  deploy attempt tries to use a stale local bundle. Regenerated locally
  via `dotnet ef migrations bundle` (real command, real output) to
  unblock this task; **not** committed (gitignored) and not itself a
  code fix — flagged as a new `TODO.md` item below rather than silently
  worked around.
- With a fresh, current-schema database, the Host started and served
  `/openapi.json` successfully — but with `"paths": {}` (empty). Not a
  bug: `OpenApiDocumentBuilder` builds the publish surface entirely from
  currently-registered `EventTypeDefinitions`, and a fresh database has
  none. Registered one real event type (`DemoWidgetCreated`) via a real
  DPoP-signed (`ADR-017`/RFC 9449) `client_credentials` token from a
  real running `EventStore.DevIdp` instance and a real `PUT /registry/…`
  call — `201`. `/openapi.json` then had a real, populated
  `/publish/demowidgetcreated` path with a real generated schema.
- Ran the real, globally-installed Kiota CLI (`microsoft.openapi.kiota`
  1.35.0, already present — no fresh install needed) against that real
  spec: `kiota generate -d openapi.json -l CSharp -c EventStoreApiClient
  -n SdkCodegenProof.Client -o kiota-client`. Generated real, strongly-
  typed C# (`DemowidgetcreatedRequestBuilder`,
  `DemowidgetcreatedPostRequestBody`, etc.) — confirmed by reading the
  actual generated files, not just a success message. `kiota info -l
  CSharp` named `Microsoft.Kiota.Bundle` 2.0.0 as the one runtime
  dependency needed.
- Wrote a real throwaway console consumer referencing the generated
  client + `Microsoft.Kiota.Bundle`, a custom `IAuthenticationProvider`
  attaching a real bearer token + a real per-request DPoP proof
  (`EventStore.Dpop.DpopKeyPair`, the same real primitive
  `AuthScenarioAssertions.cs`'s own test helper uses), and called
  `client.Publish.Demowidgetcreated.PostAsync(...)` for real against the
  real running Host.
- **Third, most significant real finding**: this failed —
  `ApiException: ... 500`. The Host's own log showed the real cause:
  `BadHttpRequestException: Failed to read parameter "PublishEventRequest
  request" ... Cannot get the value of a token type 'StartObject' as a
  string`. `PublishEventRequest.Payload` (`src/EventStore.Inbox/
  PublishEventRequest.cs`) is, by design, a `string` — raw JSON text,
  "since its shape is whatever the registered schema... says it is," per
  its own code comment. But `OpenApiDocumentBuilder.BuildEnvelopeSchema`
  publishes `payload` in the OpenAPI document as a nested **JSON Schema
  object** matching the target event type's own schema, not as an opaque
  `string`. Kiota faithfully generates a client matching what the spec
  says — a strongly-typed nested object — which is genuinely
  **incompatible with the real wire contract**: the generated client, as
  generated, cannot successfully call this endpoint at all. Confirmed
  the root cause precisely (not just inferred) by sending a raw,
  hand-built HTTP request with `payload` as a JSON-encoded **string**
  instead of a nested object against the identical endpoint/token — real
  `202 Accepted`. This is a genuine, previously-undiscovered mismatch
  between `ADR-002`'s published OpenAPI contract and the real runtime
  deserialization behavior, not a Kiota bug and not a mistake in this
  proof's own code.
- **This was left unfixed, deliberately** — out of this task's own
  scope (a core `EventStore.SpecGeneration` change to how `payload` is
  described needs its own real design pass: `type: string` with the
  real schema moved to a `description`/`x-` extension is the obvious
  fix, but whether anything else — Scalar's own human-readable rendering
  of `/openapi.json`, `ADR-002`'s own documented contract — depends on
  the current, richer nested-object shape wasn't checked, and shouldn't
  be guessed at under this task's own scope). Filed as a new `TODO.md`
  item below rather than a `docs/bugs/` entry, per that protocol's own
  "filed the same pass it's fixed" bar — this one isn't fixed yet.
