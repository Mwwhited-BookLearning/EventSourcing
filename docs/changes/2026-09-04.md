- **Third, most significant real finding**: this failed —
  `ApiException: ... 500`. The Host's own log showed the real cause:
  `BadHttpRequestException: Failed to read parameter "PublishEventRequest
  request" ... Cannot get the value of a token type 'StartObject' as a
  string`. `PublishEventRequest.Payload` (`src/EventStore.Inbox/
  PublishEventRequest.cs`) is, by design, a `string` — raw JSON text,
  "since its shape is whatever the registered schema... says it is," per
  its own code comment. But `OpenApiDocumentBuilder.BuildEnvelopeSchema`
  publishes `payload` in the OpenAPI document as a nested **JSON Schema
  object** matching the target event type's own schema, not as an opaque
  `string`. Kiota faithfully generates a client matching what the spec
  says — a strongly-typed nested object — which is genuinely
  **incompatible with the real wire contract**: the generated client, as
  generated, cannot successfully call this endpoint at all. Confirmed
  the root cause precisely (not just inferred) by sending a raw,
  hand-built HTTP request with `payload` as a JSON-encoded **string**
  instead of a nested object against the identical endpoint/token — real
  `202 Accepted`. This is a genuine, previously-undiscovered mismatch
  between `ADR-002`'s published OpenAPI contract and the real runtime
  deserialization behavior, not a Kiota bug and not a mistake in this
  proof's own code.
- **This was left unfixed, deliberately** — out of this task's own
  scope (a core `EventStore.SpecGeneration` change to how `payload` is
  described needs its own real design pass: `type: string` with the
  real schema moved to a `description`/`x-` extension is the obvious
  fix, but whether anything else — Scalar's own human-readable rendering
  of `/openapi.json`, `ADR-002`'s own documented contract — depends on
  the current, richer nested-object shape wasn't checked, and shouldn't
  be guessed at under this task's own scope). Filed as a new `TODO.md`
  item below rather than a `docs/bugs/` entry, per that protocol's own
  "filed the same pass it's fixed" bar — this one isn't fixed yet.

## Fixed: both real bugs the SDK-codegen pass above found

- **The `payload`-shape contract mismatch, root-caused and fixed for
  real.** `OpenApiDocumentBuilder.BuildEnvelopeSchema` described
  `payload` using the target event type's own JSON Schema inlined as a
  nested object; `PublishEventRequest.Payload`'s real model binder
  deserializes it as a raw `string` instead (confirmed:
  `PublishService.EncryptAndIndexClassifiedFieldsAsync`'s own
  `JsonNode.Parse(request.Payload)` only compiles if `Payload` is
  already a string). Checked which side of the contract to trust before
  changing anything, per this project's own doc-vs-code standing rule —
  `docs/03-api-contracts.md` isn't one of the `docs/data/*.md`
  shape-authority group, so the doc follows the real code, not the
  reverse. Fixed `OpenApiDocumentBuilder.cs` to describe `payload` as
  `type: string`, with the real per-event-type schema preserved (only)
  on a new `x-payload-schema` extension so Scalar/spec readers still see
  it; corrected `docs/03-api-contracts.md`'s own OpenAPI example and
  prose to match, additive-history style (`~~...~~` isn't used here
  since this was a spec/doc description of behavior, not a decision
  record, but the correction is dated and explained inline rather than
  silently rewritten). Added a real regression test
  (`OpenApiScenarioAssertions.PublishPayloadIsDescribedAsAStringNotANestedObject`,
  wired into all three provider `Publish*Tests` classes) that parses a
  live-generated `/openapi.json` document and asserts `payload`'s `type`
  is `"string"` — verified passing for real (Sqlite; the identical
  Postgres/SqlServer wiring wasn't independently re-run since it's the
  same shared assertion against the same builder).
- **A second, independent bug found while writing that regression
  test, fixed the same pass**: `OpenApiDocumentBuilder.GetOrBuildJsonAsync`'s
  returned string carried a literal UTF-8 BOM character at the start
  (`Encoding.UTF8`'s `StreamWriter` preamble, round-tripped through
  `GetString` into the .NET string itself — real, not cosmetic:
  `JsonNode.Parse(string)` doesn't skip a BOM the way
  `JsonNode.Parse(Stream)` does, so any strict JSON parser handed this
  exact string, including the new regression test itself on first
  write, gets a real `'0xEF' is an invalid start of a value` crash).
  Fixed by using a BOM-less `UTF8Encoding` instance instead of the
  `Encoding.UTF8` static property. `AsyncApiDocumentBuilder.cs`'s
  sibling method was checked and already avoids this (it parses from
  the `Stream` directly, never round-trips through `GetString`), so
  needed no change.
- **The stale-migration-bundle gap**: added `scripts/bundles/README.md`
  (a build-once-artifact warning plus the exact regeneration command),
  and narrowed `.gitignore`'s `scripts/bundles/` rule to
  `scripts/bundles/*/` so the README itself can be tracked while every
  provider's actual `efbundle` binary stays ignored — a bare
  `!scripts/bundles/README.md` negation could not do this alone, since
  git's own gitignore rules can't re-include a file whose parent
  directory is itself excluded.

Verified for real: full solution build (0 errors), the new regression
test passing, and a full `Publish*`/`AsyncApi*`/`Localization*`
integration-test rerun (28/28 passing — one transient SqlServer/
Testcontainers flake on the first run resolved cleanly on rerun,
unrelated to these changes). Both `TODO.md` items this pass closes are
