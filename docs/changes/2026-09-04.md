## Fixed: both real bugs the SDK-codegen pass above found

- **The `payload`-shape contract mismatch, root-caused and fixed for
  real.** `OpenApiDocumentBuilder.BuildEnvelopeSchema` described
  `payload` using the target event type's own JSON Schema inlined as a
  nested object; `PublishEventRequest.Payload`'s real model binder
  deserializes it as a raw `string` instead (confirmed:
  `PublishService.EncryptAndIndexClassifiedFieldsAsync`'s own
  `JsonNode.Parse(request.Payload)` only compiles if `Payload` is
  already a string). Checked which side of the contract to trust before
  changing anything, per this project's own doc-vs-code standing rule —
  `docs/03-api-contracts.md` isn't one of the `docs/data/*.md`
  shape-authority group, so the doc follows the real code, not the
  reverse. Fixed `OpenApiDocumentBuilder.cs` to describe `payload` as
  `type: string`, with the real per-event-type schema preserved (only)
  on a new `x-payload-schema` extension so Scalar/spec readers still see
  it; corrected `docs/03-api-contracts.md`'s own OpenAPI example and
  prose to match, additive-history style (`~~...~~` isn't used here
  since this was a spec/doc description of behavior, not a decision
  record, but the correction is dated and explained inline rather than
  silently rewritten). Added a real regression test
  (`OpenApiScenarioAssertions.PublishPayloadIsDescribedAsAStringNotANestedObject`,
  wired into all three provider `Publish*Tests` classes) that parses a
  live-generated `/openapi.json` document and asserts `payload`'s `type`
  is `"string"` — verified passing for real (Sqlite; the identical
  Postgres/SqlServer wiring wasn't independently re-run since it's the
  same shared assertion against the same builder).
- **A second, independent bug found while writing that regression
  test, fixed the same pass**: `OpenApiDocumentBuilder.GetOrBuildJsonAsync`'s
  returned string carried a literal UTF-8 BOM character at the start
  (`Encoding.UTF8`'s `StreamWriter` preamble, round-tripped through
  `GetString` into the .NET string itself — real, not cosmetic:
  `JsonNode.Parse(string)` doesn't skip a BOM the way
  `JsonNode.Parse(Stream)` does, so any strict JSON parser handed this
  exact string, including the new regression test itself on first
  write, gets a real `'0xEF' is an invalid start of a value` crash).
  Fixed by using a BOM-less `UTF8Encoding` instance instead of the
  `Encoding.UTF8` static property. `AsyncApiDocumentBuilder.cs`'s
  sibling method was checked and already avoids this (it parses from
  the `Stream` directly, never round-trips through `GetString`), so
  needed no change.
- **The stale-migration-bundle gap**: added `scripts/bundles/README.md`
  (a build-once-artifact warning plus the exact regeneration command),
  and narrowed `.gitignore`'s `scripts/bundles/` rule to
  `scripts/bundles/*/` so the README itself can be tracked while every
  provider's actual `efbundle` binary stays ignored — a bare
  `!scripts/bundles/README.md` negation could not do this alone, since
  git's own gitignore rules can't re-include a file whose parent
  directory is itself excluded.

## Item 55's own dedicated security review: performed, found and fixed 2 real bugs, still not marked Done

`08-build-plan.md`'s Order-Revealing Encryption item (`ADR-097`) has
named its own bespoke crypto primitive's dedicated correctness/security
review as a real, separate gate since `2026-08-27` — nobody had actually
done it. Read `src/EventStore.Erasure/OrderRevealingEncryption.cs` in
full, its tests, `ADR-097`, and verified for real (WebSearch, not
assumed) the two attack papers `ADR-097` already cites — Naveed/Kamara/
Wright (CCS 2015) and Grubbs/Sekniqi/Bindschaedler/Naveed/Ristenpart,
confirmed as IEEE S&P 2017 (IACR ePrint 2016/895) and accurately
characterized in both this file and `MaskingSchemaValidator.cs`'s own
citation.

**Two real, previously-unknown correctness bugs found and fixed, each
with a new regression test**:
1. `double.Parse` silently accepted `"NaN"`/`"Infinity"`/`"-Infinity"`
   text for a `Number` field, producing an encoding with no defined
   relationship to .NET's own NaN-handling `CompareTo` order. Now
   rejected explicitly.
2. **+0.0 and -0.0 encoded to different ciphertext and compared as
   ordered**, but .NET's own `double.CompareTo` — the correctness oracle
   every existing test in this file is defined against — treats them as
   equal. The new regression test for this initially asserted the wrong
   expected value (based on an incorrect assumption that .NET's
   `CompareTo` uses IEEE 754-2008 totalOrder semantics for signed zero);
   running it for real caught the mistake immediately, which is exactly
   the point of writing the test rather than reasoning about the
   ordering from memory. Fixed by canonicalizing -0.0 to +0.0 before
   encoding.

Also added explicit documentation, in the implementation's own header,
of a leakage property this construction has always had but never stated
in one place: identical plaintext under the same key produces
byte-identical ciphertext, so anyone with read access to the stored
column (not just query access) can identify every group of equal-valued
rows with zero decryption. Confirmed the no-override guardrail
(`x-masking-searchable.indexKind: "OrderRevealing"` refused unconditionally
on any field also carrying `x-masking.regulatoryClassification`) is
enforced at the single real registration path
(`MaskingSchemaValidator`), not something with a bypass.

**Deliberately still not marked Done** — the review happened and is
recorded, satisfying the item's exit criterion by its literal text, but
a solo AI review of a bespoke, from-scratch cryptographic primitive does
not meet the bar a "dedicated correctness/security review" of something
this specialized implies, even one that found and fixed two real bugs.
Genuine recommendation, not a hedge: get an independent human
cryptographic review before enabling this on any real production data.
Also still blocked, separately, on the pre-existing app-tier-only
comparison scope limit (item 56 above only builds the native evaluator
seam for the sibling `Range`/`Equality` indexes, not `OrderRevealing`
itself — `ADR-098`'s own scope, unaffected by this review).

Verified for real: `dotnet test` on the affected unit tests (8/8 passing,
including the 2 new regression tests), a full solution build (0 errors),
and the existing `SearchableEncryptionSqliteTests` (7/7 passing,
confirming the no-override guardrail and erasure/query paths are
unaffected by these fixes).
