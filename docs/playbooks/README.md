# UI Playbooks

A **seventh kind of document** in this design package, distinct from
everything else under `docs/`: every other doc is written and maintained
by hand; every file under this folder is **generated** by
`tests/EventStore.E2ETests` (`ADR-055`'s own "Implementation note,
2026-08-28" addendum) — a real Playwright walkthrough of a real user
workflow against the actual running application, with a screenshot
captured at each meaningful step, assembled into a markdown user guide.

**Never hand-edit a file under this folder.** Every playbook's own first
line says so, but it's worth stating here too: the content is
overwritten the next time its owning test runs. Edit the test's own step
captions instead (`tests/EventStore.E2ETests/*PlaybookTests.cs`), then
re-run `dotnet test tests/EventStore.E2ETests` to regenerate.

## Naming convention

`docs/playbooks/{domain}/{workflow}-{feature doc name}.md` — reuses each
proving-ground domain's own already-established `Workflow` lettering
(`docs/domains/{domain}/README.md`'s own `## Workflows` section: Vitals'
A–D, Meridian's A–C) as this project's closest existing "epic" concept,
rather than inventing a new one (confirmed with the user rather than
assumed, since this project has no literal "epic" term anywhere else).
Screenshots for a given playbook live in a sibling folder matching the
markdown file's own basename (e.g.
`workflow-a-patient-enrollment-and-informed-consent/step-01.png`), so
the prose and its images move or delete together as one unit.

**A genuinely interesting, separate finding surfaced building the
screening playbook**: the registered `ApplicantIdentity` `ViewDefinition`
template's own bound fields (`applicantId`/`documentType`/
`claimedLegalName`/`dateOfBirth`/`did`) don't match `SanctionsScreening
Performed`'s payload shape at all — only `applicantId` renders, every
other field on screen is blank, and the actually-useful screening data
(`ScreeningDate`/`ListsChecked`/`MatchFound`) never appears through this
template even though it's genuinely published. A `ViewDefinition` is
scoped to an `EntityType`, but the data actually available in any given
client instance is scoped to the one `EventType` it subscribes to —
nothing currently reconciles the two. Not fixed here (redesigning the
template is a real content decision, out of this pass's scope) —
flagged plainly in the playbook's own caption instead of quietly
producing a misleadingly sparse screenshot.
