# References

A single bibliography for every real-world standard, spec, pattern, or
library this design package relies on or seriously considered. Each
numbered doc (`01`–`09`) also carries its own short "Suggested References"
section with just the citations relevant to that doc — this file is the
comprehensive index, organized by whether the concept was actually
**adopted** into the design or is recorded here as **reference-only**
(considered, and explicitly not built, with the reason stated).

## Reference-only — considered, not adopted

Recorded here for the same reason `README.md` states its own "deliberately
is not" scope decisions plainly rather than silently: so a reader doesn't
have to wonder whether something was overlooked versus deliberately left
out.

| Concept | Standard / spec | Why it's not in this design |
|---|---|---|
| Transactional Outbox pattern | [microservices.io — Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html) | Still not needed for its classic purpose — "how do I atomically update my own row *and* publish an event about it" (the dual-write problem) — since `Events` **is** the log Follow tails directly; publish and append are the same write, no second system to keep in sync with (`ADR-015`'s consequences touch on this from the projection side). **Disambiguation, not a reversal**: this design's own "outbox" terminology elsewhere (`ADR-033`'s peer-sync outbox/inbox, `ADR-039`'s client-local outbox) is a durable-retry-queue primitive, a different problem from the classic Transactional Outbox's dual-write atomicity — same word, two different mechanisms, per this design's own "disambiguate terminology collisions" convention. |
| DNS-SD / mDNS service discovery | [RFC 6763](https://datatracker.ietf.org/doc/html/rfc6763), [RFC 6762](https://datatracker.ietf.org/doc/html/rfc6762) | Still not adopted, but re-examined: `ADR-033`'s cross-site peer discovery (how a new peer server finds other sites) is a related, real question orchestration alone doesn't answer once sites are independently deployed — but mDNS/DNS-SD are LAN-scoped discovery protocols, the wrong tool for cross-internet, cross-site discovery specifically, so they don't become the answer just because a related need appeared. See `docs/10-open-questions.md`. |
| Strangler Fig migration pattern | [Martin Fowler — StranglerFigApplication](https://martinfowler.com/bliki/StranglerFigApplication.html) | This is a from-scratch design, not a legacy migration — there's nothing being strangled. |
| Capability tokens (Macaroons/Biscuit) | [Macaroons (Google/NDSS 2014)](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/), [Biscuit](https://doc.biscuitsec.org/reference/specifications.html) | **Reasoning updated, still not adopted.** This entry's own stated bar for reconsidering — "a caller needing to mint a narrower credential for someone else without going back to the IdP" — has since arisen (`ADR-043`'s delegated access grants). It was filled by UCAN (already adopted, `ADR-036`), not Macaroons/Biscuit: UCAN's attenuated-delegation-chain model already covers the exact same territory these would have, so adding a second capability-token format alongside it would be redundant, not additive. |
| Local-first software / CRDTs | [Ink & Switch — Local-first software](https://www.inkandswitch.com/essay/local-first/), [Automerge](https://automerge.org/docs/hello/), [Yjs](https://docs.yjs.dev/) | Re-examined after `ADR-033` (multi-origin replication) and `ADR-039` (offline-first client outbox) — both are genuinely local-first/concurrent-write scenarios this rejection's original reasoning predates. | WebDAV, entirely | [RFC 4918](https://datatracker.ietf.org/doc/html/rfc4918) | Considered for `ADR-032`'s browsable attachment access, decided against — see `docs/comparisons/webdav-library.md`. Every library option was flawed (NWebDav archived, Dav.AspNetCore.Server thin, IT Hit commercial), and once the attachment store's other access paths were confirmed already served by plain HTTP + GraphQL, WebDAV's one unique value (OS-native mounting) wasn't worth any of the three trade-offs. |
| NWebDav | [github.com/ramondeklein/nwebdav](https://github.com/ramondeklein/nwebdav) | Considered for `ADR-032`; repository archived (read-only) July 19, 2025, disqualifying it outright regardless of the WebDAV-entirely decision above — `docs/comparisons/webdav-library.md` |
| Dav.AspNetCore.Server | [github.com/ThuCommix/Dav.AspNetCore.Server](https://github.com/ThuCommix/Dav.AspNetCore.Server) | Considered for `ADR-032` — free and current, but thin (3 stars/7 forks) for security-relevant surface area; moot once WebDAV itself was declined — `docs/comparisons/webdav-library.md` |
| IT Hit WebDAV Server Engine for .NET | [webdavsystem.com/server](https://www.webdavsystem.com/server/) | Considered for `ADR-032` — the only genuinely well-maintained WebDAV library found (v14+, full cross-platform ASP.NET Core support), but commercial/paid, which would have been this design's first paid dependency — `docs/comparisons/webdav-library.md` |
| Chain-of-Responsibility (rendering fallback) | *Design Patterns* (Gamma, Helm, Johnson, Vlissides), 1994 | **Reasoning updated, still not adopted.** This design now has a real UI/rendering layer (`ADR-039`'s MVVM client, `features/mvvm-client.md`'s real Salt mockup) — the original "no UI layer at all" reasoning is stale.
